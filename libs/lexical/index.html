lexical is a header-only library of validators for the string formats of JSON Schema, in C++20, one of the libraries of webcpp. Each format is a function that takes a std::string_view and answers bool, and, but regex, a Boost.URL grammar rule, which composes with Boost.URL’s combinators into grammars of a program’s own. Each is checked as its RFC or ECMA-262 defines it, against the official JSON-Schema-Test-Suite, and regex against V8. Nothing allocates but an IRI too long for its inline buffer, through a std::pmr::memory_resource.

This page teaches lexical format by format: what each checks, its rules and its examples. Every program it shows was compiled and run, natively and for wasm32-wasip2, wasm32-wasip3 and emscripten, and printed the output shown under it. The reference that closes it lists every name the headers declare.

Introduction

JSON Schema names string formats, date-time, email, hostname, uri, regex and the others, each defined by an RFC or by ECMA-262. lexical checks each of them as its reference defines it, and nothing more: a validator answers whether a string is in the format, and a rule says where in a longer input the format’s text ends.

Every validator takes any byte string. One that is not well-formed UTF-8 is invalid in every format, and in the formats that are ASCII, so is any byte above 0x7F.

A first example

A program that checks a string of a few formats:

#include <webcpp/lexical.hpp>

#include <iostream>
#include <string_view>

namespace lexical = webcpp::lexical;

namespace {

void show(std::string_view format, std::string_view text, bool valid) {
    std::cout << format << ' ' << text << ": " << (valid ? "valid" : "invalid") << '\n';
}

}  // namespace

int main() {
    show("date-time", "1985-04-12T23:20:50.52Z", lexical::is_date_time("1985-04-12T23:20:50.52Z"));
    show("date", "2021-02-29", lexical::is_date("2021-02-29"));
    show("email", "joe.bloggs@[IPv6:::1]", lexical::is_email("joe.bloggs@[IPv6:::1]"));
    show("hostname", "xn--nxasmq6b.example", lexical::is_hostname("xn--nxasmq6b.example"));
    show("uri", "//example.com/p", lexical::is_uri("//example.com/p"));
    show("uri-reference", "//example.com/p", lexical::is_uri_reference("//example.com/p"));
    show("json-pointer", "/a~1b", lexical::is_json_pointer("/a~1b"));
}

It prints:

date-time 1985-04-12T23:20:50.52Z: valid
date 2021-02-29: invalid
email joe.bloggs@[IPv6:::1]: valid
hostname xn--nxasmq6b.example: valid
uri //example.com/p: invalid
uri-reference //example.com/p: valid
json-pointer /a~1b: valid

2021-02-29 is no date, 2021 being no leap year; //example.com/p is a URI reference and no URI, which needs a scheme.

Requirements

<webcpp/lexical.hpp> includes every format but regex, whose header <webcpp/lexical/regex.hpp> brings the Unicode tables of ECMA-262’s classes; the names are in the namespaces webcpp::lexical and webcpp::lexical::grammar. lexical is header-only C++20 and needs Boost 1.92 or newer: Boost.URL, whose compiled part webcpp builds from Boost’s sources for every target, and Boost.System; and webcpp’s configuration, config, and webcpp::idna, for internationalized names. A b2 project uses it through /webcpp/lexical//lexical, which brings all of them:

    <library>/webcpp/config//config
    <library>/webcpp/idna//idna
    <library>/webcpp//boost_url ;

It runs natively, on wasm32-wasip2 and wasm32-wasip3, and on emscripten, with exceptions or without.

Dates and times

is_date_time, is_date and is_time check RFC 3339’s date-time, full-date and full-time (section 5.6), and is_duration its appendix A’s duration, exactly: ASCII digits only, a month 01 to 12, a day that exists in its month of the Gregorian calendar (February 29 in a year divisible by 4, and not by 100 unless by 400), hours 00 to 23, minutes 00 to 59, any number of fraction digits, and an offset of Z or +hh:mm/-hh:mm. T and Z match in either case, as RFC 3339’s note says; so do the letters of a duration, which are ABNF’s quoted strings (RFC 5234 2.3).

Second 60 is a leap second. RFC 3339 allows it when the time, moved to UTC by its offset, is 23:59, and is_time(s) follows it, as drafts 7 to 2020-12 of JSON Schema test. JSON Schema v1 says a time must not hold one: is_time(s, leap_seconds::refused) is its time. is_date_time allows them in every draft, v1 included, as the suite’s date-time tests say. The date of a leap second is not checked against IERS’s list: no table, the same answer every year.

A duration’s numbers are never converted, so any number of digits is valid and nothing overflows. P1Y2D is invalid: appendix A keeps years, months and days in that order and contiguous, and a week stands alone.

Identifiers

is_uuid checks RFC 9562’s string form of a UUID: 32 hexadecimal digits in either case, in groups of 8, 4, 4, 4 and 12 joined by hyphens. It checks the shape, not the version or the variant, as JSON Schema’s suite asks; braces and the urn:uuid: prefix are not part of the form.

is_json_pointer checks RFC 6901’s JSON Pointer: the empty string, or reference tokens each led by /, in which ~ is followed by 0 or 1. A token holds any other code point, NUL included, so the string is decoded as UTF-8 and must be well-formed.

is_relative_json_pointer checks a relative JSON Pointer: a non-negative integer without a leading zero, then # or a JSON Pointer. Draft 2020-12 and v1 of JSON Schema cite draft-bhutton-relative-json-pointer-00, which lets an index manipulation follow the integer, a sign and another non-negative integer without a leading zero (0+1, 0-0); drafts 7 and 2019-09 cite draft-handrews-relative-json-pointer-01, which has none. The draft’s grammar puts the manipulation only before a JSON Pointer, yet its own example 0-1# puts it before #; lexical accepts both, so 1-1# is valid too. The function takes that choice as its second argument: index_manipulation::allowed, the default, for 2020-12 and v1, and index_manipulation::refused for 7 and 2019-09. The rule takes it as relative_json_pointer_rule_t{index_manipulation::refused}. A sign that no integer follows (0+, 0-#), or one whose integer has a leading zero (0+01), is no manipulation, under either choice.

Addresses

is_ipv4 and is_ipv6 are Boost.URL’s own rules, boost::urls::ipv4_address_rule and boost::urls::ipv6_address_rule, which are also the rules a grammar of a program’s own composes. An IPv4 address is RFC 2673’s dotted quad, each part 0 to 255 without a leading zero (RFC 3986’s dec-octet), so 192.168.0.01 is invalid. An IPv6 address is one of RFC 4291 2.2’s three text forms, without a zone id or a prefix length.

Host names

is_hostname checks RFC 1123 2.1’s host names: labels of 1 to 63 letters, digits and hyphens, no hyphen first or last, joined by single dots, the name at most 253 octets, no empty label and so no trailing dot. A label that starts with xn--, in any case, is an A-label, an internationalized label in its ASCII form: lexical lowercases it, as UTS 46 maps an ASCII label, and asks webcpp::idna whether IDNA2008 accepts it, decoded, canonical and with the Bidi rule of the label alone, the verdict is_idn_hostname gives that label. Another label with -- in its third and fourth places, an R-LDH label such as ab--cd, is a valid host name, as RFC 1123 says, and not an internationalized one (RFC 5890 2.3.1).

lexical judges each A-label alone, a decision of its own, so RFC 5893’s Bidi rule across the labels of a name, section 2, is checked only by is_idn_hostname: 0a.xn--4db is a host name, while its U-label form, 0a. and a Hebrew letter, is no internationalized host name. The two formats differ here by that decision, as they do on R-LDH labels.

Internationalized host names

is_idn_hostname checks a host name that may hold any script, by UTS 46’s processing and IDNA2008’s validity, through idna’s to_ascii with its default options (idna’s strict profile). The name is mapped as UTS 46 says, so fullwidth digits, an ignored U+200B, a name not in NFC and the ideographic full stop U+3002 are valid where IDNA2008 accepts the result; then every label must be valid in IDNA2008, CONTEXTO and the Bidi rule across the labels included, and the name fit DNS’s lengths in its ASCII form: labels of at most 63 octets, the name at most 253, and no trailing dot. An R-LDH label such as ab--cd is a host name and not an internationalized one, and the Bidi rule spans an internationalized name’s labels where is_hostname judges each A-label alone. E-mail addresses

is_email checks RFC 5321 4.1.2’s Mailbox, the address of an SMTP envelope: a local part of atoms joined by dots or a quoted string, at most 64 octets, then @ and a host name, or an address literal, [192.0.2.1] or [IPv6:2001:db8::1], the tag in any case. RFC 5321’s other literals need a tag registered with IANA, and IPv6 is the only one, so [RFC-5322-domain-literal] is invalid. RFC 5322’s comments and display names are not part of a Mailbox. The whole Mailbox is at most 254 octets: RFC 5321 4.5.3.1.3 limits a path to 256 octets, its angle brackets included.

A literal’s addresses are judged by Boost.URL’s rules, RFC 3986’s IPv4 address and RFC 4291’s IPv6 address, rather than by RFC 5321 4.1.3’s own Snum and IPv6-comp: an IPv4 part with a leading zero, [001.2.3.4], which Snum allows, is invalid, and an IPv6 address whose :: stands for a single group, [IPv6:1:2:3:4:5:6::8], which IPv6-comp refuses, is valid.

Its address literal is a composition of Boost.URL’s combinators, tuple_rule, variant_rule, delim_rule and squelch, over Boost.URL’s ipv4_address_rule and ipv6_address_rule. The domain is not a variant_rule alternative: the rule looks for [ and then asks the literal’s rule or hostname_rule, so that the reason a host name was refused, idna’s for an A-label, reaches the caller; Boost.URL’s variant_rule answers mismatch when every alternative fails. A grammar of a program’s own composes lexical’s rules the same way (Composing rules).

is_idn_email checks RFC 6531’s internationalized Mailbox: the local part may hold any well-formed non-ASCII UTF-8, C1 controls and noncharacters included, and is not normalized; the domain is an internationalized host name or an address literal. A quoted pair stays ASCII. Its lengths are those of the Mailbox as written, in UTF-8: the local part at most 64 octets and the whole at most 254, the form an SMTPUTF8 envelope carries (RFC 6531 extends RFC 5321’s Mailbox without changing its limits, which RFC 5321 counts in octets), whatever the domain’s ASCII form measures; the domain also fits DNS’s lengths in its ASCII form, as is_idn_hostname asks.

URIs and IRIs

is_uri is Boost.URL’s parse_uri, RFC 3986’s URI, a scheme required and a fragment allowed, and is_uri_reference is Boost.URL’s parse_uri_reference, a URI or a relative reference, each with a guard of lexical’s, and so are their rules, uri_rule and uri_reference_rule. RFC 3986 4.2 gives a relative reference that has an authority a path-abempty, empty or led by /. Boost.URL 1.92 accepts //example.com:abc/p, read as host example.com, an empty port and the path abc/p, and //a@b@example.com/, read as user a, host b and the path @example.com/. With a scheme it refuses both, and stops the URI at the authority, so that inside a larger grammar Boost.URL’s rule matches http://a@b of http://a@b@example.com/. lexical refuses a relative reference whose path after an authority is neither empty nor led by /, and uri_reference_rule refuses both forms alike with error::invalid. The guard stays until a Boost release refuses those references itself.

RFC 3986 holds [ and ] only around an IP literal (3.2.2): a path, a query and a fragment hold them percent-encoded, as %5B and %5D. Boost.URL 1.92 refuses them in a path and a fragment, and accepts them in a query: http://a/?[x] is a URI for Boost.URL. lexical refuses a bracket in a query, in is_uri, is_uri_reference, is_iri, is_iri_reference and their rules alike, which give error::invalid for it inside a larger grammar; an IP literal, http://[::1]/, and %5B in a query stay valid. This guard stays until a Boost release refuses those brackets itself.

RFC 3986 3.5 gives a fragment pchar, / and ? alone: the first # starts the fragment, and a second is held only percent-encoded, as %23. Boost.URL 1.92 adds # to its fragment characters on purpose, so http://a/#x#y is a URI for Boost.URL, whose fragment is x#y. lexical refuses a # in a fragment, in the same four functions and their rules, which give error::invalid for it inside a larger grammar; #x%23y stays valid. This guard stays until a Boost release refuses it itself.

is_iri and is_iri_reference check RFC 3987’s IRI and IRI reference, which allow non-ASCII code points, by mapping the IRI to a URI as RFC 3987 3.1 says and handing it to Boost.URL. Each non-ASCII code point must be well-formed UTF-8 and in ucschar, or in iprivate within the query; the bidirectional formatting characters U+200E, U+200F and U+202A to U+202E are refused anywhere, as RFC 3987 4.1 requires, and so is any non-ASCII code point inside an IP literal: RFC 3987 takes its IP literal from RFC 3986, ASCII alone. Each octet of a non-ASCII code point then becomes %XX, which RFC 3986 allows everywhere else that RFC 3987 allows ucschar, so a non-ASCII code point in a scheme or a port is refused by Boost.URL. No IDNA is involved: an IRI’s host is a registered name of any ucschar.

The mapped URI needs contiguous storage. An ASCII IRI is parsed as it is, never copied; a non-ASCII one is mapped into a buffer of 1,024 octets on the stack, which holds any IRI of up to 341 octets; a longer one takes one buffer of its mapped length from the memory resource given to is_iri(s, resource), or from std::pmr::get_default_resource(). A resource of a program’s own, here a buffer that refuses to grow:

std::array<std::byte, 4096> storage{};
std::pmr::monotonic_buffer_resource resource(storage.data(), storage.size(),
                                             std::pmr::null_memory_resource());
std::string long_iri = "http://example.com/";
for (int i = 0; i < 300; ++i) {
    long_iri += "\303\251";  // 300 e with an acute accent: 1,819 octets mapped, past 1,024
}
std::cout << std::boolalpha;
std::cout << "short: "
          << lexical::is_iri("http://\306\222\303\270\303\270.example/\317\200", resource)
          << '\n';
std::cout << "long: " << lexical::is_iri(long_iri, resource) << '\n';
std::cout << "bidi: " << lexical::is_iri("http://a/\342\200\216", resource) << '\n';

It prints:

short: true
long: true
bidi: false

RFC 3986 3.2.2’s IP literal holds an IPv6 address or an IPvFuture, and no zone identifier. RFC 6874 added one, http://[fe80::1%25eth0]/, which Boost.URL 1.92 takes; RFC 9844 obsoleted RFC 6874 in 2025 and reverted its change to RFC 3986. lexical refuses a zone identifier, in the same four functions and their rules, which give error::invalid for it inside a larger grammar; %25 outside an IP literal stays valid. This guard stays until a Boost release refuses zone identifiers itself. Each guard, and the one verdict of Boost.URL that lexical keeps though RFC 3986 differs, is listed in Known deviations.

Boost.URL is a compiled library: a program that uses these formats links /webcpp//boost_url, which /webcpp/lexical//lexical brings. Measured on 2026-10-09 with Boost 1.92 and wasi-sdk 34, built with b2’s release flags (-O3, wasm exceptions) and stripped at link time, a wasm32-wasip2 program that calls is_uri is 85,625 bytes larger than an empty one.

Known deviations

lexical is faithful to RFC 3986, the reference JSON Schema names for these formats, where Boost.URL 1.92 is more liberal. lexical refuses four things Boost.URL accepts: a relative reference whose path after an authority is neither empty nor led by /; [ or ] in a query; # in a fragment; and a zone identifier in an IP literal. Its rules also refuse a reference that Boost.URL’s would stop at an authority before a path segment, as at the second @ of http://a@b@example.com/. The tests pin each of these verdicts.

lexical keeps one verdict of Boost.URL that RFC 3986 does not give, since it never loosens Boost.URL: an IPvFuture led by an uppercase V, http://[V1.x]/, is refused, though RFC 5234 makes ABNF’s quoted strings case-insensitive and RFC 3986’s "v" matches it; http://[v1.x]/ is valid.

These are all the differences found on 2026-10-09, when the verdicts of Boost.URL 1.92 and of lexical were compared with a transcription of RFC 3986’s ABNF, on inputs that put every ASCII character but NUL and line feed into each part of a reference, and on references generated at random.

URI templates

is_uri_template checks RFC 6570’s URI Template of any level, without expanding it: literals, and expressions in braces with an optional operator and comma-separated variables, each with a prefix length of 1 to 9999 or an explode *. Erratum 6937, verified in 2022, makes the apostrophe a literal, as JSON Schema’s suite expects. The operators RFC 6570 reserves for future use, the equals sign, the comma, the exclamation mark, the at sign and the vertical bar, are accepted, as its ABNF accepts them. A literal may be a ucschar or iprivate code point, so a template of an IRI is valid too.

Regular expressions

is_regex answers whether a string is a regular expression, JSON Schema’s regex: ECMA-262’s Pattern in u mode, with ECMAScript 2025’s modifiers, (?i:...), and its duplicate group names, (?<y>...)|(?<y>...). It is declared in <webcpp/lexical/regex.hpp>, the one header of lexical that brings the Unicode tables of ECMA-262’s classes: <webcpp/lexical.hpp> leaves it out, and a program that never validates a pattern does not compile them.

for (const std::string_view pattern : {
         R"(^\p{Letter}+$)",
         R"((?<year>\d{4})-(?<month>\d{2}))",
         R"((?<=\$\d*)[0-9])",
         "^(abc]",
         R"(\Aabc\z)",
         "(?i)abc",
         "(?i:abc)",
     }) {
    std::cout << pattern << " -> " << (webcpp::lexical::is_regex(pattern) ? "valid" : "invalid")
              << '\n';
}

How a pattern is judged

A pattern is valid when ECMA-262 accepts it as a Pattern in u mode, early errors included: when new RegExp(pattern, "u") does not throw a SyntaxError. lexical’s validator reads the pattern as that grammar reads it, and refuses what the grammar refuses there: Annex B’s escapes and classes, \a, \- outside a class, \8, an octal escape; Perl’s \A, \Z and \z; a group of another dialect, (?P<n>...), (?#...), a leading (?i); a property ECMA-262 does not name, as \p{letter} or \p{Script=Foo}; a backreference to a group the pattern does not hold; two groups of one name that a match could both hold. A pattern that is not well-formed UTF-8 is refused, and a NUL is a literal like any other code point.

Valid means that the syntax and the early errors accept the pattern, and nothing more. is_regex compiles no pattern and runs none: it says nothing of how long a matcher takes on a valid pattern, nor of the limits an engine sets on the program it builds from one. The property names \p{...} accepts are Unicode 17.0.0’s, read from the generated tables (The Unicode tables): no ICU and no std::locale.

ECMA-262 allows a lookbehind of any width, (?<=\$\d*), and so does is_regex: it never measures a lookbehind, since it compiles nothing.

is_regex has no rule: a pattern has no grammar of its own inside a longer input, so is_regex judges a whole string.

Bounds

Two bounds keep a hostile pattern, which JSON Schema meets in an instance, from taking the stack or the time of a program. Past one of them, is_regex answers false without judging the pattern, though ECMA-262 may allow it:

What it allocates

is_regex allocates nothing, on any target. It takes no memory resource: its reader works on the pattern’s own bytes and keeps its state on the stack, to the depth max_regex_nesting allows. So <webcpp/lexical/regex.hpp> keeps lexical’s rule that a validator allocates nothing, as the allocation table says (Allocation).

Compared with V8

A test of lexical, regex_v8, compares is_regex with V8 on 24,297 patterns, of which 16,475 are valid by V8’s verdict. The patterns are drawn at random, from seeds 2 to 9 of Python’s random.Random, from a grammar of atoms, groups of every kind, backreferences, assertions, quantifiers and defects; every name \p{...} accepts, under each of its forms, and the same names misspelt; every pattern the JSON-Schema-Test-Suite’s schemas hold, in pattern and patternProperties, and every string of its tests of the format regex; and the cases the grammar does not draw: ECMAScript 2025’s modifiers and duplicate group names, lookbehinds of every width, escapes of every kind, and classes and quantifiers at their edges. V8’s verdict is new RegExp(pattern, "u") throwing a SyntaxError or not, written by the oracle of test/oracle, which runs the pinned Node, 26.7.0, whose V8 is 14.6 and whose Unicode is 17.0. On each of these patterns the verdict of is_regex is V8’s, on every target (Testing).

The Unicode tables

tools/generate_tables.py, in lexical’s repository, writes <webcpp/lexical/detail/regex_tables.hpp> from Unicode’s data files of version 17.0.0, pinned in tools/unicode.json, each by its URL under https://www.unicode.org/Public/17.0.0/ and its SHA-256: a file its cache lacks is downloaded, every file is hashed, and a digest that differs stops it before it writes anything. Before it writes, it checks what the validator and the traits assume of the data: General_Category has 30 values that are no group; every value a file holds is one PropertyValueAliases.txt names; each of ECMA-262’s binary properties holds a code point; every name is ASCII and names one value; the classes fit the traits’ mask; and no simple case folding orbit holds more than four code points. A script that no code point has, Katakana_Or_Hiragana, gets no name, as ECMA-262’s table of the values of Script leaves it out. tools/generate_patterns.py writes the patterns regex_v8 reads, the same way.

The own lane generated runs both generators again, into the build directory, and compares each output with the committed file, byte for byte; update-generated writes them in place, the one writer of the generated files. The ordinary lanes never run them, since a generator may need the network. The data are Unicode’s, under the Unicode License v3, whose notice is in the appendix "Unicode data".

Composing rules

Every format but regex is also a Boost.URL rule, in webcpp::lexical::grammar: an object whose type <name>_rule_t is public, so a rule that takes a parameter, time_rule_t{leap_seconds::refused} or iri_rule_t{&resource}, is spelled without a factory. A rule yields the text it matched, as a grammar::text; uri_rule and uri_reference_rule yield Boost.URL’s url_view. ipv4 and ipv6 are Boost.URL’s own rules, boost::urls::ipv4_address_rule and ipv6_address_rule.

A rule composes with Boost.URL’s combinators, tuple_rule, variant_rule, optional_rule, range_rule, into a grammar of a program’s own: an internationalized host and an optional port, bücher.example:8080, are a tuple_rule of idn_hostname_rule and an optional_rule of another tuple_rule, a colon, squelch(delim_rule(':')), then unsigned_rule<std::uint16_t>, which yields the host’s text and the port’s number; a rule that refuses says whose rule it was, through its error’s category:

constexpr auto idn_host_port = urlg::tuple_rule(
    fg::idn_hostname_rule,
    urlg::optional_rule(urlg::tuple_rule(urlg::squelch(urlg::delim_rule(':')),
                                         urlg::unsigned_rule<std::uint16_t>{})));

for (const std::string_view text : {
         "b\303\274cher.example:8080",
         "example.com",
         "a\302\267b.example:80",
         "example.com:99999",
     }) {
    const auto parsed = urlg::parse(text, idn_host_port);
    if (parsed.has_error()) {
        const boost::system::error_code error = parsed.error();
        std::cout << text << " -> refused by " << error.category().name() << '\n';
        continue;
    }
    const auto& [host, port] = *parsed;
    std::cout << text << " -> host " << host;
    if (port) {
        std::cout << ", port " << *port;
    }
    std::cout << '\n';

Each validates the text it took and fails as a whole rather than match a shorter prefix, and a rule that fails leaves its input where it was. idna_label_rule is a terminal of lexical’s own that asks webcpp::idna for its verdict, so a grammar joins labels with separators of its own. It judges each label alone: a grammar that joins labels into a name checks what spans the name itself, RFC 5893’s Bidi rule across its labels (section 2) and its 253 octets in the ASCII form, or hands the whole name to idn_hostname_rule, which checks both. Joined by a grammar’s own dots, 0a. and a label of a Hebrew letter are two valid labels and no valid name.

An internationalized rule’s error is idna’s, the idna::error that refused the name (Errors), but only where nothing discards it: Boost.URL’s variant_rule answers mismatch when every alternative fails, whatever each one said. lexical’s e-mail rules look for [ themselves rather than make the domain an alternative, so that idna’s reason reaches the caller; a grammar that needs that reason does the same.

Two facts of Boost.URL shape a composition. A range_rule over a rule larger than 128 bytes keeps it in a pool of Boost.URL’s own, which allocates: pass such a rule through boost::urls::grammar::ref, as lexical does. And parse of a whole string fails with error::leftover when the rule stops early, which is how a validator refuses trailing input.

Errors

A validator answers bool: whether the string is in the format. A rule answers a grammar::result, the text it matched or why it refused, and lexical has no error category of its own:

  • boost::urls::grammar::error::mismatch: no text of the format starts where the rule was asked to match, so a variant_rule tries its next alternative;

  • boost::urls::grammar::error::invalid: the format’s text started there and broke one of its constraints, a month 13 or a leap second at the wrong minute;

  • boost::urls::grammar::error::leftover, from parse on a whole string: the format’s text ended before the string did;

  • an error of webcpp::idna, from the rules of internationalized names: the reason UTS 46 or IDNA2008 refused the name.

lexical raises no exception of its own, and builds without exceptions. WEBCPP_LEXICAL_NO_EXCEPTIONS, defined without exceptions or by the developer, changes nothing in it: it exists so that a program can set it for every webcpp library alike. Only an allocation can throw, std::bad_alloc from the default resource or the global operator new: an IRI function’s resource (Allocation). is_regex allocates nothing and is noexcept: a pattern it refuses is answered false, never an exception (How a pattern is judged).

Guarantees

  1. For every format but regex, is_x(s) and parse(s, x_rule) give the same answer for every string.

  2. No function or rule allocates but those the allocation table names: the IRI functions, only through a memory resource.

  3. Nothing throws but an allocation that fails.

  4. Every function refuses a string that is not well-formed UTF-8.

  5. A rule that fails leaves its iterator where it was.

  6. is_regex answers every byte string, a value, and never throws: a pattern past one of its bounds is answered false before it can take more stack or time than the bounds allow.

  7. The Unicode tables and the patterns compared with V8 are what their generators write from the pinned files, byte for byte.

webcpp::lexical::max_regex_nesting

The deepest a pattern’s groups may nest for is_regex to judge it: 32 levels of groups, lookarounds and modifiers, one inside the other.

Synopsis

Declared in <webcpp/lexical/regex.hpp>
