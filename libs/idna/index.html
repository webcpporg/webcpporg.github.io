idna is a header-only library of internationalized domain names in C++20, one of the libraries of webcpp: Punycode (RFC 3492), Unicode’s UTS 46 processing, to ASCII and to Unicode, and the validity rules of IDNA2008 (RFC 5890 to 5893), over Unicode 17.0.0 tables generated into its headers. Every operation returns its error as a value, and every operation that writes into a caller’s buffer allocates nothing.

This page teaches idna concept by concept: why each exists, its smallest example, its variations and its rules. Every program it shows was compiled and run, natively and for wasm32-wasip2, wasm32-wasip3 and Emscripten, and printed the output shown under it. The reference that closes it lists every name the headers declare.

Introduction

The labels of a domain name were ASCII: letters, digits and the hyphen. An internationalized domain name lets a label hold any script, bücher.example or παράδειγμα.δοκιμή, and still reach the DNS, which stays ASCII: a label that is not ASCII travels as an A-label, xn-- followed by the label’s code points in Punycode, so bücher.example is looked up as xn--bcher-kva.example.

Two standards say which labels are valid, and how a name a person typed becomes one:

  • IDNA2008, RFC 5890 to 5893, defines a valid label: the property of each code point, derived from Unicode (PVALID; CONTEXTJ and CONTEXTO, valid in a context the RFC states; DISALLOWED), Normalization Form C, the hyphens, and the Bidi rule of a name that mixes right-to-left and left-to-right labels. It maps nothing: bücher is a valid label, and Bücher is not.

  • UTS 46, Unicode’s IDNA Compatibility Processing, first maps what was typed (case, compatibility forms, the full stops of other scripts), then normalizes it, then checks it, by rules close to IDNA2008’s but not the same: it accepts symbols such as ¡, which IDNA2008 disallows, and has no CONTEXTO rules at all.

idna implements both, and its default profile is the stricter union of the two: UTS 46’s mapping, then IDNA2008’s validity on top of UTS 46’s. It is what JSON Schema’s idn-hostname format asks for, and what no UTS 46 library measured against that format’s tests gives alone: each accepts the labels IDNA2008 refuses. idna::options{.idna2008 = false} is UTS 46 alone.

A first example

This program converts two names to their ASCII form, and an A-label back to its Unicode form, with the default options:

#include <webcpp/idna.hpp>

#include <array>
#include <iostream>
#include <string_view>

namespace idna = webcpp::idna;

int main() {
    std::array<char, idna::max_domain_length> ascii{};
    for (const std::string_view name : {"B\303\274cher.Example", "a\302\267b.example"}) {
        const idna::result<std::size_t> converted = idna::to_ascii(ascii, name);
        if (converted.has_error()) {
            std::cout << name << " -> error: " << converted.error().message() << '\n';
            continue;
        }
        std::cout << name << " -> " << std::string_view(ascii.data(), converted.value()) << '\n';
    }

    std::array<char, 1024> unicode{};
    const idna::unicode_result shown = idna::to_unicode(unicode, "xn--bcher-kva.example");
    std::cout << std::string_view(unicode.data(), shown.size)
              << (shown.error ? " (with an error)" : "") << '\n';
}

It prints:

Bücher.Example -> xn--bcher-kva.example
a·b.example -> error: code point outside its allowed context
bücher.example

Bücher.Example is mapped first, its capitals lowered, so it is valid, and its first label, which is not ASCII, becomes an A-label. a·b.example is refused: U+00B7 MIDDLE DOT is valid in IDNA2008 only between two l, a CONTEXTO rule that UTS 46 alone does not have. to_unicode decodes the A-label back, and reports no error.

Punycode

Punycode, RFC 3492, writes a string of code points with the ASCII letters, digits and hyphen alone, and reads it back: the code points below U+0080, the basic ones, are copied first, then a hyphen, then numbers in base 36 that say where each other code point goes. An A-label is xn-- followed by the Punycode of its U-label. idna::punycode::encode and decode are that encoding, without the prefix, which the conversions add and remove. Here is RFC 3492 section 7.1’s sample (L), 3年B組金八先生:

// RFC 3492 section 7.1's sample (L).
const std::u32string_view sample = U"3\u5E74B\u7D44\u91D1\u516B\u5148\u751F";
std::array<char, 64> encoded{};
const idna::result<std::size_t> written = idna::punycode::encode(encoded, sample);
std::cout << std::string_view(encoded.data(), written.value()) << '\n';

decode gives the code points back, into a span of char32_t:

std::array<char32_t, 64> decoded{};
const idna::result<std::size_t> read =
    idna::punycode::decode(decoded, "3B-ww4c5e180e575a65lsy2b");
std::cout << read.value() << " code points, the same: "
          << (std::u32string_view(decoded.data(), read.value()) == sample ? "yes" : "no")
          << '\n';

Both return the number of chars or code points written, or an error: a character that is no digit, a number cut short, a value that is not a Unicode scalar value, or arithmetic past 32 bits, which RFC 3492 section 6.4 refuses:

for (const std::string_view bad : {"-9uc", "bcher-k", "999999999999999999999"}) {
    std::cout << bad << " -> " << idna::punycode::decode(decoded, bad).error().message()
              << '\n';
}

The program prints:

3B-ww4c5e180e575a65lsy2b
8 code points, the same: yes
-9uc -> invalid Punycode
bcher-k -> invalid Punycode
999999999999999999999 -> Punycode overflow

The digits are read in either case; the basic code points are copied as they are, case included, as RFC 3492’s mixed-case annotation leaves them, and encode writes its digits in lowercase. A hyphen at the very start is no delimiter, since nothing precedes it, so -9uc is refused, as RFC 3492 says: it is the A-label xn---9uc, which a careless decoder would read as xn--9uc. Each function has a second form that returns a std::pmr string from a memory resource (Allocation). Neither form bounds the length of its input: a pmr form’s time grows with the square of it, and a span form’s at most with the input’s length times the span’s size, so a program bounds input it does not trust before it hands it to a pmr form (Punycode’s bound).

Converting names

idna::to_ascii and idna::to_unicode are UTS 46’s ToASCII and ToUnicode, sections 4.2 and 4.3: the name is mapped, normalized to NFC, split into labels at each full stop, and each label is converted and checked. The first example (A first example) calls both. Each has two forms: one that writes into the caller’s span and allocates nothing, and one that returns a string from a memory resource (Allocation).

The processing

Each code point is looked up in UTS 46’s mapping table: a code point that is valid stays, one that is mapped is replaced by its mapping (A by a, ﬁ by fi, U+3002 IDEOGRAPHIC FULL STOP by .), one that is ignored is removed (U+00AD SOFT HYPHEN), a deviation stays unless the processing is transitional (ß, ς, and the two joiners), and one that is disallowed stays, to be refused when its label is checked. The result is normalized to NFC and split at U+002E. A label that starts with xn-- is decoded from Punycode and checked as the U-label it holds; any other is checked as it is. The checks, in their order, are those of The rules.

idna does this one label at a time, in a working storage of one label’s code points, so a name of any length needs the same small storage (Limits).

To ASCII

to_ascii(output, domain, opts) writes the ASCII form of domain into the caller’s span and returns the number of chars written: each label that is not ASCII as xn-- and its Punycode, the others as they are, joined by .. A name that fails any check has no ASCII form: the result is the first error found, in the order of the labels, then bidi for the Bidi rule across the labels, then domain_too_long, and output_too_small last, so a span too small for a name that is too long anyway reports the name. With the DNS lengths verified, the default, the ASCII form is at most idna::max_domain_length, 253 chars, so a std::array<char, idna::max_domain_length> always holds it.

to_ascii(domain, opts, resource) returns the same ASCII form as a std::pmr::string. With the DNS lengths verified, it reports the same first error as a span form large enough to hold the result, for every name, and it is never output_too_small: a label that outgrows the span form’s working storage is too long for the DNS anyway, and both forms refuse it there (The working storage).

To Unicode

to_unicode(output, domain, opts) writes the Unicode form, in UTF-8, and returns an idna::unicode_result: how many chars it wrote, and the first error. As UTS 46 asks, the conversion goes on after an error, so that a name can be shown even when it is not valid: each label is written as the processing leaves it, mapped and normalized, an A-label decoded when its Punycode decodes and kept as it is otherwise. A label that fails its checks is written so too, as the toUnicode column of IdnaTestV2 records it, and no U+FFFD is put in place of what failed: A_B.Example is written a_b.example, with not_ldh. With the DNS lengths verified, a final empty label, the DNS root of example., is no error in the Unicode form, as UTS 46’s X4_2 allows; any other empty label is empty_label. When the span is full, the writing stops at a code point boundary and the error is output_too_small, which takes the place of any other: the caller needs a larger span before anything else. Input that is not well-formed UTF-8 writes nothing, and is invalid_utf8.

to_unicode(domain, opts, resource) returns an idna::unicode_string, the Unicode form as a std::pmr::string and the first error. It is never output_too_small, and the two forms differ only past the working storage, which the Unicode form, checking no label’s maximum length, meets with the default options: the span form stops at a label beyond it, and the pmr form converts the label (The working storage).

Options

Every conversion and every check takes an idna::options, the flags of UTS 46 section 4 and one of idna’s own, idna2008. The defaults are the strict profile: every check on, nontransitional processing, the DNS lengths verified, and IDNA2008’s validity on top. idna::options is an aggregate, so a program names only what changes: idna::options{.idna2008 = false} is UTS 46 alone, and idna::options{.verify_dns_length = false} lets labels of any length through.

Validity

idna::check_label and idna::check_domain say whether a label, or a domain name, is valid as it is given, by IDNA2008’s rules and UTS 46’s validity criteria, without UTS 46’s mapping: nothing is lowercased, normalized or replaced, so a label with a capital letter, or one not in NFC, is refused. The one exception is an A-label, whose case does not matter (below). They are the checks a program needs when a name must already be in its final form, as a hostname’s A-labels must. is_valid_label and is_valid_domain say the same as a bool.

// "\302\267" is U+00B7 MIDDLE DOT in UTF-8, which RFC 5892 allows only between two 'l'.
for (const std::string_view label :
     {"example", "xn--bcher-kva", "l\302\267l", "a\302\267l", "ab--cd", "Example"}) {
    const idna::result<void> checked = idna::check_label(label);
    std::cout << label << ": " << (checked.has_value() ? "valid" : checked.error().message())
              << '\n';
}

An A-label’s xn-- and Punycode are read in either case, as RFC 5890 compares them. The label must be ASCII, and its Punycode must decode to a label that holds a code point beyond ASCII (UTS 46’s P4). Its U-label is then checked by the rules below, Normalization Form C included, and encoded again: an A-label that is not the encoding of its U-label, its letters compared in lowercase, is refused, as RFC 5891 section 5.4 asks. Each failure of the A-label itself, a code point beyond ASCII, Punycode that does not decode, P4 or the round trip, is invalid_punycode, or punycode_overflow for a number past 32 bits. Under ignore_invalid_punycode, a label whose Punycode does not decode is kept as it is, and only its length is checked.

check_label refuses a U+002E inside its label as disallowed, and applies the Bidi rule to its label as to a name of one label. check_domain splits at U+002E alone: the other full stops, U+3002, U+FF0E and U+FF61, separate labels only after UTS 46’s mapping, so as given they are code points UTS 46 maps, and disallowed. It applies the Bidi rule across the labels, and adds the length of the whole name:

// "\327\220" is U+05D0 HEBREW LETTER ALEF in UTF-8, a right-to-left letter.
for (const std::string_view domain : {"a.\327\220", "0a.\327\220", "0a.b"}) {
    std::cout << domain << ": " << (idna::is_valid_domain(domain) ? "valid" : "invalid")
              << '\n';
}

The same check under UTS 46 alone accepts what IDNA2008’s context rules refuse:

const idna::options uts46_alone{.idna2008 = false};
std::cout << "a\302\267l under UTS 46 alone: "
          << (idna::is_valid_label("a\302\267l", uts46_alone) ? "valid" : "invalid") << '\n';

The program prints:

The rules

A label is checked in this order, and the first rule it breaks is its error; to_ascii and to_unicode apply the same rules to each label after the mapping, with the NFC check only for a decoded A-label:

  1. Normalization Form C (UTS 46 V1, RFC 5891 section 5.4): not_nfc.

  2. Hyphens, under check_hyphens: none in both the third and the fourth position (V2), hyphen_in_third_and_fourth, which keeps such labels free for a future prefix, xn-- among them; none at either end (V3), hyphen_at_start_or_end. Without check_hyphens, a label that starts with xn-- (V4), ace_prefix.

  3. No leading combining mark (V6, RFC 5891 section 5.4): leading_combining_mark.

  4. UTS 46’s status (V7): every code point valid, or a deviation in nontransitional processing; disallowed.

  5. STD3 ASCII, under use_std3_ascii_rules (U1): ASCII only a to z, 0 to 9 and the hyphen; not_ldh.

  6. CONTEXTJ, under check_joiners (RFC 5892 A.1, A.2): U+200C after a virama, or between a code point of Joining_Type L or D and one of R or D, with only T between; U+200D after a virama; contextj.

  7. IDNA2008, under idna2008: no code point UTS 46 marks NV8 or XV8, not_idna2008; then the CONTEXTO rules, contexto: U+00B7 MIDDLE DOT between two l (A.3), U+0375 GREEK KERAIA before a Greek code point (A.4), U+05F3 and U+05F4, GERESH and GERSHAYIM, after a Hebrew one (A.5, A.6), U+30FB KATAKANA MIDDLE DOT in a label that holds Hiragana, Katakana or Han (A.7), and Arabic-Indic digits never beside extended ones (A.8, A.9).

Across the labels of a name, under check_bidi: when one label holds an R, AL or AN code point, the name is a Bidi domain name, and then every label must satisfy RFC 5893 section 2, bidi. 0a.א fails: its first label starts with a digit, which rule 1 refuses in a Bidi domain name. Under verify_dns_length, the lengths of the ASCII form: each label’s with the label, an empty one as empty_label and, after its rules, one of more than 63 octets as label_too_long; the whole name’s last, after the Bidi rule, domain_too_long. A label that outgrows the working storage of 256 code points, which no label within the DNS lengths does, is refused as soon as it does, before its rules: label_too_long under verify_dns_length, storage_exhausted without it (Errors).

idna derives IDNA2008’s property of a code point from UTS 46’s table: PVALID, CONTEXTJ or CONTEXTO exactly when its status is valid or deviation and it bears no NV8 or XV8 mark. The generator checks this against IANA’s IDNA2008 tables each time it runs (Unicode and the tables).

Errors

Every operation of idna that can fail returns its error as a value: an idna::result<T>, Boost.System’s result, or, for to_unicode, which always converts what it can, a struct whose error is a boost::system::error_code. idna throws nothing of its own. Its errors are the values of idna::error, of the category webcpp.idna, one per family of rules rather than one per status code of UTS 46: IdnaTestV2, Unicode’s own conformance file, says an implementation "need only record that there is an error". The first error found is the one reported, but for output_too_small: to_ascii reports it last, after every label’s error, bidi and domain_too_long, and the span form of to_unicode lets it replace an earlier error (Converting names). The labels are processed in order, and the checks of a label in the order UTS 46 section 4.1 lists them, IDNA2008’s last.

Allocation

idna allocates nothing it does not have to, and lets its user choose where what it does allocate comes from. Every conversion has two forms:

  • A span form writes into the caller’s buffer, std::span<char> or std::span<char32_t>, and allocates nothing, whatever its input. The validators, check_label and check_domain, allocate nothing either.

  • A pmr form returns a std::pmr::string or std::pmr::u32string from the std::pmr::memory_resource it is given, by default std::pmr::get_default_resource(). It allocates from that resource alone: its result, and a label’s working storage beyond the inline capacity (Limits).

The span form of to_ascii needs no more than a buffer on the stack:

// A span form writes into the caller's buffer and allocates nothing.
std::array<char, idna::max_domain_length> buffer{};
const idna::result<std::size_t> written = idna::to_ascii(buffer, "b\303\274cher.example");
std::cout << std::string_view(buffer.data(), written.value()) << '\n';

Its pmr form, here with a std::pmr::monotonic_buffer_resource over a buffer of the program’s own, which allocates nothing from the heap either:

// A pmr form takes its memory from the resource it is given, here a buffer on the stack.
std::array<std::byte, 16384> storage{};
std::pmr::monotonic_buffer_resource resource(storage.data(), storage.size(),
                                             std::pmr::null_memory_resource());
const idna::result<std::pmr::string> owned =
    idna::to_ascii("b\303\274cher.example", idna::options(), resource);
std::cout << owned.value() << '\n';

The two forms of to_ascii differ for a label longer than the inline storage, which only a program that turns the DNS lengths off can give it: the span form refuses it, and the pmr form holds it in its resource. to_unicode, which checks no label’s maximum length, meets such a label with the default options too (The working storage).

// Without the DNS lengths, a label of 300 code points is beyond the inline storage: the span
// form refuses it, and the pmr form holds it in its resource.
const std::string long_label(300, 'a');
const idna::options no_lengths{.verify_dns_length = false};
std::array<char, 512> wide{};
std::cout << idna::to_ascii(wide, long_label, no_lengths).error().message() << '\n';
std::cout << idna::to_ascii(long_label, no_lengths, resource).value().size() << " octets\n";

xn--bcher-kva.example
label beyond the working storage
300 octets

The test allocation replaces the global operator new for itself alone and counts: no call in any span form or validator, over long names, long labels and every kind of failure, with the strict profile, UTS 46 alone and the DNS lengths off, and in the pmr forms, exactly the calls of their memory resource (guarantee 1).

Limits

The DNS lengths

Under verify_dns_length, the default, a label is 1 to idna::max_label_length, 63, octets in its ASCII form, and a name 1 to idna::max_domain_length, 253, without a final root label, which is refused: RFC 1034 section 3.1’s limits, as UTS 46 section 4.2 states them. A U-label is measured by its A-label: 55 a and a ü make an A-label of 63 octets, and 56 make one of 64.

The working storage

The conversions and the checks hold one label at a time, in a working storage of 256 code points inside the call, about 1.3 KiB with the label’s ASCII form, and a second one while a label is checked for NFC the slow way. Every label the DNS lengths accept fits: an A-label decodes to at most 59 code points, and a code point decomposes to at most 4, U+1FAF among them, the longest canonical decomposition of Unicode 17.0.0, which the generator checks.

A label beyond 256 code points once decomposed is too long for the DNS, and what meets it depends on the length check:

  • Under verify_dns_length, to_ascii, in both forms, and the validators refuse it as label_too_long, which it is, as they refuse a label whose NFC check’s copy outgrows the storage.

  • Without it, the span form of to_ascii and the validators return storage_exhausted, and the pmr form of to_ascii takes the label’s storage from its memory resource.

  • to_unicode checks no label’s or name’s maximum length, and meets such a label with any options: its span form stops there with storage_exhausted, and its pmr form converts the label, an A-label within Punycode’s bound (below). The difference is by design: a span form allocates nothing, and the label is no name the DNS can hold.

The storage fills while a label is gathered, before any of the label’s checks, so a label beyond it reports that first: U+FFFF followed by 300 a is label_too_long, not disallowed. In the span form of to_unicode, the processing stops there, keeping an error recorded before it, and its output ends with the last label written before the long one: a name of the labels a_b, 300 a and c gives a_b, and not_ldh.

Punycode’s bound

Punycode’s work grows with the square of a label’s length: RFC 3492’s encoder passes over the label once for each distinct code point, and its decoder inserts each code point among those before it. The conversions bound it at 256 code points, the working storage’s, and Punycode past the bound is punycode_overflow whatever ignore_invalid_punycode says, since a limit of the implementation is no invalid Punycode. to_ascii encodes, so a label of more than 256 code points that is not ASCII is punycode_overflow there. Both conversions decode, so an A-label whose Punycode decodes to more than 256 code points is punycode_overflow in either, and kept as it is in the Unicode form. to_unicode encodes nothing: a long label that is not an A-label is written as it is. Only a pmr form meets the bound, to_ascii without the DNS lengths, and to_unicode, with any options, for an A-label, since a span form refuses such a label as beyond its storage first. At the bound, the worst label costs about 4 times one as long that Punycode handles in linear time, measured at -O2.

punycode::encode and punycode::decode are the primitive, and have no such bound: their pmr forms take input of any length, in time that grows with its square, and their span forms stop when the caller’s span is full, in time that grows at most with the input’s length times the span’s size. A program bounds the length of input it does not trust before it hands it to a pmr form.

The stack

The deepest call of idna, a check of a label, or a conversion of an A-label, whose U-label holds more than 32 combining marks in a row, which the slow NFC check sorts by counting, ran in about 11 KiB of stack, and the conversions and checks of an ordinary name, such as xn--bcher-kva.example, in about 8 KiB, a program’s start and its printf included, against the 64 KiB a WebAssembly program gets by default. These are measured figures, with no margin promised: a program built with wasi-sdk 34 in a debug build (-O0 -g) for wasm32-wasip2 and wasm32-wasip3, run by wasmtime 47 with a stack made smaller, 256 bytes at a time, until it trapped. Another compiler or version may need more. idna does not recurse.

The generator

tools/generate_tables.py, in idna’s repository, writes the tables, and the vectors of the conformance tests, IdnaTestV2.txt and NormalizationTest.txt as C++ data under test/generated/ (Testing). Its inputs are pinned in tools/unicode.json, each by its URL under https://www.unicode.org/Public/17.0.0/ and its SHA-256, with IANA’s IDNA2008 tables, idna-tables-12.0.0, read only by its checks. A file its cache lacks is downloaded, every file is hashed, and a digest that differs stops it, naming the file and both digests, before it writes anything.

Before it writes, it checks what idna assumes of the data, and stops naming the assumption that fails: every status of the mapping table is one of the five it knows; IANA’s IDNA2008 property of every code point IANA assigns one agrees with the derivation from UTS 46’s table, U+002E FULL STOP aside, which IANA disallows and UTS 46 keeps as the separator no label holds; the CONTEXTJ and CONTEXTO code points are those of RFC 5892 appendix A; no full canonical decomposition is longer than 4 code points; no Hangul syllable has a decomposition in UnicodeData.txt, since idna computes those; and every property value a file holds is one it knows, either one the tables keep or one it reads as other. It reads the test files as strictly: every line of IdnaTestV2.txt has its seven fields, its status codes take the forms the file’s header names, and its one escape is \uXXXX; every line of NormalizationTest.txt has its five columns of code points; and each entry of test/known_failures.json names a line of IdnaTestV2.txt by its number and its source, once, with a reason, for the pinned version of Unicode. Two runs write the same bytes. Its cache is bin/unicode/17.0.0/ of the superproject, which it fills from unicode.org and iana.org when a file is missing. The data are Unicode’s, under the Unicode License v3, whose notice is in the appendix "Unicode data".

The own lane tables runs the generator again, into the build directory, and compares each of its outputs with the committed file, byte for byte, naming each that differs; update-generated writes them in place, and is the one writer of the generated files. The ordinary lanes never run the generator, which may need the network; the CI runs the lane on its own.

b2 -a libs/idna/test//tables
b2 libs/idna/test//update-generated

What the tables cost

Only <webcpp/idna/detail/properties.hpp> includes the tables, and of the public headers only uts46.hpp and validity.hpp reach it, with <webcpp/idna.hpp>, which includes them: punycode.hpp, errors.hpp and options.hpp cost nothing of them. The tables hold 147,324 bytes of data, and a program links only those it reads. A translation unit that includes <webcpp/idna.hpp> and calls to_ascii, compiled at -O2, takes about 0.7 s of processor time and makes an object of 188 KB natively with Apple Clang 21, and about 0.8 s and 197 KB for wasm32-wasip2 with wasi-sdk 34, against 0.14 s and 0.07 s, and under 1 KB, for the same program without idna. Each time is the least of fifteen compilations, user and system time, on an Apple M5 Max shared with other work.

Moving to another version of Unicode

A move is one change of its own, which updates every place that holds the version, in this order:

  1. tools/unicode.json: its version, and the url and the sha256 of each of Unicode’s files. IANA’s idna-tables-12.0.0 stays as it is. test/known_failures.json: its unicode, and no entry, since each names a line of the old IdnaTestV2.txt.

  2. tools/generate_tables.py, run from the superproject’s root by b2 libs/idna/test//update-generated, which downloads the new files. A property value the new version adds, most often a script, stops it by name. The value then joins the generator’s list of the values it reads as other, SCRIPT_OTHERS, BIDI_OTHERS, JOINING_OTHERS or OTHER_CATEGORIES, once it is known not to matter to IDNA, or the values the tables keep, SCRIPTS, BIDI_CLASSES or JOINING_TYPES, with the code that reads them, when it does; the comment above those lists names the version they were read from. Any other check that fails is an assumption of idna’s that no longer holds, and is settled before the move goes on. Once every check passes, update-generated writes include/webcpp/idna/detail/tables.hpp and the vectors again.

  3. include/webcpp/idna/options.hpp: unicode_version, which detail/properties.hpp refuses to compile while it differs from the tables’; the version that test/options_test.cpp and test/properties_test.cpp pin; and the counts and line numbers of the test files that test/vectors_test.cpp pins.

  4. doc/idna.adoc: the attributes :unicode-version: and :uts46-revision:, which every mention of the version and of UTS 46’s revision on this page reads.

  5. The text that names the version: the description of meta/libraries.json, the first paragraph of README.md, and the section "Unicode and the tables" of AGENTS.md.

  6. Every lane, the own lane tables among them, and the known failures of test/known_failures.json brought up to date, each with its reason, and update-generated run again, which writes each reason into its row.

  7. The changelog, in a line that names the new version.

Guarantees

Each guarantee keeps its number and its anchor; code, tests and comments cite them.

  1. No span form of a conversion and no validator allocates, whatever its input; a pmr form allocates from its memory resource alone.

  2. No conversion, validator or Punycode function throws but the allocation of the memory resource a pmr form was given. The category’s message(int) returns a std::string, as Boost.System’s error_category declares it, so it may throw what the global operator new throws. The member message(char*, std::size_t) of error_code, which calls the category’s message(int, char*, std::size_t), copies the message into a caller’s buffer and throws nothing.

  3. The same input and options give the same output and the same error on every target.

  4. With verify_dns_length, to_ascii returns at most idna::max_domain_length chars, and reports a name whose ASCII form is longer as domain_too_long, unless an earlier error comes first in the order of the errors (To ASCII), and never as output_too_small in a buffer of that size. After an error, the buffer of the span form of to_ascii, as of a Punycode span form, holds nothing to read; the span form of to_unicode goes on after an error, as UTS 46 asks, and the size chars of its unicode_result are the name as the processing left it.

  5. The tables are exactly what tools/generate_tables.py writes from the pinned Unicode 17.0.0 files.

Conformance, and known failures

IdnaTestV2.txt is UTS 46’s own conformance file. idna passes every line of it, which test/known_failures.json records as an empty list: a line listed there must fail in the pass under UTS 46 alone, which the strict pass then leaves out, and every other line must pass, so the list never lies. The one kind of entry it may hold is a line that fails because of a difference between two versions of Unicode, the file’s and the tables’, with a reason that names both. The lines with a lone surrogate, which no UTF-8 string holds, are refused as invalid_utf8, as the file allows. JSON Schema’s own tests of hostname and idn-hostname run in webcpp::lexical, against the validators it builds on idna.
