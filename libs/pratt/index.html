pratt is a header-only engine for Pratt parsing, top-down operator precedence, in C++20, one of the libraries of webcpp. It knows no token, no operator and no tree: a program gives it a stream of tokens and a grammar that says what each token means, and gets back the grammar’s node or an error, as a value. A calculator built on the engine comes with it, exact in decimal by default.

This page teaches pratt concept by concept: why each exists, its smallest example, its variations and its rules. Every program it shows was compiled and run, natively and for wasm32-wasip2 and wasm32-wasip3, and printed the output shown under it. The reference that closes it lists every name the headers declare.

Introduction

A parser turns text into structure: 1 + 2 * 3 into an addition whose right operand is a product. Pratt parsing, or top-down operator precedence, after Vaughan Pratt’s paper of 1973, does it with one loop and one question asked of every token: what it means at the start of an expression, what it means after one, and how tightly it holds what stands on its left. Precedence and associativity become numbers, and a new operator is a new answer to that question, not a new rule of a grammar.

pratt is that loop, and nothing else: an engine that knows no token, no operator and no tree. A program gives it a token stream and a grammar, and the engine calls the grammar for each token it reads. The grammar decides what a parse builds, a value computed on the way, a tree, or a string, and every failure comes back as a value. Beside the engine, pratt ships a calculator built on it, calc, which computes exactly in decimal by default (The calculator).

nud, led and lbp

Pratt names the three answers of a token:

  • nud, its null denotation: what it means with nothing on its left. A digit is a number, - is the negation of what follows it, ( opens a grouping.

  • led, its left denotation: what it means after a complete expression, which becomes its left operand. - is a subtraction there, and * a product.

  • lbp, its left binding power: how tightly it binds that left operand. A token of power 0, such as the end of the input or a closing parenthesis, takes no left operand, and ends an expression.

The engine’s whole algorithm is one function, expression(rbp). It reads a token and calls its nud; then, as long as the next token’s lbp is greater than rbp, it reads that token and calls its led with what it has parsed so far. A nud or a led that needs an operand calls expression again, with the binding power of its own operator, so the recursion stops at the first operator that binds less tightly. A * that asks for its right operand with its power, 20, stops before a + of power 10, which then takes the product as its left operand: precedence is that comparison of two numbers.

One token can have both denotations, as - has, and its nud and its led are two functions that never meet. That is what makes Pratt parsing fit the languages people write, where the same character is a sign, an operator, a grouping or a call, depending on where it stands.

A first grammar

This program parses integers of one digit with a unary minus and the binary +, - and *, and computes their values while it parses. It begins with the engine’s header and an alias for its namespace:

#include <webcpp/pratt.hpp>

#include <cstddef>
#include <iostream>
#include <string_view>

namespace pratt = webcpp::pratt;

The engine reads tokens from a token stream: here, the characters of a text, each one a token, with '\0' once the text is spent. peek shows the next token, advance consumes it, and at_end says whether anything is left:

/** The characters of `text`, one token each, and '\0' once the text is spent. */
class characters {
public:
    using token_type = char;

    explicit characters(std::string_view text) : text_(text) {}

    [[nodiscard]] char peek() const { return pos_ < text_.size() ? text_[pos_] : '\0'; }

    char advance() {
        const char token = peek();
        if (pos_ < text_.size()) {
            ++pos_;
        }
        return token;
    }

    [[nodiscard]] bool at_end() const { return pos_ == text_.size(); }

private:
    std::string_view text_;
    std::size_t pos_ = 0;
};

The grammar answers the three questions. Its node_type, what a parse builds, is int, since this grammar computes as it goes. lbp gives + and - the power 10 and * the power 20. The nud of a digit is its value, and the nud of - asks the parser for an operand with the power 30, above every binary operator, so that the minus takes only the next number. The led of a binary operator asks for the right operand with the operator’s own power, then combines the two:

/** Integers of one digit, a unary minus, and the binary `+`, `-` and `*`. */
struct arithmetic {
    using node_type = int;

    /** How tightly `token` binds the expression on its left: 0 ends an expression. */
    [[nodiscard]] static int lbp(char token) {
        switch (token) {
            case '+':
            case '-': return 10;
            case '*': return 20;
            default: return 0;
        }
    }

    /** What `token` means at the start of an expression: a digit, or a minus sign. */
    template <class Parser>
    pratt::result<int> nud(Parser& p, char token) const {
        if (token >= '0' && token <= '9') {
            return token - '0';
        }
        if (token == '-') {
            const pratt::result<int> operand = p.expression(30);
            if (operand.has_error()) {
                return operand;
            }
            return -*operand;
        }
        if (token == '\0') {
            return pratt::error::unexpected_end;
        }
        return pratt::error::unexpected_token;
    }

    /** What `token` means after the expression `left`: a binary operator. */
    template <class Parser>
    pratt::result<int> led(Parser& p, char token, int left) const {
        const pratt::result<int> right = p.expression(lbp(token));
        if (right.has_error()) {
            return right;
        }
        switch (token) {
            case '+': return left + *right;
            case '-': return left - *right;
            default: return left * *right;
        }
    }

    // NOLINTEND(misc-no-recursion)
};

pratt::parse parses a whole input with a grammar, and returns a pratt::result<int>, the value or the error:

int main() {
    const arithmetic grammar;
    for (const std::string_view text : {"1+2*3", "2*3+4", "8-2-1", "-2*3", "1+", "1+*2", "12"}) {
        const pratt::result<int> value = pratt::parse(grammar, characters(text));
        if (value.has_error()) {
            std::cout << text << " -> error: " << value.error().message() << '\n';
        } else {
            std::cout << text << " -> " << *value << '\n';
        }
    }
}

It prints:

1+2*3 -> 7
2*3+4 -> 10
8-2-1 -> 5
-2*3 -> -6
1+ -> error: unexpected end of input
1+*2 -> error: unexpected token
12 -> error: trailing input after expression

1+2*3 and 2*3+4 both multiply first, whatever their order, since * binds more tightly than +. 8-2-1 is 5, (8-2)-1, because the led of the first - asks for its right operand with the power 10, and the second -, of the same power, is not greater, so it ends that operand and takes 8-2 as its own left one: an operator that asks with its own power is left-associative. -2*3 negates only the 2, as the minus asks with 30. The last three fail, each with an error of pratt’s: the input ends where an operand was due, a * stands where no nud has a meaning for it, and the 2 of 12, a second number with no operator before it, is input left over after a whole expression.

Requirements

  • A C++20 compiler. pratt’s tests and examples are built and run on every native lane of webcpp’s continuous integration, on emscripten under node, and for wasm32-wasip2 and wasm32-wasip3 with the Clang of wasi-sdk, under wasmtime (Testing).

  • Boost’s headers, 1.92 or newer. The engine uses Boost.System, for result and the error codes, and the calculator Boost.Decimal, for its default number type. pratt is header-only, and nothing of Boost is compiled for it.

  • webcpp’s configuration, config, whose <webcpp/config.hpp> every header of pratt includes first. It is header-only too.

  • Exceptions are the program’s choice. pratt throws nothing of its own, and no header of it throws, tries or catches, so the same headers serve a build with exceptions and one without. webcpp builds pratt with exceptions on every target, and its lint compiles every public header, and every test and example, without them; whether a program uses them is up to whoever builds it. A program without exceptions defines boost::throw_exception, which Boost.System’s result names, as xactor’s page shows.

  • RTTI is never restricted. Every target is built with it, and pratt asks no program to turn it off.

  • Nothing else: no threads, no clock, no global or static mutable state, and no allocation in the engine (Allocation).

Writing a grammar

A parse takes two things of the program’s: a token stream, which gives the tokens, and a grammar, which gives them their meaning. Each is a type that models a concept of the engine, checked when the program compiles, with no base class, no virtual function and no type erasure between them and the engine. What a parse builds is the grammar’s node, which the engine never looks into.

The token stream

A type models pratt::token_stream when it names its tokens token_type and has three functions:

  • peek(), which returns the next token without consuming it;

  • advance(), which consumes the next token and returns it;

  • at_end(), which says whether the input is spent.

The parser reads peek to decide whether the next token extends an expression, calls advance once for each token it hands a nud or a led, and asks at_end once a whole expression is parsed. peek must stay valid at the end of the input, and return there a token whose lbp is 0 and whose nud fails: '\0' in the first grammar, an end token in the calculator.

A stream may hold every token in advance, or lex each one as it is asked for. The characters of the first grammar is the simplest of them, and the calculator’s lexer, calc::stream, is lazy: it holds the source, its position and one token of lookahead, and no vector of tokens exists. The parser holds the stream by value, and moves it in.

The grammar

A type G models pratt::grammar_for<G, S>, a grammar of the tokens of a stream S, when it names its node node_type and has three functions of a token t:

  • lbp(t), its left binding power, an int;

  • nud(p, t), its meaning at the start of an expression;

  • led(p, t, left), its meaning after the expression left, which the engine moves in.

nud and led receive the parser, p, through which they parse their operands, and return a pratt::result<node_type>: the node, or an error. They are usually templates of the parser’s type, which names the grammar and the stream. The engine calls a led only for a token whose lbp is greater than the binding power the expression is parsed with, so a token of lbp 0 never reaches its led when the whole input is parsed with 0.

The parser’s expression(rbp) is what a nud or a led calls for an operand, and two more functions serve one that reads past its own token: p.peek() and p.advance(), the stream’s. The grammar of the openui-lang micro-subset reads the arguments of a call with them.

The node

The node is whatever the grammar builds. The first grammar’s is an int, the value, computed while the parse goes; the grammar of the helpers below builds a string, the S-expression of the parse; the calculator’s node is a value and the name of a variable, so that = knows what it writes (The calculator). A program that keeps a tree makes the node a tree of its own. The engine moves nodes, and does nothing else with them.

The helpers

Most operators come in a few kinds, and the engine writes each kind once, as a function a nud or a led returns. Each takes the parser and a binding power, parses its operands through expression, and calls a function of the grammar’s, make, which builds the node from the operands’ nodes:

This grammar is written with all six, and its node is the S-expression of the parse, (+ 1 (* 2 3)), so that its output shows how each line grouped. Its tokens are characters, as in the first grammar. Its binding powers put the sign below ^, and the postfix ! above everything; the grammar is shown here without its nud and its led, which follow:

/** Digits, `+ - * / ^`, a unary minus, a postfix `!`, and parentheses, as S-expressions. */
struct sexpr {
    using node_type = std::string;

    static constexpr int additive = 10;
    static constexpr int multiplicative = 20;
    static constexpr int sign = 30;
    static constexpr int power = 40;
    static constexpr int factorial = 50;

    [[nodiscard]] static int lbp(char token) {
        switch (token) {
            case '+':
            case '-': return additive;
            case '*':
            case '/': return multiplicative;
            case '^': return power;
            case '!': return factorial;
            default: return 0;
        }
    }

};

Its nud makes a digit a literal, - a prefix operator and ( a grouping. unary and binary are two functions of the program that return the make of a node of one operand and of two:

template <class Parser>
pratt::result<std::string> nud(Parser& p, char token) const {
    if (token >= '0' && token <= '9') {
        return pratt::literal(
            [](char digit) -> pratt::result<std::string> { return std::string(1, digit); },
            token);
    }
    switch (token) {
        case '-': return pratt::prefix(p, sign, unary('-'));
        case '(': return pratt::grouping(p, [](char next) { return next == ')'; });
        case '\0': return pratt::error::unexpected_end;
        default: return pratt::error::unexpected_token;
    }
}

Its led makes + - * / left-associative, ^ right-associative, and ! postfix. Only those tokens have an lbp above 0, so no other token reaches the led:

template <class Parser>
pratt::result<std::string> led(Parser& p, char token, std::string left) const {
    switch (token) {
        case '+':
        case '-':
        case '*':
        case '/': return pratt::infix_left(p, lbp(token), std::move(left), binary(token));
        case '^': return pratt::infix_right(p, power, std::move(left), binary('^'));
        default: return pratt::postfix(std::move(left), unary('!'));
    }
}
int main() {
    const sexpr grammar;
    for (const std::string_view text :
         {"1-2-3", "2^3^2", "1+2*3", "-2^2", "-3!", "2*-3", "(1+2)*3", "(1+2", "1+)", "()"}) {
        const pratt::result<std::string> tree = pratt::parse(grammar, characters(text));
        if (tree.has_error()) {
            std::cout << text << " -> error: " << tree.error().message() << '\n';
        } else {
            std::cout << text << " -> " << *tree << '\n';
        }
    }
}

It prints:

1-2-3 -> (- (- 1 2) 3)
2^3^2 -> (^ 2 (^ 3 2))
1+2*3 -> (+ 1 (* 2 3))
-2^2 -> (- (^ 2 2))
-3! -> (- (! 3))
2*-3 -> (* 2 (- 3))
(1+2)*3 -> (* (+ 1 2) 3)
(1+2 -> error: expected closing token
1+) -> error: unexpected token
() -> error: unexpected token

-2^2 negates the power, since the sign asks for its operand with 30 and ^ binds with 40: the sign’s operand is 2^2. -3! takes the factorial first for the same reason, and 2*-3 shows the same - as a nud where a led stood before it. A grouping parses 1+2 with 0, so the + inside it binds whatever the power of what is outside, and a missing ) is expected_closing_token. A ) where an operand is due has no nud, and is an unexpected token.

Every helper recurses through expression alone, so a grammar written with them routes every token through its nud and its led, and the parser’s depth limit bounds its whole recursion (Limits).

Parsing

pratt::parse(grammar, stream) parses the whole of a stream as one expression, with the power 0, and returns a pratt::result of the grammar’s node: the node, the first error a nud or a led returned, or trailing_input when tokens remain after a whole expression. A third argument, max_depth, bounds the recursion (Limits).

The class it uses is pratt::parser<Grammar, Stream>, which a program can construct itself, to call expression with another power, or to go on reading the stream after one expression. It holds a pointer to the grammar, so the grammar must outlive it, and a temporary grammar does not compile there; parse takes one, since its parser lives only for the call.

An error is whatever a nud or a led returned, passed on unchanged: one of pratt’s (Errors), or an error code of the program’s own category, which the engine never reads.

The calculator

<webcpp/pratt/calculator.hpp> is a grammar on the engine, ready to use: numbers and variables, the arithmetic and comparison operators of C, and assignment, increment and decrement. calc::evaluate(source, env) parses one line and computes its value as it parses, reading and writing its variables in an environment, env, which keeps them from one call to the next. Every operator goes through the engine’s helpers; the calculator adds no parsing of its own.

A program needs the header, and Boost.Decimal’s, whose default number type the calculator computes in:

#include <webcpp/pratt/calculator.hpp>

#include <boost/decimal.hpp>
#include <boost/decimal/charconv.hpp>

#include <array>
#include <iostream>
#include <string_view>

namespace pratt = webcpp::pratt;
namespace calc = webcpp::pratt::calc;

evaluate returns a pratt::result of the environment’s number type, here boost::decimal::decimal64_t. This program writes each line, then its value in Boost.Decimal’s shortest form, or its error:

/** Writes `line`, then its value in Boost.Decimal's shortest form, or its error. */
void print(std::string_view line, const pratt::result<boost::decimal::decimal64_t>& value) {
    std::cout << line << " -> ";
    if (value.has_error()) {
        std::cout << "error: " << value.error().message() << '\n';
        return;
    }
    std::array<char, 48> buffer{};
    const boost::decimal::to_chars_result written =
        boost::decimal::to_chars(buffer.data(), buffer.data() + buffer.size(), *value);
    std::cout << std::string_view(buffer.data(), written.ptr) << '\n';
}

A variable that no line has written is an error only where it is read: a = 5 writes a name the environment does not hold yet.

Exactness and the number type

The calculator computes in boost::decimal::decimal64_t by default, a decimal floating-point type of 16 significant digits, for exactness: a decimal fraction written in the input, 0.1 or 19.99, is exactly that number, so 0.1 + 0.2 == 0.3 holds and price * quantity is 59.97, not a binary approximation of it. The lexer builds each number in the number type’s own arithmetic, its digits as one integer divided once by ten to the number of its fraction digits, and never through a double.

A literal longer than the type’s precision keeps its first 17 significant digits in decimal64_t and in double (digits10 + 1, or max_digits10 where that is more): a later digit of the integer part multiplies the value by ten, and a later digit of the fraction is dropped. So 1. followed by any number of zeros is exactly 1, a literal up to the type’s largest value is finite, the largest double written out in full included, and 1 followed by 400 zeros is an infinity. A long literal is within one unit in the last place of the nearest decimal64_t, and within a few of the nearest double, whose digits round as they are read. A fraction keeps its value down to the type’s smallest subnormal, and is 0 below it.

An integral power is computed by repeated squaring, in the number type’s own multiplications, for exactness and determinism: every product is exact while it fits the type’s precision, so 43 + 12 + 2 * (44 - 12) ^ 4 is exactly 2097207, and the result is the same bits on every platform, where a library’s pow may round differently from one to the next. Past the precision, each product rounds, and the relative error grows with the exponent, where a correctly rounded pow would not: in double, 1.000000001 ^ 1000000000 differs from the result of std::pow in its ninth significant digit. That is the price of the same bits on every platform.

The same bits assume each compiler’s default for fusing a multiplication and an addition, which every operation of the calculator keeps apart in statements of their own. Built with -ffp-contract=fast or -ffast-math, a compiler may fuse them anyway, and a double result may then differ in its last place from one platform to another.

The power’s sign is the base’s when the exponent is odd. A negative integral exponent is one divided by the positive power, so 2 ^ -3 is 0.125, and 0 ^ 0 is 1. When the positive power overflows, or underflows to 0, pow computes the result instead, so 2 ^ -1074 is the smallest positive double and 0.1 ^ -400 is an infinity. Otherwise only an exponent that is not an integer calls pow.

Division by zero is an error, division_by_zero, for / and for %, and for 0 ^ -1, which divides by zero too. A floating-point type would answer an infinity or a NaN, and the line after would compute on with it; the calculator stops at the line that asked.

Any type that models calc::number serves. It is copyable and constructible from int, has the binary + - / *, the unary - and the six comparisons, and pow, fmod and trunc, found as using std::pow; pow(a, b) finds them, each returning the type itself. Boost.Decimal’s types model it, and so do float, double and long double. The number type is the environment’s: calc::environment<double> computes in double.

43 + 12 + 2 * (44 - 12) ^ 4 -> 2097207
0.1 + 0.2 -> 0.30000000000000004
0.1 + 0.2 == 0.3 -> 0

The integral powers are still exact, 2 ^ 60 included, since repeated squaring multiplies powers of two, which double holds exactly. The decimal fractions are not: 0.1 and 0.2 are the nearest binary fractions, whose sum is not the nearest one to 0.3. 2.25 ^ 0.5 is not an integral power, and is the result of std::pow. Its exact value, 1.5, is a double, so any pow that errs by less than an ulp returns it exactly, on every standard library.

The environment

The environment is where the variables live, and its type is the program’s choice. A type E models calc::environment_for when its number_type models calc::number and it has two functions:

  • lookup(name), which returns a pointer to the value of name, or nullptr when the name is not set;

  • assign(name, value), which sets it and returns a pratt::result<void>, so that it can refuse, a storage that is full for instance, with an error of its own.

The name is a std::string_view into the line, so an environment that keeps a name copies it. calc::environment<Number, Allocator> is the calculator’s own, a std::map whose nodes and keys allocate through the program’s allocator (Allocation). This one is a program’s own, two variables in fixed storage, in double:

/** Two variables of names up to 8 characters, in fixed storage, computed in double. */
class two_variables {
public:
    using number_type = double;

    [[nodiscard]] const double* lookup(std::string_view name) const {
        for (std::size_t i = 0; i < used_; ++i) {
            if (slots_[i].name() == name) {
                return &slots_[i].value;
            }
        }
        return nullptr;
    }

    pratt::result<void> assign(std::string_view name, double value) {
        for (std::size_t i = 0; i < used_; ++i) {
            if (slots_[i].name() == name) {
                slots_[i].value = value;
                return {};
            }
        }
        if (used_ == slots_.size() || name.size() > slot::capacity) {
            return boost::system::errc::make_error_code(boost::system::errc::not_enough_memory);
        }
        slot& fresh = slots_[used_++];
        std::ranges::copy(name, fresh.characters.begin());
        fresh.length = name.size();
        fresh.value = value;
        return {};
    }

private:
    struct slot {
        static constexpr std::size_t capacity = 8;

        std::array<char, capacity> characters{};
        std::size_t length = 0;
        double value = 0;

        [[nodiscard]] std::string_view name() const { return {characters.data(), length}; }
    };

    std::array<slot, 2> slots_{};
    std::size_t used_ = 0;
};

The lexer is lazy: it reads one token ahead, and the parse reads the tokens in order, so the first error in reading order is the one returned. A token’s error is found when the token is read, and an operator’s own error, an undefined operand or a zero divisor, once the operator has its operands. template <class Parser>
pratt::result<node_type> led(Parser& p, const token& t, node_type left) const {
    switch (t.type) {
        case kind::assign:
            return pratt::infix_right(p, assign_bp, std::move(left), detail::binary("="));
        case kind::colon:
            return pratt::infix_left(p, pair_bp, std::move(left), detail::binary(":"));
        case kind::lparen: return call(p, std::move(left));
        case kind::invalid: return pratt::error::invalid_character;
        case kind::unterminated: return pratt::error::unexpected_end;
        default: return pratt::error::unexpected_token;
    }
}

The call’s led reads its arguments in a loop, each one a whole expression of the engine’s, until the ):

template <class Parser>
static pratt::result<node_type> call(Parser& p, node_type callee) {
    node_type node = "(call " + std::move(callee);
    if (p.peek().type == kind::rparen) {
        p.advance();
        return std::move(node) + ")";
    }
    while (true) {
        pratt::result<node_type> argument = p.expression(0);
        if (argument.has_error()) {
            return argument;
        }
        node += ' ';
        node += *argument;
        const kind next = p.peek().type;
        if (next == kind::rparen) {
            p.advance();
            return std::move(node) + ")";
        }
        if (next != kind::comma) {
            return pratt::error::expected_closing_token;
        }
        p.advance();
    }
}

A character that is no token, and a " that the line does not close, are tokens of their own with the highest power, as in the calculator, so the engine reaches them wherever they stand: the first is invalid_character, the second unexpected_end. The node allocates, since it is a string; it is the examples’ output format, and the parser of openui-lang to come defines a tree of its own, under the rule of Allocation.

Errors

pratt reports every failure as a value, and throws nothing of its own. Every operation that can fail, every nud and every led returns a pratt::result<T>, which is Boost.System’s result: a T, or the boost::system::error_code of the failure. pratt’s own errors are the enumerators of pratt::error, in a category of their own, pratt::error_category(), whose name is webcpp.pratt. Limits

Pratt parsing recurses: each operand that a nud or a led asks for is a call of expression, below the calls of the nud and the led that asked, so every level of nesting in the input costs stack. A line of ten thousand ( would nest ten thousand calls, and overflow the stack: a crash, not an error.

The depth limit

The parser counts its active expression calls, and refuses the call that would make them more than its limit, max_depth, with nesting_too_deep, before it reads a token. So the stack never grows past what the limit allows, and the input that would have overflowed it is an error like any other. max_depth is an argument of the parser’s constructor, of parse and of calc::evaluate, and its default is pratt::default_max_depth, which is 64. A negative max_depth behaves as 0, which refuses every parse.

A 1 inside a number of parentheses is that number plus one calls deep:

calc::environment<> env;
std::cout << "default_max_depth: " << pratt::default_max_depth << '\n';

std::cout << "63 pairs: ";
print(calc::evaluate(nested(63), env));

std::cout << "64 pairs: ";
print(calc::evaluate(nested(64), env));

std::cout << "64 pairs, max_depth 128: ";
print(calc::evaluate(nested(64), env, 128));

std::cout << "10000 opening parentheses: ";
print(calc::evaluate(std::string(10000, '('), env));

It prints:

default_max_depth: 64
63 pairs: 1
64 pairs: error: expression nested too deeply
64 pairs, max_depth 128: 1
10000 opening parentheses: error: expression nested too deeply

The limit bounds the recursion through expression alone. That is the whole recursion of a grammar whose nuds and leds parse every operand through expression or the helpers, as the calculator’s and the micro-subset’s do, the micro-subset’s argument loop included. A nud or a led that recurses through functions of its own, without calling expression, is not bounded by it, and bounds that recursion itself.

Raising the limit

A program that raises the limit raises its stack with it, by the cost of a level times the levels it adds. On wasm, the stack is set when the program is linked, with the linker’s flag -Wl,-z,stack-size= and the size in bytes. A program that evaluates groupings 1024 deep in a debug build needs about 1024 times 272 bytes and 7.5 KiB, about 280 KiB, so it links with a stack of 1 MiB, which keeps the margin the default keeps:

clang++ --target=wasm32-wasip2 -std=c++20 \
    -Wl,-z,stack-size=1048576 \
    program.cpp -o program.wasm

and passes max_depth to every call: calc::evaluate(line, env, 1024). A b2 project adds the flag to its target’s requirements:

<linkflags>-Wl,-z,stack-size=1048576

Natively, the stack is the thread’s. The main thread’s is the system’s, commonly 8 MiB on Linux and macOS (ulimit -s shows it), and a thread a program creates takes the size it is created with, through pthread_attr_setstacksize or Boost.Thread’s boost::thread::attributes::set_stack_size. The measurement above holds 12741 levels of ^ on 8 MiB in a debug build, so a native program has room for a limit far above the default without changing its stack.

Allocation

A webcpp library avoids dynamic allocation as far as its job allows, and lets its user choose the allocator of what it does allocate. In pratt:

  • The engine allocates nothing. A parser holds a pointer to its grammar, its stream and a count of its active expression calls. What a parse allocates is what the grammar’s nodes and stream allocate: nothing for the calculator’s, and a string for each node of the S-expression grammars of this page’s examples, their output format.

  • The calculator’s parse allocates nothing. Its lexer is lazy and holds a view of the line; its tokens and its nodes are views and numbers.

  • The environment allocates through its Allocator. calc::environment<Number, Allocator> allocates through it alone: in assign, when a name is new, the map’s node and the name’s characters when the name is longer than the string’s own small buffer; and, with a standard library whose map allocates when it is built, as MSVC’s does, then. Replacing the value of a name it holds and reading one allocate nothing. An environment of the program’s own allocates what it chooses, and the one of The environment nothing at all.

  • A Number that allocates does so through its own allocator. decimal64_t and double allocate nothing. A type whose arithmetic allocates, Boost.Multiprecision’s mpfr_float with et_off for instance, allocates through the allocator it was built with, which the calculator never sees.

So, for a Number that allocates nothing, the environment’s allocator is the calculator’s only source of memory. calc::environment takes any allocator: the map’s allocator is Allocator rebound to the map’s value type, and the key’s is Allocator rebound to char, so an allocator written for any type serves, a polymorphic one included. This one counts what it allocates, and takes the memory from std::allocator:

/** What a counting allocator has done, in an object its program owns. */
struct tally {
    std::size_t allocations = 0;
    std::size_t deallocations = 0;
};

/** An allocator that counts into a tally, and takes its memory from std::allocator. */
template <class T>
class counting {
public:
    using value_type = T;

    explicit counting(tally* count) noexcept : count_(count) {}

    template <class U>
    explicit counting(const counting<U>& other) noexcept : count_(other.count()) {}

    T* allocate(std::size_t n) {
        ++count_->allocations;
        return std::allocator<T>{}.allocate(n);
    }

    void deallocate(T* pointer, std::size_t n) noexcept {
        ++count_->deallocations;
        std::allocator<T>{}.deallocate(pointer, n);
    }

    [[nodiscard]] tally* count() const noexcept { return count_; }

    template <class U>
    bool operator==(const counting<U>& other) const noexcept {
        return count_ == other.count();
    }

private:
    tally* count_;
};

Testing

A test of a grammar checks that each input gives the node it should, and each wrong input the error it should. In pratt both are values, a pratt::result of the node or of the error, and nothing in a parse depends on the world outside the test: no clock, no thread, no global state, and no exception to catch. A parse of the same input by the same grammar gives the same result every time.

Testing a grammar

The test below checks the grammar of the openui-lang micro-subset (The openui-lang micro-subset and the REPLs), with Boost.Core’s lightweight_test, the framework of one header that pratt’s own tests use. It includes the engine, the framework and the grammar:

A test of errors compares the error of each wrong line with an enumerator of pratt::error, and checks the depth limit on both of its sides, with a limit small enough to write the input by hand:

void every_error_is_a_value() {
    BOOST_TEST(parsed("Stack(1").error() == pratt::error::expected_closing_token);
    BOOST_TEST(parsed("= 3").error() == pratt::error::unexpected_token);
    BOOST_TEST(parsed("root @ 3").error() == pratt::error::invalid_character);
    BOOST_TEST(parsed("a b").error() == pratt::error::trailing_input);
}

void the_depth_is_bounded() {
    BOOST_TEST(parsed("((x))", 3).has_value());
    BOOST_TEST(parsed("(((x)))", 3).error() == pratt::error::nesting_too_deep);
}

main calls the cases and returns boost::report_errors(), the program’s status:

When every check holds, the program prints No errors detected. on its standard error, nothing on its standard output, and returns 0. A check that fails prints its expression, its values, its file and its line on the standard error, and main returns 1. .value() of a result that holds an error throws, or, built without exceptions, calls boost::throw_exception, which ends the program: the test stops there rather than compare a node that is not there.

How pratt is tested

pratt’s tests are lightweight_test programs, one per subject, under test/, each declared in test/Jamfile with webcpp’s webcpp.run:

Test What it checks

errors

The values of pratt::error, which are fixed, the category’s name and messages, and the conversion and the comparison with an error_code.

engine

The engine with a grammar of the test’s own, whose binding powers come from a table: precedence, associativity, prefix and postfix positions, the errors the engine and its helpers report, the order of the nud and led calls, the depth limit at its default, one level beyond and at a custom value, and what models token_stream and grammar_for.

sexpr

The engine through a grammar whose tokens are characters and whose nodes are strings, with nothing of the calculator.

lexer

The calculator’s number concept and its lazy lexer, over decimal64_t and double: the kinds, texts and values of the tokens, numbers built in the number type’s own arithmetic and past its range, the invalid token, whitespace, and the end token that stays.

calculator

The calculator over decimal64_t and double: values and errors, exact integral powers, division by zero, assignment and increment through parentheses, an invalid character wherever it stands, the first error in reading order, and the environments a user brings, one in fixed storage whose assign fails and one whose allocator counts.

allocation

The global operator new, replaced for this program alone: no call across a session over an environment in fixed storage, and over calc::environment only those of its allocator.

depth

The default depth limit with the calculator’s own frames: a grouping, a chain of signs and a chain of ^ exactly default_max_depth deep are evaluated and one level more is refused, twice the default still fits the stack, and a line of ten thousand ( is refused. On wasip2 and wasip3, in a debug build with wasm’s default stack, it is the check of the measurement of Limits.

openui

The openui-lang micro-subset, through the grammar it shares with its REPL: every line of its session, ( as a grouping and as a call, the right-associative =, and the errors of its lazy lexer.

Each case is a function named after the rule it checks, such as a_decimal_fraction_is_exact_in_decimal, and main calls them all and returns boost::report_errors(). Beside them, test/Jamfile compiles each public header alone, as the only include of its translation unit, so that a header that leans on an include it does not make fails, naming it. The lint checks the boundary that meta/include-boundaries.json declares: the engine’s headers include neither the calculator nor Boost.Decimal, since the engine knows no grammar and no number type. And example/Jamfile builds every program this page shows, runs it with the .input beside it as its standard input when there is one, and compares what it printed with the .expected beside it; a program that returns anything but 0 fails too.

Targets

test/Jamfile and example/Jamfile declare the targets they are built for, webcpp.targets native emscripten wasip2 wasip3, and b2 builds each program for those alone:

Target How it is built and run

native

Any toolset that is not one of the three below: GCC, Clang and MSVC among them. With exceptions, unless its user asks for exception-handling=off, which links webcpp’s tools/throw_exception.cpp.

emscripten

b2’s toolset emscripten, wasm32, run by node: 16 tests and 11 examples.

wasip2

The toolset clang-wasip2, the Clang of wasi-sdk for wasm32-wasip2, run by wasmtime. With exceptions, as WebAssembly’s exception handling, as on wasip3.

wasip3

The toolset clang-wasip3, for wasm32-wasip3, run by wasmtime. With exceptions, as WebAssembly’s exception handling.

That pratt works without exceptions is checked by the lint, which compiles every public header, and every test and example, which instantiate its templates, with exception-handling=off; a template that none of them instantiates is not checked.

<webcpp/pratt/config.hpp>, which every public header of pratt includes first, defines WEBCPP_PRATT_NO_EXCEPTIONS when webcpp has no exceptions (WEBCPP_HAS_EXCEPTIONS is not defined: the compiler has none, or the program defined WEBCPP_NO_EXCEPTIONS), and a program may define it for pratt alone, to turn pratt’s exceptions off in a build that has them, as Boost.Asio’s BOOST_ASIO_NO_EXCEPTIONS does. pratt raises no exception of its own, so the macro changes nothing in it: it exists so that a program can set it for every webcpp library alike. The tests config, config_developer_defined and config_all_off check the three ways it is defined, and the lint refuses a throw in a public header, even in a template nothing instantiates: an exception goes through boost::throw_exception.

From the root of a webcpp checkout, each of these builds and runs, natively:

b2 libs/pratt/test

The 16 tests: the lightweight_test programs, and each of the 5 public headers compiled alone.

b2 libs/pratt/example

The 11 examples, each built, run, and its output compared with the one beside it.

b2 libs/pratt/test libs/pratt/example toolset=emscripten

The same on emscripten: 16 tests and 11 examples, each run by node, b2’s toolset itself.

b2 libs/pratt/test libs/pratt/example toolset=clang-wasip2 testing.launcher=wasmtime

The same for wasm32-wasip2: 16 tests and 11 examples, each run by wasmtime. toolset=clang-wasip3 does the same for wasm32-wasip3: 16 tests and 11 examples.

The WASI toolsets are b2’s clang, which a user-config.jam registers against wasi-sdk, as xactor’s page shows. The emscripten toolset is registered against emsdk, as trystero’s page shows, and runs a program with node itself, never with a testing.launcher. b2 compares timestamps, so a result that counts is built from scratch, with b2 -a. b2 libs/pratt/test//calculator builds and runs one test alone, while working on it.

The test matrix

The continuous integration runs pratt’s tests and examples in lanes, one toolset each: the native compilers, and wasip2 and wasip3. Each lane builds from scratch and records what b2 built and ran:

b2 -a --dump-tests --out-xml=<lane>.xml toolset=<toolset> libs/pratt/test libs/pratt/example

webcpp’s tools/report/report.py merges the files of every lane into a matrix: a page of the libraries by lanes, and a page of each library’s tests and examples by lanes, where each cell says whether that program passed in that lane, or how it failed, at compile time, at link time or when it ran. The matrix is published with the documentation, at https://webcpporg.github.io/report/.

webcpp::pratt::calc::environment

The calculator’s own environment: a std::map from names to values, whose map and keys allocate through the user’s allocator.

Synopsis

Declared in <webcpp/pratt/calculator.hpp>

template<
    number Number = boost::decimal::decimal64_t,
    class Allocator = std::allocator<std::pair<std::string const, Number>>>
class environment;

Description

It allocates through Allocator alone: in assign, when a name is new, the map’s node, and the key’s characters when the name is longer than the string’s small buffer; and when it is constructed, with a standard library whose map allocates then, as MSVC’s does. Assigning a name it holds replaces the value in place, and lookup allocates nothing. For a Number that allocates nothing, such as decimal64_t or double, nothing else that evaluate does allocates, so this environment’s allocator is the calculator’s only source of memory. A Number whose arithmetic allocates, Boost.Multiprecision’s mpfr_float with et_off for instance, allocates through its own allocator.

The key holds a std::basic_string whose allocator is Allocator rebound to char, and the map’s allocator is Allocator rebound to the map’s value type, so any allocator serves, whatever type it is written for: environment<Number, A<char>> and the default are both well formed. The map compares with std::less<>, so a name is looked up as a std::string_view, without building a key.

webcpp::pratt::calc::grammar

The calculator’s grammar over an environment: numbers, variables, the arithmetic operators + - * / % ^, the comparisons, =, and ++ and -- before and after a variable.

Synopsis

Declared in <webcpp/pratt/calculator.hpp>

template<environment_for Environment>
class grammar;

Description

^ is right-associative and binds tighter than a unary sign, so -2 ^ 2 == -4; = is right-associative, so c = d = 5 sets both. A comparison gives 1 or 0. ++x gives the new value and x++ the old, as in C. An integral exponent is computed by repeated squaring in Number, so an integer power is exact while it fits the type’s precision; past that, the relative error grows with the exponent, where a correctly rounded pow would not, which is the price of the same bits on every platform. x ^ -n is 1 / x ^ n, or pow’s result when x ^ n overflows or underflows to 0; otherwise only a non-integral exponent calls pow.

The tokens are read one at a time, and the first error found in reading order is the one returned. A token’s error is found when the token is read, and an operator’s when the operator has its operands: = checks its target before it reads its right operand, so 5 = 3 $ gives error::invalid_assignment_target, while + finds an undefined operand, or / a zero divisor, only after its right operand is read, so x + 1 $ gives error::invalid_character even when x is undefined, and so does 1 / 0 $.

A write made before the error stays made: nothing is undone. i++ $ increments i, then gives error::invalid_character, and i++ ) increments it, then gives error::trailing_input.

webcpp::pratt::calc::stream

The calculator’s lexer, a lazy webcpp::pratt::token_stream.

Synopsis

Declared in <webcpp/pratt/calculator.hpp>

template<number Number>
class stream;

Description

It holds the source, its position and one token of lookahead, and lexes the next token only when advance consumes the current one.

A number is digits, then optionally . and more digits; it is computed in Number arithmetic alone, never through double, so 0.1 is exactly one tenth in a decimal type. A name is a letter or _, then letters, digits and _. Space, tab, carriage return and line feed separate tokens. Any other character is a token of kind kind::invalid, one character long, which the grammar rejects where it stands.

A number keeps its first digits10 + 1 significant digits, or max_digits10 where that is more, 17 in both decimal64_t and double, as one integer, divided once by ten to the number of its fraction digits. A later digit of the integer part multiplies the value by ten, and a later digit of the fraction is dropped. So a literal of at most digits10 significant digits, with at most 22 fraction digits in double, is the nearest value; a longer one is within one unit in the last place of it in decimal64_t, and may be a few units away in double, whose digits round as they are read. 1. followed by any number of zeros is exactly 1; a literal up to the type’s largest value is finite, the largest double written out in full included, and 1 followed by 400 zeros is infinite; and a fraction keeps its value down to the type’s smallest subnormal, and is 0 below it. A type without std::numeric_limits keeps every digit.

A non-ASCII character is a token of kind kind::invalid per byte, so the parse stops at its first byte with error::invalid_character.
