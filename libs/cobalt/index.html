webcpp::cobalt makes Boost.Cobalt-style C++20 applications usable in browsers through Emscripten and in WASIp2/P3 runtimes such as Wasmtime. JSPI and Asyncify are Emscripten suspension variants; they are not WASI versions. Cobalt supplies coroutines and asynchronous composition, while Asio supplies the executor and I/O.

Use How-to: select the compiled integration to select the runner and optional TLS, Configuration and deployment profiles to choose requirements, and Differences to understand the boundaries of compatibility. The Feature matrix distinguishes target facilities from runtime permission.

Tutorial: await a timer

Use the library at libs/cobalt in the WebCPP superproject, matching Boost 1.92 headers and a configured C++20 compiler. The application writes co_main; the separately linked runner owns main and drives its executor.

#include <webcpp/test/exit_status.hpp>

#include <webcpp/asio/steady_timer.hpp>
#include <webcpp/cobalt/main.hpp>
#include <webcpp/cobalt/op.hpp>
#include <webcpp/cobalt/result.hpp>
#include <webcpp/cobalt/this_coro.hpp>

#include <chrono>
#include <cstdio>

// Boost 1.92 intentionally omits this promise hook without exceptions. Clang
// 21 and 23 still warn at the coroutine definition even with -fno-exceptions.
// Keep the workaround on this native example, without changing Boost's types.
#if defined(__clang__) && defined(WEBCPP_TARGET_NATIVE) && !defined(__EXCEPTIONS)
#if __has_warning("-Wcoroutine-missing-unhandled-exception")
#pragma clang diagnostic push
#pragma clang diagnostic ignored "-Wcoroutine-missing-unhandled-exception"
#endif
#endif

webcpp::cobalt::main co_main([[maybe_unused]] int argc, [[maybe_unused]] char** argv) {
    // Cobalt's awaiter has static members called by the compiler's co_await expansion.
    // NOLINTNEXTLINE(readability-static-accessed-through-instance)
    const auto exec = co_await webcpp::cobalt::this_coro::executor;
    webcpp::asio::steady_timer timer(exec, std::chrono::milliseconds(50));
    auto [error] = co_await webcpp::cobalt::as_tuple(timer.async_wait(webcpp::cobalt::use_op));
    if (error) {
        std::printf("timer error: %d\n", error.value());
        co_return webcpp::test::exit_status(1);
    }
    std::puts("cobalt slept");
    co_return webcpp::test::exit_status(0);
}

#if defined(__clang__) && defined(WEBCPP_TARGET_NATIVE) && !defined(__EXCEPTIONS)
#if __has_warning("-Wcoroutine-missing-unhandled-exception")
#pragma clang diagnostic pop
#endif
#endif

The example’s webcpp::test::exit_status reports its result to the project’s browser test harness. It is test support, not a Cobalt API requirement. The coroutine gets its executor, awaits an Asio timer with Cobalt’s completion token, checks the error, then returns its exit status.

From the superproject root:

unset CPATH CPLUS_INCLUDE_PATH C_INCLUDE_PATH
b2 -a variant=release libs/cobalt/example//asio_cobalt.output

The matched output is:

cobalt slept

For a real browser, build the page driver with Emscripten:

b2 -a toolset=emscripten variant=release libs/cobalt/test/browser//browser-pages
b2 -a toolset=emscripten variant=release webcpp-suspend=asyncify libs/cobalt/test/browser//browser-pages

The driver serves the example page and checks its interaction in Chrome. A successful Node run alone does not establish browser support.

How-to: select the compiled integration

Include webcpp/cobalt/main.hpp and the operation headers and use webcpp::cobalt. Select one entry-point model:

B2 dependency Application contract

/webcpp/cobalt//core

The application supplies main and drives its context.

/webcpp/cobalt//cobalt

The application supplies co_main; link exactly one runner.

/webcpp/cobalt//io_ssl

Add the corrected SSL wrapper to a custom-main application.

/webcpp/cobalt//cobalt_ssl

Combine the runner and corrected SSL wrapper.

The SSL targets select the same source-built OpenSSL and embedded CA provider as Asio and Beast. The plain core does not pull in TLS. Browser HTTPS/WSS uses the browser’s TLS implementation and trust policy, not these OpenSSL targets.

Build with another build system

sources.json is the source inventory, split into core, runner, ssl and multi_add for each target. B2’s generated src/sources.jam comes from the same inventory. Consumers compile these already shipped files; the maintainer-only upstream/sync.py is not a build step.

Use matching Boost 1.92 headers. Compile sources and application with the same target, exception mode, threading ABI and Cobalt configuration. For native, define BOOST_COBALT_NO_LIB=1 when linking the explicit archives. The native core and runner use the unchanged upstream sources. The native SSL inventory selects WebCPP’s separate corrected wrapper and composed-transfer adapter.

Add Asio’s explicit runtime source for Wasm: src/wasip2/pollable.cpp, src/wasip3/waitable.cpp or src/browser_src.cpp from the Asio library. Verify the pinned WASI SDK ABI before compiling its bridge. Emscripten also requires embind, stack exports and the chosen suspension flags. Its browser bridge must reach the final link as an object, so JavaScript import metadata is retained.

For guest TLS, provide matching OpenSSL headers and libssl/libcrypto, the generated embedded-CA header include directory, WEBCPP_ASIO_HAS_OPENSSL=1 and WEBCPP_COBALT_LINK_SSL=1. A macro alone does not link or configure OpenSSL. The WASI OpenSSL provider also links wasi-libc’s wasi-emulated-getpid, wasi-emulated-signal, wasi-emulated-process-clocks and wasi-emulated-mman support libraries, after its crypto archive, as the consumer recipe records. Replacing the CA bytes is an Asio TLS-context operation; it does not change the browser’s certificate store.

The superproject’s tools/test/fixtures/portable-network/CMakeLists.txt is a consumer recipe. tools/test/portable_network_distribution.py creates a source archive with a SHA-256 inventory, deletes its staging inputs and extracts it into a path with spaces. The archive omits Git/B2/cache files. Consumers use a direct compiler or CMake. Compiler dependency files verify the actual source and header paths, the complete Cobalt source selection and the configuration of each source. Checkout headers and undeclared external dependencies fail that audit.

The optional --openssl-prefix and --ca-header inputs copy explicitly supplied dependencies into the extracted tree before compiling the TLS tests. They must match the selected target and ABI. --evidence-dir <directory> preserves the tested source archive and compiler-receipt.json, including commands and resolved dependency paths. These are local consumer proofs, not a second release pipeline.

For example, run the native CMake consumer from the superproject:

python3 tools/test/portable_network_distribution.py \
  --compiler /path/to/clang++ --boost-include /path/to/boost/include \
  --target native --build-system cmake \
  --cobalt-executor custom --cobalt-pmr custom \
  --evidence-dir /path/to/evidence

The custom configuration is the compiled fixture test/distribution/consumer_config.hpp. It declares an Asio context executor and a counting PMR resource before any Cobalt header. Every compiled source receives that same preincluded header. The test crosses translation-unit boundaries and checks allocations through the compiled core’s allocator. It proves that concrete customization, not every user-defined executor or memory implementation.

Await a browser Promise

Use Asio’s browser::async_await with the executor obtained from this_coro::executor and Cobalt’s use_op completion token. The operation resumes the coroutine when JavaScript settles the Promise; rejection follows the bridge’s error contract. DOM-event waits use the corresponding Asio bridge. Neither operation exists on a native or WASI target without JavaScript hosting. The Promise tests cover both exception modes and both Emscripten suspension modes.

Preserve the corrected native SSL composition

Include webcpp/cobalt/io/ssl.hpp, keep the concrete io::ssl::stream type and call webcpp::cobalt::io::read or write for complete-buffer transfers. These overloads preserve cancellation through Asio’s composed operations. read_some and write_some remain primitive operations on the corrected stream.

Do not erase the stream to Boost’s generic I/O interface and expect this composition correction to follow it. That selects Boost’s original generic read/write implementation, whose cancellation association failed the native regression. The wrapper’s handshake state protections still apply, but this does not repair an upstream composition chosen through a different static type.

Stream and buffer storage must outlive the pending operation. A transferred-byte count can be nonzero on cancellation. Terminal cancellation does not make a connection reusable; end that connection according to the underlying Asio contract.

SSL handshake and stream state

The wrapper fixes the Boost.Cobalt SSL state defects on native and WASIp2/P3. The same state guards apply with exceptions enabled or disabled in a supported compiler/threading profile. WASI SDK 34 provides both exception modes for single-thread P2/P3 and only EH off for cooperative P3; native co_main limitations remain as described in Exceptions and errors. Browser HTTPS/WSS uses host TLS and does not use this wrapper.

The fixed wrapper supports STARTTLS. Before its first handshake, reads and writes use plain TCP. Complete a successful, verified handshake before sending confidential application data. secure() reports TLS establishment, not whether the application configured trust and hostname verification.

State or operation Behavior

Before the first handshake

secure() is false; plain TCP I/O is allowed.

Successful handshake

secure() becomes true before the coroutine resumes; application I/O uses TLS.

Failed or cancelled handshake

secure() stays false; further application I/O returns not_connected with zero bytes.

Handshake after an attempt has started

Returns already_started; use a new stream for another attempt.

Shutdown before TLS establishment

Returns no_protocol_option.

Completed shutdown, including failure or cancellation

Clears secure() and blocks application I/O; another shutdown returns no_protocol_option.

Both handshake overloads update the same state. The buffered overload reports consumption of already-read handshake bytes. Serialize state-changing operations; the wrapper does not synchronize overlapping handshakes, shutdown or direct SSL object manipulation.

native_ssl_handle() returns a borrowed SSL*, owned by the stream. Do not free it or retain it after stream destruction. Use it to configure SNI before the handshake and check the result. native_handle() still denotes the TCP socket. Peer trust, hostname verification and SNI remain distinct application duties.

Cancelling an application transfer cannot retract bytes already sent and does not undo the handshake, so secure() may remain true after transfer cancellation. It is not a connection-health or retry-safety indicator. End the connection after terminal cancellation; do not infer safe reuse from that flag.

Configuration and deployment profiles

This source distribution requires Boost 1.92.0 headers. The public configuration rejects other Boost versions before an application can combine them with the pinned compiled sources, including when compiling without B2. The native core inventory includes src/native_version.cpp for the same check when only the archive is built. Do not omit source-inventory entries.

Define requirements before any Cobalt header, consistently in every translation unit. WEBCPP_COBALT_HAS_* macros are read-only observations: defining one does not supply the missing environment feature. REQUIRE_* controls default to unset; setting one to 1 requests a compile-time diagnostic when unavailable.

Control or observation Meaning

WEBCPP_COBALT_NO_EXCEPTIONS

Derived from the collection’s exception policy, or explicitly selected for this integration. It does not change the compiler’s exception ABI or repair upstream issue 287.

WEBCPP_COBALT_LINK_SSL

Unset by default; set to 1 when explicitly linking the matching corrected SSL implementation and provider; supplied by the SSL B2 targets.

WEBCPP_COBALT_REQUIRE_SOCKET_BACKEND

Require guest TCP/UDP, unavailable in a normal browser.

WEBCPP_COBALT_REQUIRE_OPENSSL

Require both a guest TLS target and explicit SSL linkage.

WEBCPP_COBALT_REQUIRE_THREADS

Require a thread-enabled Asio/compiler profile.

WEBCPP_COBALT_REQUIRE_LOCAL_SOCKETS

Require native local sockets.

WEBCPP_COBALT_REQUIRE_SIGNALS

Require native operating-system signals, not coroutine cancellation signals.

WEBCPP_COBALT_REQUIRE_SERIAL_PORT

Require native serial-port support.

WEBCPP_COBALT_REQUIRE_REVERSE_DNS

Require reverse name lookup, unavailable in the WASI/browser adapters.

WEBCPP_COBALT_REQUIRE_PIPE_CREATION

Require guest-created asynchronous pipes with transfer, cancellation and EOF support. WASIp2 has no guest pipe creation; the Emscripten lifecycle is not supported.

WEBCPP_COBALT_REQUIRE_POSIX_STDIO

Require native POSIX descriptors for asynchronous stdio. SDK 34’s WASI stdio descriptors do not provide nonblocking mode.

WEBCPP_COBALT_REQUIRE_POLLABLE_STDIO

Require Asio’s explicit WASIp2 pollable stdio adapter, usable with Cobalt’s completion tokens.

WEBCPP_ASIO_DEFAULT_MAX_HANDLERS_PER_TURN

Asio’s shared browser scheduling default, 100; compile the runner with the same value. It is a handler-count budget, not a time limit.

The corresponding HAS_SOCKET_BACKEND, HAS_OPENSSL_BACKEND, HAS_THREADS, HAS_LOCAL_SOCKETS, HAS_SIGNALS, HAS_SERIAL_PORT and HAS_REVERSE_DNS observations use the WEBCPP_COBALT_ prefix. HAS_BROWSER_BRIDGE, HAS_BROWSER_WORKERS and HAS_HOST_DNS distinguish JavaScript integration, pthread hosting and forward lookup. Internal BACKEND_* macros are not public configuration controls.

In a browser build, including io.hpp, io/acceptor.hpp, io/socket.hpp, io/stream_socket.hpp or io/datagram_socket.hpp requests a raw socket facility and produces a targeted diagnostic. Include only the coroutine headers needed by a browser HTTP/WebSocket client and use Beast’s host transport adapter. The same socket headers select the guest transport on native and WASIp2/P3.

Keep Boost’s build-wide Cobalt controls when selecting executor and memory policies: BOOST_COBALT_USE_IO_CONTEXT, BOOST_COBALT_CUSTOM_EXECUTOR, BOOST_COBALT_USE_STD_PMR, BOOST_COBALT_USE_BOOST_CONTAINER_PMR, BOOST_COBALT_USE_CUSTOM_PMR and BOOST_COBALT_NO_PMR. Native sources read them directly; Wasm configuration forwards them to the shipped implementation. The defaults are the type-erased Asio executor and standard-library PMR. Choose one executor policy and one PMR policy. Rebuild the complete core, runner, optional SSL and application with matching definitions; changing only one translation unit violates the library’s configuration contract.

Custom executor and PMR declarations follow Boost’s customization convention: supply boost::cobalt::executor or boost::cobalt::pmr in a configuration header included before Cobalt in every source. For Wasm, the executor must belong to the selected WebCPP Asio backend. A custom PMR implementation or Boost.Container PMR also brings its own explicit dependencies. Source-archive consumers cover the default policy, io_context plus no-PMR, and an application-declared context executor with counting PMR, using direct compilation and CMake. These witnesses do not certify arbitrary custom executor/resource implementations.

Conflicting executor or PMR selections in one translation unit produce a configuration error. There is no general linker guard for arbitrary configuration differences between separately compiled translation units or prebuilt archives. The consumer recipe applies one common configuration target to the application, core, runner and SSL. Its dependency audit rejects a compiled source missing the requested policy. Rebuild all of them when changing policy; an existing archive cannot acquire a different ABI just by defining a macro in the application.

HAS_PIPE_CREATION, HAS_POSIX_STDIO and HAS_POLLABLE_STDIO are separate observations. Receiving a host-provided stream does not imply that the guest can create a pipe. Use WEBCPP_COBALT_FOR from async_for.hpp for asynchronous range iteration; it forwards to the selected coroutine backend.

Emscripten 6.0.11 does not provide the complete pipe lifecycle. A Node test confirms byte transfer and pending-read cancellation through Cobalt. A separate pipe_eof_sdk_limitation probe calls only libc: after closing the last writer, poll reports POLLIN|POLLHUP, but an empty nonblocking read returns EAGAIN instead of EOF. This SDK limitation leaves HAS_PIPE_CREATION at zero; the passing negative probe is not lifecycle support or browser evidence. The probe fails if the SDK behavior changes, requiring the capability to be re-evaluated. Native and WASIp3 continue to test closure of the final writer through Cobalt. Native Windows retains Boost.Asio’s broken_pipe error for that read; native POSIX and WASIp3 report eof. In each case no further bytes are returned.

Exceptions and errors

Both exception modes remain selectable. The build warns about Boost.Cobalt issue 287: moving some pending coroutine objects with libc++ and exceptions disabled can abort. This is an upstream limitation, not a claim that every use of std::move fails. The warning is informational; it does not enable exceptions or make the operation safe. Use the versioned reproducer when evaluating another compiler/runtime. The native runtime tests keep Apple Clang’s known missing-promise-member diagnostic visible with -Wno-error=coroutine-missing-unhandled-exception for their no-exceptions consumers. This test-local setting is not exported by the library targets; external strict builds must account for the upstream diagnostic described in Differences.

Native MSVC rejects co_main with exceptions disabled because Boost 1.92’s main_promise omits unhandled_exception. The test suite classifies that specific configuration as an upstream compile limitation, paired with the same coroutine compiling with exceptions enabled and a no-exceptions witness for the missing promise member. This does not disable other no-exceptions consumers or change the native Boost type. Use exceptions for native MSVC co_main applications.

Testing

The migration remains under local validation. The current Original applications and environment counterparts records each original application and its available counterparts against the shipped implementation. Historical Asio/Cobalt results do not certify the new source layout. The independent whole-candidate review and its correction reviews accompany the local lint gate. Remote CI has separate evidence; a local review is not a remote CI verdict.

Native identity preserves Boost 1.92 defects outside the corrected SSL wrapper. The upstream-limitations lane records precise failures for composed accept and composition cancellation. Its output says UPSTREAM-LIMITATION; a passing negative probe means the limitation was reproduced, not that cancellation works. An unexpected exit, diagnostic or newly fixed upstream behavior fails the probe and requires the compatibility record to be revisited.

The finite echo counterpart uses accept(socket&), which forwards cancellation directly to the pending accept. It avoids Boost 1.92’s composed accept limitation without changing native types or sources. Its TCP driver checks concurrent traffic, EOF, cancellation before any connection, cancellation with a live session, peer reset after a confirmed echo and invalid arguments. Both cancellation cases require the server to finish normally and report its exact session and byte counts.

The affected owned coroutine tests scope GCC 14’s allocation false-positive diagnostic to their coroutine functions. The immutable upstream HTTP and ticker compile probes instead keep that warning visible with -Wno-error=mismatched-new-delete, only for their GCC 14 targets. Other warnings remain errors, and neither setting is a library usage requirement. See Differences for the upstream explanation.

The immutable upstream ticker declares a local msg that shadows its msg parameter. MSVC diagnoses that valid source with C4457 under /W4; /WX then rejects the compile probe. Only original_ticker selects /wd4457 on MSVC. The source remains byte-identical, other warnings remain errors, and this option is not exported to library consumers or other test programs. That same MSVC probe uses /bigobj: its template-heavy Debug translation unit exceeds the default COFF section limit (C1128). This changes the object-file format limit, not the source, runtime behavior or warning policy.

The tests distinguish immutable upstream programs, namespace-only migrations and behavioral counterparts. test/applications/upstream retains original hashes; test/applications/prepare.py produces the separately identified namespace migrations. A missing host facility is documented or diagnosed, never replaced by an empty successful program.

The spsc-wakeup lane checks only the await_ready/await_suspend lost-wakeup window. The adaptation closes that window but retains the original queue’s delayed-notification race: a notification can resume a writer after its free slot has already been reused, and a failed push is ignored. The spsc-sequence lane is a deterministic limitation probe, with the immutable original on native and the unchanged counterpart on native, Emscripten and WASIp3. Passing means the known value loss was reproduced, not that concurrent transfer is reliable. The browser workbench marks SPSC unavailable and does not start it. A native failure in the original does not establish support for a Wasm backend.

Native SSL has compile-time type-identity tests for both header orders, plus runtime client, handshake-state, transfer-cancellation and shutdown tests against real local peers. The same TLS 1.2/1.3 state tests run on WASIp2/P3. A native CMake consumer also compiles the complete source inventory and runs those tests from a copied source snapshot without B2, Git or replacement Boost headers.

The Cobalt-owned tls-integration lane runs the SSL client, state and cancellation fixtures in native single/multi-thread profiles with exceptions on/off, WASIp3 single-thread profiles with exceptions on/off, and WASIp3 cooperative threads with exceptions off. It reuses the shared real TLS peer driver and builds each Cobalt source directly, keeping the test report under Cobalt ownership. Native MSVC single-thread fixtures select the static CRT so the provider uses its no-threads configuration. The existing tls lane retains its native, WASIp2 and WASIp3 coverage.

The SSL client also checks move construction, socket identity and cancellation after destroying the source, both before and after handshake completion.

Browser examples keep cancellation state in the owning module instance, with a scoped C++ registration. Duplicate registration cannot replace an active run; normal completion and exception unwinding remove it. Browser tests also call the exported cancellation function after completion and require a zero result.

The state cases cover STARTTLS, a buffered ClientHello, state observed at await time, trust rejection, malformed CA data, hostname verification and SNI. Transfer cancellation covers primitive reads/writes and complete-buffer operations with partial progress. The peer applies backpressure; only an actual operation_aborted satisfies a cancellation case. A completion that wins the race requires a fresh connection and a bounded retry, rather than being counted as cancellation. An outer watchdog catches lost completion.

Shutdown tests first wait until the peer observes close_notify. The peer then either closes without its own TLS shutdown, producing stream_truncated, or holds the connection while the coroutine requests cancellation, producing operation_aborted. Both cases must clear secure(), block application I/O and reject a second shutdown. Elapsed time alone is not proof of a pending operation.

The worker lifecycle test receives a posted readiness notification after the worker has started its asynchronous timer wait. Its five-second deadline still bounds the test; it is not a general worker-latency guarantee or a change to the SDK’s timer polling.

The inventory pins all twelve Cobalt 1.92 applications. Native core types are Boost types; Wasm uses the shipped WebCPP backend. Every cell below names the actual target, thread/exception setting and host. Browser page and dedicated worker observations are separate from Node.

Release measurements of the shipped implementation

These local measurements compare Boost-backed native interfaces with the shipped Wasm implementation on one machine. They are not a cross-machine performance guarantee. See the raw environment, commands, hashes and samples accompanying the tables.

Sizes cover -O2, -O3, -Os and -Oz, each with full LTO off/on. Runtime comparisons use -O3 without LTO across every feasible profile. All builds use Release and NDEBUG. EH-on uses -fwasm-exceptions for JSPI/WASI and -fexceptions for Asyncify in this toolchain. Those comparisons include the selected exception code generation, not suspension alone. The workload executable contains seven finite matched workloads, not an unchanged upstream application. The baseline contains only an empty runner. Browser payload is JavaScript plus Wasm; native is a Mach-O executable. Runtime installations and native system shared libraries are outside these payload sizes.

All 136 optimization/profile builds also execute the empty runner and seven short checked workloads for both libraries: 2,176 payload qualification runs in native, Node or Wasmtime. They validate the size artifacts; their timings are excluded from the performance tables. Real-browser measurements and correctness observations below remain separate.

Single/multi are B2 threading properties. Native single does not disable Boost threads; Wasm multi selects the thread-capable SDK profile. Each workload runs one context on one execution thread. This is not a multicore throughput comparison. P3 threads are cooperative.

Build time is one forced rebuild of six programs per setting with three compiler jobs and a warmed SDK cache. No other build/test from this session ran concurrently; other user and OS activity is not controlled. A single build is an observation, not a timing distribution.

Interpreting the native comparison

Every workload constructs a channel and timer before its loop, including the post-only loop. The initialized reactor remains part of that context. On this macOS/Boost combination, the native scheduler polls kqueue between posted completions. Therefore the ratios compare these initialized-reactor applications, not the intrinsic cost of an isolated coroutine or post. They must not be generalized to Linux, Windows, or a context that never initializes I/O. The native Cobalt runner also registers POSIX signals, unlike its WASI runner.

A separate diagnostic uses unmodified Boost and changes only whether it constructs an idle timer before 10,000 checked posts. Five pairs observed 59.5-98.9 ns/post without that timer and 10.50-12.15 us/post with it. This supports the initialized-reactor explanation for the large native post/channel ratios. It is a boundary check with fixed order and no discarded warmup, not a replacement statistical benchmark. Its source, command and output are retained as native-reactor-control files beside the results; the immutable source snapshot is .cpp.txt. Copy it to the recorded .cpp path before replaying that historical command. The main samples are unchanged.

Runtime and memory scope

Each operation is one completed iteration: post resumes once; immediate sends then receives in a buffered Asio channel; channel transfers one value through an unbuffered channel; parallel joins one Asio-channel send/receive pair; allocation performs five posts and five arena allocations; timer awaits a zero-expiry timer; http parses one complete in-memory HTTP response. Asio uses parallel_group and Cobalt uses join for paired operations. HTTP does not measure network or TLS latency. Every iteration contributes to a checked checksum.

Thirty fresh executions per workload/profile use frozen common operation counts and an in-process warmup. The report records median, p95, min/max and a bootstrap 95% interval for the median. Ten baseline starts measure fresh process/page startup. The browser process is retained; each page/worker is new, with no-store HTTP. OS and engine caches are not cleared, so these are not cold-machine or empty-code-cache measurements. The explicit buffered loader measures fetch, compile and instantiate separately; it does not represent the default streaming loader.

Three instrumented executions describe C++ allocation counts/requested bytes and Cobalt frame PMR requests. Those nested counters must not be added. Direct C malloc and JavaScript allocations are outside their scope. Wasm linear memory is capacity, not live heap. Process RSS includes Node/Wasmtime; browser-module RSS/CPU are unavailable. Instrumentation timing is retained only as a diagnostic, not a comparative performance claim.

Guarantees

  1. Native core coroutine and plain I/O types retain their Boost.Cobalt identity. The corrected SSL wrapper is the documented exception.

  2. Consumer builds use shipped source files and explicit dependencies. They do not patch Boost or select replacement Boost include trees.

  3. The browser runner uses Asio’s configured handler limit. This limit is checked between handlers, not inside a running handler.

  4. A failed or cancelled handshake on the corrected SSL stream prevents subsequent application I/O from falling back to plaintext.

Appendix A: Differences

On native targets, task, promise, generator, completion tokens and plain I/O types are Boost.Cobalt types. The upstream native implementation and runner sources remain byte-identical. One WebCPP translation unit checks the Boost version while compiling the core; it adds no runtime behavior. This preserves native interoperability; it also preserves upstream limitations outside the separately corrected SSL wrapper.

With Boost 1.92, the native limitation probes cover cancellation not reaching composed accept or composed waits. Further native checks reproduced with cleanup instantiation failures and a write_at constraint expecting write_op instead of write_at_op. Apple Clang 21 also diagnoses the original main and thread promises’ missing unhandled_exception members when compiling without exceptions; with warnings treated as errors, that consumer fails to compile. MSVC rejects the no-exceptions co_main with error C2039 for the same missing member; the limitation probes preserve a control with exceptions enabled and verify the promise shape. These are not new native guarantees supplied by WebCPP. The Wasm implementation carries its documented corrections, including the positioned-write constraint.

GCC 15.2 has a compiler regression for await_suspend with additional default arguments, including Cobalt’s race. It can fail with an internal compiler error in make_decl_rtl even in a program using only Boost.Cobalt. Use GCC 15.3 or a compiler containing the fix for GCC PR121643. The CI provisions GCC 15.3 and verifies this coroutine pattern before the suite; it does not patch the native Cobalt headers or skip the affected applications.

GCC 14 can emit -Wmismatched-new-delete for the upstream coroutine frame allocator. The maintainer identifies this as a false positive in Boost.Cobalt issue 7. Strict builds that promote this warning to an error fail even though allocation and release use the same stored memory resource. This compiler diagnostic is distinct from the no-exceptions runtime limitation in issue 287. WebCPP does not change native allocation or export a warning suppression to consumers. For an affected strict build, scope the diagnostic adjustment to the coroutine functions or translation units that reproduce it, rather than disabling allocation diagnostics globally.

The original io::udp_v6 constant also selects ICMP rather than UDP. Native identity preserves that defect. Use an explicit static protocol with the same IPv6 family and datagram type but the UDP protocol value; the udp_v6 regression records the original mismatch and exchanges datagrams with that control. The shipped Wasm backend corrects io::udp_v6 itself.

After the final writer closes a native Windows pipe, Boost.Asio reports broken_pipe rather than eof on the next empty read. The native Cobalt pipe retains that error and returns zero bytes. See Asio issue 1442. Native POSIX and WASIp3 tests require eof; none of these paths rewrites the native error.

WebCPP fixes Boost.Cobalt 1.92 SSL wrapper defects on native and WASIp2/P3. The owner approved this native exception on 2026-11-06 and retained it on 2026-11-07. webcpp::cobalt::io::ssl::stream is a distinct, corrected type; its native SSL context and plain Asio dependencies retain Boost identity. These are Cobalt wrapper fixes, not changes to OpenSSL’s cryptographic implementation or to native Cobalt’s core and runner.

The original handshake completion did not update the stream’s TLS state. Consequently, a successful handshake could leave secure() false, subsequent I/O selecting plain TCP and shutdown() returning no_protocol_option. Lazy handshake/shutdown operations also captured state at construction instead of checking it when awaited. The fix updates the stream before resuming the coroutine and checks its current state when an operation starts.

The original wrapper also allowed application I/O to select plain TCP after a failed or cancelled handshake. The fix records the first TLS attempt and blocks that fallback with not_connected and zero transferred bytes. Shutdown completion clears the TLS state even on error or cancellation. The precise state and retry contract is in SSL handshake and stream state; successful negotiation still does not replace the application’s trust and hostname verification settings.

Native complete-buffer SSL read/write overloads also fix lost cancellation by using Asio’s composed operations with the completion handler’s associated properties. This correction requires the concrete SSL type as explained in Preserve the corrected native SSL composition. Erasing it to Boost’s generic I/O stream still selects the unchanged upstream composition.

Move construction rebinds socket access to the destination’s SSL lowest layer and preserves handshake state, fixing the socket facade’s reference to the moved-from object. Copying and assignment are unavailable. Move only when no lazy or outstanding operation retains either stream’s address; moving does not transfer those operation references. After moving, the source is non-secure and may be destroyed. Tests destroy the source before handshake and after completed successful or rejected handshakes, then exercise the destination.

The TLS 1.2/1.3 regression fixtures are test/tls/cobalt_ssl_client.cpp, cobalt_ssl_state.cpp and cobalt_ssl_cancel.cpp: they check real peers, state transitions, blocked application I/O, moves, transfer cancellation and shutdown. The native identity fixtures check both header orders. See Testing for the lanes and their exception/threading profiles. These wrapper fixes do not repair the other native Boost limitations described above.

On Wasm, library-owned headers and sources select the same shipped Asio backend as WebCPP Beast. Corrections include the browser runner, WASI networking and SSL state machine, and aligned storage handling. The importer verifies original and corrected inputs and output hashes; application builds do not execute it. See upstream/README.md and its manifests for provenance.

In the browser, the runner and the checked task runner yield between bounded turns, with Asio’s default of 100 handlers. A long-running individual handler still blocks its thread. JSPI delegates suspension to the engine; Asyncify uses instrumented Wasm. Availability, stack requirements and performance are separate from Cobalt’s coroutine semantics.

An upstream example depending on a native signal, Unix socket, filesystem, blocking thread or TCP listener may require an explicit host counterpart. The matrix identifies that adaptation instead of promising identical facilities in a browser. A browser WebSocket or fetch operation uses host TLS and security policy rather than the guest OpenSSL wrapper.
