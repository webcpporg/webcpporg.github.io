xactor is a header-only, deterministic actor system for C++20, one of the libraries of webcpp. Its actors handle one message at a time, on one thread, in an order that depends only on the order the messages were sent; every execution is paid from a budget of fuel; and time is a number the host brings.

This page teaches xactor concept by concept: why each exists, its smallest example, its variations and its rules. Every program it shows was compiled and run, natively and, but for the program built on Boost.Asio, for wasm32-wasip2 and wasm32-wasip3, and printed the output shown under it. The reference that closes it lists every name the headers declare.

Introduction

An actor is an independent object that reaches others only by messages: it has its own state, which only it changes, in response to a message it receives, and it handles one message at a time. So each actor can be understood on its own, and tested by the messages it takes and sends. xactor runs actors in that model, and promises a program what it can build on:

  • The same input makes the same run. The actors run on one thread, the host’s, and the order in which they receive their messages depends only on the order the messages were sent. Two runs of the same deliveries, under any of xactor’s drivers, deliver the same messages in the same order, and record the same envelope log to prove it.

  • Every execution ends. All the work that one message from the host causes is an execution, and an execution has a budget of fuel, from which every message its actors send is paid. No chain or storm of messages runs forever.

  • Time is the host’s. xactor reads no clock. An actor that must act later arms a timer, which fires when the host brings a time that reaches it, so a run with timers is as repeatable as one without.

The behaviour of an actor is C++ code. It can be dynamic, a class whose handle decides at run time what each message does, or static, a state machine compiled into the program, here with Boost.MSM (Static actors). A library can build on xactor too: webcpp’s xstate builds its actor layer on it.

Requirements

  • A C++20 compiler. xactor’s tests and examples are built and run natively, and for wasm32-wasip2 and wasm32-wasip3 with the Clang of wasi-sdk, under wasmtime (Testing).

  • Boost’s headers, 1.92 or newer. xactor uses Boost.System, for result and the error codes, and, outside a WASI build, Boost.Asio, for its Asio driver. It is header-only, and nothing of Boost is compiled for it.

  • webcpp’s configuration, config, whose <webcpp/config.hpp> every header of xactor includes first. It is header-only too.

  • Without exceptions, a definition of boost::throw_exception. xactor throws no exception of its own: it is built and tested with exceptions on, on every target, and its headers compile without them. Whether a program uses them is its own choice. Without them, Boost.System’s result still names boost::throw_exception, and the program defines it (Quick start). A program built with exceptions needs nothing here, since Boost defines the function then.

  • Nothing else: no threads, no clock, and no global or static mutable state.

Quick start

This program has two actors. A counter asks an echo for the numbers 1, 2 and 3, one message each. The echo answers each with the same number, and once the counter has its three answers, it finishes with their sum. The host, the code around the actors, creates both, sends the counter one message, and runs the actors until no message is left.

The program begins with xactor’s header and an alias for its namespace:

#include <webcpp/xactor.hpp>

#include <cstddef>
#include <iostream>
#include <variant>

namespace xactor = webcpp::xactor;

The messages are plain structs, and the message type of the actors is one std::variant of all of them. Every type of xactor that carries a message is a template over that variant:

struct start {};

struct ask {
    int value = 0;
};

struct answer {
    int value = 0;
};

struct total {
    int value = 0;
};

using message = std::variant<start, ask, answer, total>;

What an actor does is its logic: a class derived from xactor::actor_logic<message>, whose one handle is called with one message at a time. The message arrives in an envelope, cause, which holds it as cause.payload, and everything the actor does to other actors it does through its turn, turn. The echo replies to whoever asked. The counter is created with the echo’s actor_ref, the name of the actor it asks; on start it sends three asks, and it adds up the answers until it has three, when it finishes with the total:

/** Answers every ask with the same number. */
class echo final : public xactor::actor_logic<message> {
public:
    xactor::result<void> handle(xactor::turn<message>& turn,
                                const xactor::envelope<message>& cause) override {
        if (const auto* asked = std::get_if<ask>(&cause.payload)) {
            return turn.reply(answer{.value = asked->value});
        }
        return {};
    }
};

/** Asks the echo for 1, 2 and 3, and finishes with the sum of the answers. */
class counter final : public xactor::actor_logic<message> {
public:
    explicit counter(xactor::actor_ref echo) : echo_(echo) {}

    xactor::result<void> handle(xactor::turn<message>& turn,
                                const xactor::envelope<message>& cause) override {
        if (std::holds_alternative<start>(cause.payload)) {
            for (int value = 1; value <= 3; ++value) {
                const xactor::result<void> sent = turn.send(echo_, ask{.value = value});
                if (!sent.has_value()) {
                    return sent;
                }
            }
            return {};
        }
        if (const auto* answered = std::get_if<answer>(&cause.payload)) {
            sum_ += answered->value;
            ++answers_;
            if (answers_ == 3) {
                return turn.finish(total{.value = sum_});
            }
        }
        return {};
    }

private:
    xactor::actor_ref echo_;
    int sum_ = 0;
    int answers_ = 0;
};

The host creates a scheduler, the system that holds the actors, with a budget of 100 units of fuel for each execution. It creates the two actors with create_actor, which constructs a logic from the arguments after the scheduler and returns the new actor’s actor_ref. It delivers start to the counter in execution 1, and runs a fifo_driver until no message is left. Then it reads what the counter finished with, and the fuel execution 1 has left:

xactor::scheduler<message> system(xactor::budgets{.fuel = 100});
const xactor::result<xactor::actor_ref> echoing = xactor::create_actor<echo>(system);
if (!echoing.has_value()) {
    return 1;
}
const xactor::result<xactor::actor_ref> counting =
    xactor::create_actor<counter>(system, *echoing);
if (!counting.has_value()) {
    return 1;
}

const xactor::correlation_id execution{.value = 1};
if (!system.deliver(*counting, start{}, execution).has_value()) {
    return 1;
}
xactor::fifo_driver<message> driver(system);
const xactor::result<std::size_t> delivered = driver.run_until_idle(nullptr);
if (!delivered.has_value()) {
    return 1;
}

const message* output = system.output_of(*counting);
if (output == nullptr) {
    return 1;
}
std::cout << "delivered " << *delivered << " messages\n";
std::cout << "total " << std::get<total>(*output).value << ", fuel left "
          << system.fuel_of(execution) << '\n';

It prints:

delivered 7 messages
total 6, fuel left 94

Seven messages were delivered: the host’s start, three asks and three answers. Each ask the counter sent and each answer the echo replied cost one unit of fuel, and the host’s start cost nothing, so execution 1 has 94 of its 100 units left. Every call that can fail returns a result, and the program checks each one: xactor reports a failure as a value, and throws no exception of its own (guarantee 20).

Building it

xactor needs Boost’s headers and webcpp’s configuration, libs/config, and nothing compiled. From the root of a webcpp checkout, with the program copied as quick_start.cpp, this command builds it:

clang++ -std=c++20 -I libs/xactor/include -I libs/config/include quick_start.cpp \
    -o quick_start

A compiler that does not find Boost on its default include path is given Boost’s include directory with -isystem: for Homebrew’s Boost, the one under /opt/homebrew/opt/boost. Without exceptions, the program also needs a definition of boost::throw_exception, which Boost.System’s result names: webcpp’s tools/throw_exception.cpp reports what was thrown on the standard error and aborts, since in such a build a throw is a defect, never a condition.

clang++ -std=c++20 -fno-exceptions -DBOOST_NO_EXCEPTIONS -I libs/xactor/include \
    -I libs/config/include quick_start.cpp tools/throw_exception.cpp -o quick_start

In the checkout, b2 libs/xactor/example builds and runs this program with every other program of libs/xactor/example/, and compares what each prints with the output this page shows (Testing). A b2 project uses xactor through /webcpp/xactor//xactor, which adds xactor’s headers and Boost’s to whatever names it.

The model

A program writes two things, its messages and the logic of its actors, and xactor provides the rest:

Messages

One closed std::variant of plain structs, the program’s own. Closed means every message is known when the program is compiled: std::visit over it checks that every alternative is handled, and the scheduler’s log records which alternative arrived by its index(). Every type of xactor that carries a message is a template over this variant, and xactor asks nothing more of it than to be a std::variant that can be moved. A program may name the types it uses once, for instance using turn = xactor::turn<message>;.

Actor logic

What an actor does: a class with one handle, called with one message at a time (Writing an actor logic). It never sees the scheduler, its mailbox or the driver: all it does, it does through its turn, the object it is handed with each message (Turns).

Actor

A logic running in a scheduler, created by create_actor or by a turn’s spawn_child, and named by the actor_ref they return. An actor_ref holds the actor’s address, a number from 1 in the order the actors were created; 0 names no actor.

Scheduler

The system that holds the actors: one first-in first-out mailbox for each actor, and one first-in first-out queue of the actors that have messages waiting (The scheduler). Delivering a message only puts it in a mailbox.

Driver

What decides when turns happen: it hands queued messages to their actors until none is left, or until it has handed a given number (Drivers).

Execution

Everything that one delivery from the host causes, named by a correlation_id. Its fuel pays for all of it (Fuel).

A message travels in an envelope, xactor::envelope<message>, which is what a logic’s handle receives:

Field What it holds

to

The actor it is for.

from

The actor that sent it; the address 0 when the host did, and the actor itself for the message of one of its timers.

correlation

The execution it belongs to.

sequence

Its number in the order messages entered a mailbox: the scheduler numbers each one as it enqueues it.

payload

The message.

A run goes the same way every time. The host creates the actors and delivers a message, which waits in a mailbox. A driver then calls the scheduler’s run_one, which takes the actor at the front of the queue and hands it the first message of its mailbox: the actor’s handle runs with that message and its turn, and whatever the actor sends waits in another mailbox. When nothing is left, the host reads what the actors ended with.

Writing an actor logic

An actor logic is a class derived from xactor::actor_logic<Message> that overrides its one pure virtual function, handle, which takes the actor’s turn and the envelope of the message, and returns an xactor::result<void>, as the quick start’s echo and counter do (Quick start).

  • Its input. What the logic is constructed with is its input: create_actor<Logic>(system, inputs) and a turn’s spawn_child<Logic>(inputs) pass their arguments to the constructor of Logic. The quick start’s counter takes the echo’s actor_ref as its input.

  • Its state. Its members are the actor’s state, and only its own handle changes them: the counter’s sum and count of answers.

  • One message at a time. handle is called once for each message, and returns before the next is handed over. It reads the message from cause.payload, with std::get_if, std::holds_alternative or std::visit.

  • Owned by the scheduler. A logic can be neither copied nor moved: once it runs, the scheduler owns it and never moves it.

  • Errors end it. A handle that returns an error ends its actor with the status error, and the scheduler keeps the error for error_of. The rest of the system goes on: every other actor keeps its turns, and the driver’s run goes on. A handler may return any boost::system::error_code, of xactor’s category or of its own; the scheduler keeps it as it is.

Every call of xactor that can fail returns an xactor::result<T>, Boost.System’s result with an error_code, and changes nothing when it fails. A logic checks the result of each call: it returns a failure to end its actor with it, as the quick start’s counter does with a failed send, or it goes on, as the relay of Fuel does. xactor::failure<T>(code) builds a failed result<T>. xactor’s own codes are xactor::errc values, of the category webcpp.xactor, and their message() is their name:

Code When

errc::invalid_argument

A null logic given to spawn; an address that names no actor, given to deliver, send, stop or status_of; a reply to a message from the host; a turn’s finish or stop once its actor has ended, a second finish among them; a stop_child of an actor that is not the caller’s child; a wake_at or a spawn_child once the actor has ended.

errc::resource_limit

A send, reply, wake_at or spend that the execution’s fuel cannot pay (Fuel).

The scheduler

xactor::scheduler<Message> holds the actors and hands them their messages. It is built with its budgets, whose fuel is the fuel of each execution, a million units by default. Each actor has a first-in first-out mailbox, and the actors with messages waiting wait in one first-in first-out queue, each at most once. run_one takes the actor at the front of the queue, hands it the first message of its mailbox, and puts it back at the end of the queue while its mailbox holds more. So no actor keeps the others waiting however much it sends itself, and the order of deliveries depends on nothing but the order in which messages were enqueued. Nothing in xactor starts a thread: the scheduler and its actors live on the thread that calls them, the host’s.

The quick start’s host shows the calls a host makes most (Quick start):

Turns

A turn is one delivery: the scheduler calls an actor’s handle with one message and an xactor::turn<Message>, and the turn is everything the actor may do to the system while it handles that message. The logic never sees the scheduler, so every effect goes through the turn, which knows the actor that is acting and the execution the message belongs to: a message the actor sends carries it as its sender, and is paid from the fuel of that execution.

The turn lives for one handle. It holds references to the scheduler and to the message, so a logic never keeps it, nor a reference into the message.

The quick start’s logics use some of these calls (Quick start): the counter sends its asks with send and ends with finish, and the echo answers with reply, so it never needs to know who asked. The sections that follow show the others at work: spend and fuel in Fuel, wake_at, cancel_timer and now in Timers, and spawn_child in Lifecycle.

The rules of a turn:

  • A send is queued. A message sent waits in its target’s mailbox, and its target handles it in a turn of its own, later, in the order of the queue; nothing an actor sends runs inside its own handle.

  • A reply needs a sender. A message from the host has none, and a reply to it is invalid_argument.

  • Every call that can fail returns a result, and changes nothing when it fails. The logic returns the failure to end its actor with it, or goes on.

  • An address must name an actor. A send to an address that names no actor is invalid_argument, and nothing is paid. A send to an actor that has ended is paid, and the message is dropped, as every message to an actor that has ended is (Lifecycle).

  • The rest of the turn runs after finish or stop. The actor receives nothing more, and in the rest of that turn it can still send, but a wake_at or a spawn_child is invalid_argument, and nothing is paid or constructed.

Fuel

Every message belongs to an execution, named by a correlation_id. A delivery from the host opens its execution, and every message that delivery causes, directly or through any number of actors, belongs to the same one. An execution has one reservoir of fuel, the fuel of the scheduler’s budgets, and every actor in it pays from that reservoir: one unit for each message it sends and each timer it arms, and the units it declares for its own work.

Fuel exists so that the total work of an execution is bounded, whatever shape its messages take: a chain of messages, a fan-out, two actors that answer each other forever, or an actor that computes a lot and sends little. A host that runs actors it does not trust, or that must answer within a budget, knows that every delivery it makes ends.

The smallest example is an actor that sends itself a message on every turn, for as long as the execution can pay, and prints the fuel left at the start of each turn:

/** Sends itself a hop on every turn, for as long as the execution can pay. */
class relay final : public xactor::actor_logic<message> {
public:
    xactor::result<void> handle(xactor::turn<message>& turn,
                                const xactor::envelope<message>& /*cause*/) override {
        std::cout << "relay: fuel " << turn.fuel() << '\n';
        const xactor::result<void> sent = turn.send(turn.self(), hop{});
        if (!sent.has_value()) {
            std::cout << "relay: refused, " << sent.error().message() << '\n';
        }
        return {};
    }
};

With a budget of 3, the host delivers start in execution 1:

xactor::scheduler<message> system(xactor::budgets{.fuel = 3});
const xactor::result<xactor::actor_ref> relaying = xactor::create_actor<relay>(system);
if (!relaying.has_value()) {
    return 1;
}
const xactor::correlation_id first{.value = 1};
if (!system.deliver(*relaying, start{}, first).has_value()) {
    return 1;
}
xactor::fifo_driver<message> driver(system);
const xactor::result<std::size_t> delivered = driver.run_until_idle(nullptr);
if (!delivered.has_value()) {
    return 1;
}
std::cout << "delivered " << *delivered << ", relay is "
          << spelling(system.status_of(*relaying).value()) << '\n';

spelling, a helper of the program, writes a status as its name. It prints:

relay: fuel 3
relay: fuel 2
relay: fuel 1
relay: fuel 0
relay: refused, resource_limit

The host’s start costs nothing, so the relay’s first turn sees all 3 units. Each send takes one, so the fourth turn finds none: its send fails with resource_limit, nothing is sent, and the run ends after four deliveries. A refusal is a value the logic decides about. The relay prints it and returns success, so it stays active, ready for the next execution.

A second delivery with another correlation opens a second execution, with fuel of its own:

const xactor::correlation_id second{.value = 2};

    return 1;
}
const xactor::result<std::size_t> again = driver.run_until_idle(nullptr);
if (!again.has_value()) {
    return 1;
}
std::cout << "execution 1 has " << system.fuel_of(first) << " left, execution 2 has "
          << system.fuel_of(second) << " left\n";

It prints:

relay: fuel 2
relay: fuel 1

A host gives each input a correlation of its own.

An actor that computes without sending declares what its work costs with spend, so that it is bounded too. This worker pays 2 units on every turn, then sends itself a message, and returns a refusal instead of ignoring it:

/** Pays 2 units for its own work on every turn, then sends itself a hop. */
class worker final : public xactor::actor_logic<message> {
public:
    xactor::result<void> handle(xactor::turn<message>& turn,
                                const xactor::envelope<message>& /*cause*/) override {
        const xactor::result<void> paid = turn.spend(2);
        if (!paid.has_value()) {
            return paid;
        }
        return turn.send(turn.self(), hop{});
    }
};
const xactor::result<xactor::actor_ref> working = xactor::create_actor<worker>(system);
if (!working.has_value()) {
    return 1;
}
const xactor::correlation_id third{.value = 3};
if (!system.deliver(*working, start{}, third).has_value()) {
    return 1;
}
const xactor::result<std::size_t> worked = driver.run_until_idle(nullptr);
if (!worked.has_value()) {
    return 1;
}
std::cout << "worker is " << spelling(system.status_of(*working).value()) << " ("
          << system.error_of(*working).message() << "), execution 3 has "
          << system.fuel_of(third) << " left\n";

It prints:

worker is error (resource_limit), execution 3 has 0 left

The first turn spends 2 of the 3 units and sends with the last one. The second turn’s spend(2) finds none, and fails with resource_limit; the worker returns the failure, which ends it with the status error, and error_of keeps the code.

The rules of fuel:

  • What costs. Inside a turn, send and reply cost one unit, wake_at, with a key or without, one unit, and spend(n) n units, all from the execution of the message being handled. spawn_child, stop_child, stop, finish, cancel_timer, self, parent, now and fuel cost nothing, and so does a delivery from the host.

  • All or nothing. What the execution cannot pay fails with resource_limit and changes nothing: no message is enqueued, no timer armed, no unit spent. spend takes all its units or none, and a keyed wake_at that is refused leaves the timer under its key as it was.

  • Opening an execution. The first deliver, clock_tick or release_next of a correlation opens its execution with the whole budget. A timer that a tick releases belongs to the tick’s execution, and releasing it costs nothing, since arming it was paid (Timers).

  • Reading it. turn.fuel() is the fuel the execution of the message being handled has left, and the scheduler’s fuel_of(correlation) the same from outside; for an execution not yet opened, fuel_of is the whole budget.

Timers

An actor that must act later arms a timer: turn.wake_at(deadline, message) keeps the message until the host’s time reaches deadline, then puts it in the actor’s own mailbox. xactor never reads a clock. Time is a number the host brings, with the scheduler’s clock_tick or release_next, so a run with timers is as repeatable as one without, and a test moves time by any amount at once. The unit is the host’s to choose; the example counts milliseconds.

A kettle boils 100 ms after start and whistles 120 ms after it. Its boil is a keyed timer, under the key "boil": delay arms the boil again under the same key, which replaces the one start armed, and cancel removes it. A deadline is a time, so the kettle computes each from the time the host brought last, turn.now():

/** Boils 100 ms after start and whistles 120 ms after it; delay and cancel move the boil. */
class kettle final : public xactor::actor_logic<message> {
public:
    xactor::result<void> handle(xactor::turn<message>& turn,
                                const xactor::envelope<message>& cause) override {
        if (std::holds_alternative<start>(cause.payload)) {
            const xactor::result<void> armed = turn.wake_at(turn.now() + 100, boiled{}, "boil");
            if (!armed.has_value()) {
                return armed;
            }
            return turn.wake_at(turn.now() + 120, whistle{});
        }
        if (std::holds_alternative<delay>(cause.payload)) {
            // The same key: this timer replaces the one start armed.
            return turn.wake_at(turn.now() + 150, boiled{}, "boil");
        }
        if (std::holds_alternative<cancel>(cause.payload)) {
            turn.cancel_timer("boil");
            return {};
        }
        if (std::holds_alternative<boiled>(cause.payload)) {
            std::cout << "boiled at " << turn.now() << '\n';
            return {};
        }
        std::cout << "whistle at " << turn.now() << '\n';
        return {};
    }
};

The rules of timers:

  • Order. Due timers are released in the order of their deadlines, and timers with the same deadline in the order they were armed. A timer that replaces another is armed anew, and takes its place in that order from then.

  • Only the host moves time. No timer fires without a clock_tick or a release_next that reaches its deadline. now(), on the scheduler or the turn, is the time the last of them brought, 0 before any, so a delay becomes a deadline as turn.now() + delay.

  • Released into the tick’s execution. A released timer’s message belongs to the execution the host gave clock_tick or release_next, and releasing it costs nothing, since arming it was paid. Its envelope’s from is the actor itself.

  • Keys belong to their actor. wake_at with a key replaces this actor’s timer under that key, and cancel_timer(key) removes it, for free, and does nothing when there is none. Two actors may use the same key. A keyed wake_at that the execution cannot pay leaves the timer under its key as it was.

  • An ended actor has no timers. An actor that ends, done, error or stopped, loses its timers, and in the rest of the turn that ended it, its wake_at is invalid_argument, and nothing is paid.

  • Time can move back. A tick earlier than the last moves now back: it releases what is due by then, and a deadline computed afterwards from now is earlier than one computed before it. A host that wants time to move forward only never brings an earlier time.

Lifecycle

Every actor has a status, which status_of returns. It starts active, the one status in which it receives messages, and it ends in one of the others, each final:

The values are fixed and never reused, because a system that persists its actors rebuilds them from these numbers.

Actors form families. An actor spawned in a turn is a child of that turn’s actor: it records the actor as its parent, which turn.parent() returns, and the parent records its children in the order it spawned them. An actor the host created has no parent. A family is stopped together, from its parent or by the host, each actor after its own descendants, siblings in the order they were spawned.

In the example, a supervisor spawns three children, each of which ends differently or not at all:

/** Finishes with twice the value of its first work: it is then done, with an output. */
class doubler final : public xactor::actor_logic<message> {
public:
    xactor::result<void> handle(xactor::turn<message>& turn,
                                const xactor::envelope<message>& cause) override {
        if (const auto* asked = std::get_if<work>(&cause.payload)) {
            return turn.finish(answer{.value = asked->value * 2});
        }
        return {};
    }
};

/** Fails on its first work: it returns an error, and ends with the status error. */
class failing final : public xactor::actor_logic<message> {
public:
    xactor::result<void> handle(xactor::turn<message>& /*turn*/,
                                const xactor::envelope<message>& cause) override {
        if (std::holds_alternative<work>(cause.payload)) {
            return xactor::failure<void>(xactor::errc::invalid_argument);
        }
        return {};
    }
};

/** Waits for work and never ends by itself. */
class idle final : public xactor::actor_logic<message> {
public:
    xactor::result<void> handle(xactor::turn<message>& /*turn*/,
                                const xactor::envelope<message>& /*cause*/) override {
        return {};
    }
};

On start, the supervisor spawns them, in this order, and gives each work:

/** On start, spawns a doubler, a failing child and an idle one, and gives each work. */
class supervisor final : public xactor::actor_logic<message> {
public:
    xactor::result<void> handle(xactor::turn<message>& turn,
                                const xactor::envelope<message>& cause) override {
        if (!std::holds_alternative<start>(cause.payload)) {
            return {};
        }
        const xactor::result<xactor::actor_ref> first = turn.spawn_child<doubler>();
        if (!first.has_value()) {
            return {boost::system::in_place_error, first.error()};
        }
        const xactor::result<xactor::actor_ref> second = turn.spawn_child<failing>();
        if (!second.has_value()) {
            return {boost::system::in_place_error, second.error()};
        }
        const xactor::result<xactor::actor_ref> third = turn.spawn_child<idle>();
        if (!third.has_value()) {
            return {boost::system::in_place_error, third.error()};
        }
        for (const xactor::actor_ref child : {*first, *second, *third}) {
            const xactor::result<void> sent = turn.send(child, work{.value = 21});
            if (!sent.has_value()) {
                return sent;
            }
        }
        return {};
    }
};

The rules of the lifecycle:

  • Only an active actor receives messages. Once an actor has ended, its pending messages are dropped, never delivered and never logged, and so is every later message to it. Dropping is not an error of the sender’s, which cannot know the actor has ended.

  • An actor finishes once. finish(output) makes it done and keeps the output; a second finish is invalid_argument and changes nothing. output_of is nullptr unless the actor is done, and error_of is empty unless it is error.

  • An actor ends in one way. An error that handle returns in the turn that finished or stopped its actor changes nothing: the actor stays as it ended.

  • Stopping a child stops its family. turn.stop_child(child) stops child and every actor descended from it that is still active, in the family’s order, and returns them in that order; their mailboxes and timers are dropped. A member that had already ended stays as it ended, and its descendants are stopped all the same. It is invalid_argument for anything but a child of the caller: the caller itself, a grandchild, an address that names no actor. The host’s stop(actor) does the same for any actor.

  • Ending alone. turn.stop() ends the actor handling the message as stopped, alone. An actor that finishes, fails or stops itself leaves its children running: they are its logic’s to stop, with stop_child, before it ends.

  • An ended actor creates nothing. In the rest of the turn that ended it, an actor spawns no child and arms no timer: spawn_child and wake_at are invalid_argument, and spawn_child constructs nothing. It can still send.

Drivers

The scheduler decides what a turn is, and a driver decides when turns happen: it calls the scheduler’s run_one until no message is left, or until it has delivered as many as its host allows. So the same actors run under a plain loop in a program, one message at a time in a test, or as handlers on a Boost.Asio strand, and every driver delivers the same messages in the same order. xactor’s drivers are these:

Driver For What it does

fifo_driver

A program, native or WASI

run_until_idle(log) delivers until no message is left, and returns how many it delivered. run_turn(n, log) delivers at most n, for a host that takes the thread back between turns.

test_driver

A test

step() and step(log) deliver exactly one message, and return whether there was one. It has nothing else.

asio_driver

A native program that runs its turns as Asio handlers

run_until_idle(log), the same turns posted onto one strand of an io_context the driver owns. A WASI build leaves it out.

A driver is built over one scheduler, which it holds by reference. The log of run_until_idle and run_turn is an xactor::envelope_log*, and nullptr records nothing; test_driver takes an envelope_log& in step(log), and records nothing in step().

The example plays a rally between two players. A serve from the host tells a player whom to serve to, and each player returns the ball until the rally reaches 4:

/** Returns the ball until the rally reaches 4. */
class player final : public xactor::actor_logic<message> {
public:
    xactor::result<void> handle(xactor::turn<message>& turn,
                                const xactor::envelope<message>& cause) override {
        if (const auto* served = std::get_if<serve>(&cause.payload)) {
            return turn.send(served->to, ball{.rally = 1});
        }
        const int rally = std::get<ball>(cause.payload).rally;
        if (rally == 4) {
            return {};
        }
        return turn.reply(ball{.rally = rally + 1});
    }
};

The envelope log

The envelope log is the evidence that two runs, or two drivers, delivered the same messages the same way. run_one records an entry for every message it delivers, before the actor handles it, and nothing for a message that is dropped:

Member of logged_envelope What it holds

sequence

The message’s sequence number.

to, from

Its receiver, and its sender, 0 for the host.

correlation

Its execution.

remaining_fuel

The fuel its execution had when it was delivered.

payload_index

Which alternative of the message variant it was, its index().

The log keeps which alternative arrived, not the message, so every entry has the same size and two logs compare cheaply, with ==. entries() returns them in order. Two schedulers built with the same budgets and fed the same deliveries record equal logs, whatever driver runs them.

The Asio driver

asio_driver delivers the same turns on Boost.Asio, natively: the turns run as handlers on a strand of an io_context the driver owns, on the thread that calls run_until_idle. The context is the driver’s alone: it offers no executor, so the program’s own I/O objects run on a context of their own, never on the driver’s. The driver posts each run_one onto the strand and drains the context with poll, which runs what is ready and returns. It never calls the context’s run, run_one or run_for, which would wait for more work, so a turn never blocks.

This program runs the rally of the example above with a fifo_driver, and again with an asio_driver; it repeats the players and set_up of that example, as a program of its own:

    return 1;
}

          << '\n';

Static actors

A static actor is an actor whose behaviour is a state machine compiled into the program: its states, its events and its transitions are C++ types and expressions, checked by the compiler and fixed when the program is built. It suits behaviour known when the program is written. The compiler checks its table, and nothing is read or interpreted at run time; in exchange, a change to the machine is a change to the program, and the machine cannot come from a file or a request.

xactor holds no adapter for a state machine library, and needs none. An actor logic is any class with a handle, so a logic holds a machine as a member and hands each message to it, and the machine’s actions reach the system through the turn. The program joins them with an event type that carries the turn and a handle of a few lines, and nothing else. Nothing in xactor knows the library, and the library does not know xactor, so any library whose machines take typed events joins the same way. This section writes one machine with Boost.MSM, one of Boost’s libraries.

The machine does not receive the message alone. It receives an on<Event>, which holds the message and the turn it arrived in, both by reference:

/** What the machine receives for a message: the message, and the turn it arrived in. */
template <class Event>
struct on {
    const Event& event;
    xactor::turn<message>& turn;
};

An action takes the turn from its event, so it can reply, send, finish or arm a timer as any logic does, paid from the right execution. The on<Event> is built inside handle and lives for one call of the machine, so its references never outlive the turn.

The machine is a turnstile, the first machine of many state machine tutorials. It starts locked. A coin unlocks it, and a push goes through and locks it again. A push while it is locked sounds an alarm, and a coin while it is unlocked is refunded: the turnstile replies alarm or refund to the actor that pushed or paid. A visitor puts a coin in, pushes twice and puts two coins in, all in one turn, and prints what comes back:

/** Puts a coin in, pushes twice, and puts two coins in; prints what comes back. */
class visitor final : public xactor::actor_logic<message> {
public:
    xactor::result<void> handle(xactor::turn<message>& turn,
                                const xactor::envelope<message>& cause) override {
        if (const auto* visiting = std::get_if<visit>(&cause.payload)) {
            const std::array<message, 5> plan{coin{}, push{}, push{}, coin{}, coin{}};
            for (const message& sent : plan) {
                const xactor::result<void> delivered = turn.send(visiting->turnstile, sent);
                if (!delivered.has_value()) {
                    return delivered;
                }
            }
            return {};
        }
        if (std::holds_alternative<alarm>(cause.payload)) {
            std::cout << "visitor: alarm\n";
        }
        if (std::holds_alternative<refund>(cause.payload)) {
            std::cout << "visitor: refund\n";
        }
        return {};
    }
};

    return 1;
}

         .has_value()) {
    return 1;
}

The first coin, the first push and the second coin take it to unlocked, back to locked and to unlocked again. The second push and the last coin change no state, and enter none: they are answered with alarm and refund. The visitor hears the alarm after the turnstile’s last unlocked, because the alarm joined the queue behind the turnstile, which still had messages waiting, and the scheduler serves the actors with messages in turn (The scheduler).

The machine, with Boost.MSM

The program uses MSM’s classic back-end, msm::back::state_machine, and its functor front-end, whose rows are types in a Boost.MPL vector:

MSM writes a machine as a front-end, a struct derived from msm::front::state_machine_def of itself, which holds the states, the table and the machine’s data:

/** Replies alarm to a push the turnstile does not let through. */
struct sound_alarm {
    template <class Machine, class Source, class Target>
    void operator()(const on<push>& received, Machine& machine, Source& /*source*/,
                    Target& /*target*/) {
        machine.outcome = received.turn.reply(alarm{});
    }
};

/** Replies refund to a coin the turnstile does not need. */
struct give_refund {
    template <class Machine, class Source, class Target>
    void operator()(const on<coin>& received, Machine& machine, Source& /*source*/,
                    Target& /*target*/) {
        machine.outcome = received.turn.reply(refund{});
    }
};

/** A turnstile: a coin unlocks it, a push goes through and locks it again. */
struct turnstile_chart : msm::front::state_machine_def<turnstile_chart> {
    struct locked : msm::front::state<> {
        template <class Event, class Machine>
        void on_entry(const Event& /*event*/, Machine& /*machine*/) {
            std::cout << "turnstile: locked\n";
        }
    };

    struct unlocked : msm::front::state<> {
        template <class Event, class Machine>
        void on_entry(const Event& /*event*/, Machine& /*machine*/) {
            std::cout << "turnstile: unlocked\n";
        }
    };

    using initial_state = locked;
    using none = msm::front::none;

    // clang-format off
    struct transition_table : mpl::vector<
        msm::front::Row<locked,   on<coin>, unlocked, none,        none>,
        msm::front::Row<locked,   on<push>, none,     sound_alarm, none>,
        msm::front::Row<unlocked, on<push>, locked,   none,        none>,
        msm::front::Row<unlocked, on<coin>, none,     give_refund, none>
    > {};
    // clang-format on

    /** A message the turnstile has no transition for is ignored. */
    template <class Machine, class Event>
    void no_transition(const Event& /*event*/, Machine& /*machine*/, int /*state*/) {}

    xactor::result<void> outcome;
};

Each state is a struct derived from msm::front::state<>, here with an on_entry, and initial_state names the first. Each row of transition_table is a Row<Source, Event, Target, Action, Guard>. none as its target makes an internal transition, which runs its action and leaves the state as it is, entering nothing: a push while the turnstile is locked sounds the alarm, and it stays locked. none as its action or its guard means there is none. An action is a functor, called with the event, the machine, the source state and the target state. The machine is the back-end, which derives from the front-end, so machine.outcome is the chart’s own member, into which sound_alarm and give_refund write the result of their reply. The table is kept one row per line, between clang-format off and on.

For an event the current state has no row for, MSM calls the front-end’s no_transition, and the default one asserts, which would stop the program, where assertions are on, on a message the actor does not take. The chart defines one that ignores the message.

The logic holds the back-end, an msm::back::state_machine of the turnstile_chart, and hands it each message:

/** A static actor: its behaviour is the turnstile's MSM machine, fixed when it is compiled. */
class turnstile final : public xactor::actor_logic<message> {
public:
    turnstile() { machine_.start(); }

    xactor::result<void> handle(xactor::turn<message>& turn,
                                const xactor::envelope<message>& cause) override {
        machine_.outcome = {};
        std::visit(
            [&](const auto& received) {
                machine_.process_event(
                    on<std::decay_t<decltype(received)>>{.event = received, .turn = turn});
            },
            cause.payload);
        return machine_.outcome;
    }

private:
    msm::back::state_machine<turnstile_chart> machine_;
};

An MSM machine enters its initial state when start() is called, so the logic’s constructor calls it, and the turnstile prints locked when create_actor constructs it. handle clears the outcome, visits the message, wraps the alternative it holds in an on<> with the turn, hands it to process_event, and returns the outcome: a reply that fails ends the actor with its error, as a failed send ends any logic that returns it.

Getting Boost.MSM

Boost.MSM is used through its headers alone, which a Boost installation has beside Boost’s other headers, so the program needs nothing more than xactor does. Neither xactor nor a program needs b2’s target for the library, /boost/msm//boost_msm, and neither uses it: it brings every library MSM depends on, Boost.Serialization among them, which is compiled.

The program is built and run natively, for wasm32-wasip2 and for wasm32-wasip3, with exceptions, and the machine needs none: a user’s build without them, exception-handling=off, runs it as well.

Rules that keep a run deterministic

xactor guarantees the order of a run. One first-in first-out mailbox for each actor and one first-in first-out queue of actors make the order of deliveries depend on the order of the messages alone, under every driver; fuel bounds every execution; and time moves only when the host brings it. xactor itself reads no clock, no disk and no network, blocks in no turn, keeps no static mutable state, so that two schedulers in one process are independent, and throws no exception of its own. Two schedulers built with the same budgets and fed the same deliveries record equal envelope logs (The envelope log).

An actor can still break that guarantee, by letting something other than its messages decide what it does. These rules keep it from doing so:

  • Read no clock in a turn. Take the time from turn.now(), or from the message a timer brings (Timers).

  • Read nothing from the world in a turn, and never wait. The host reads a file or the network, and delivers what it read as a message. A turn that waits holds up every actor, since they all run on one thread. Writing out, as the examples print, decides nothing, and is safe.

  • Draw no random number but from a seed that a message brought.

  • Keep no static mutable state. Two schedulers in one process must stay independent, as xactor’s own are.

  • Throw nothing, and return an error instead. xactor catches nothing: an exception thrown by a handle leaves run_one and the driver in the middle of the run, where an error returned ends one actor and the run goes on (Writing an actor logic).

  • Keep no reference to the turn or to a message beyond the turn. Both are gone once handle returns; copy what is needed.

A program checks that its run is deterministic by running the same deliveries twice, recording both runs and comparing the envelope logs, as xactor’s own tests compare its drivers (Testing).

Testing

A test of actors checks that, from a known start and given some messages, they reach the statuses and the outputs they should, and send what they should. A test is worth its checks only when the run it checks is the same every time, and in xactor nothing in a run depends on the world outside the test:

  • There is no real clock. A timer waits on the host’s time, and only the test moves it, by any amount at once (Timers).

  • There is no thread. The test’s driver hands over each message, and returns when it has (Drivers).

  • A failure is a value. A call of xactor that fails returns its error, and an actor whose handle fails ends with the status error, where the test reads the code (Writing an actor logic).

  • Work is counted. A test that gives an execution little fuel sees what its actors are refused when it runs out (Fuel).

This chapter shows how a program tests its actors, and then how xactor itself is tested, on every target it supports.

Testing a program’s actors

The test below checks an echo and the client that asks it, with Boost.Core’s lightweight_test, the framework of one header that xactor’s own tests use. It begins with xactor’s header and the framework’s:

#include <webcpp/xactor.hpp>

#include <boost/core/lightweight_test.hpp>

#include <cstdint>
#include <variant>
#include <vector>

namespace xactor = webcpp::xactor;

The echo replies to every ask with the same number, and the client asks it for the number its start names, and keeps each answer in a vector the test owns, which it is constructed with, so that the test reads what the client received:

/** Answers every ask with the same number. */
class echo final : public xactor::actor_logic<message> {
public:
    xactor::result<void> handle(xactor::turn<message>& turn,
                                const xactor::envelope<message>& cause) override {
        if (const auto* asked = std::get_if<ask>(&cause.payload)) {
            return turn.reply(answer{.value = asked->value});
        }
        return {};
    }
};

/** Asks the echo for the number a start names, and keeps each answer where the test reads it. */
class client final : public xactor::actor_logic<message> {
public:
    client(xactor::actor_ref echo, std::vector<int>& answers) : echo_(echo), answers_(answers) {}

    xactor::result<void> handle(xactor::turn<message>& turn,
                                const xactor::envelope<message>& cause) override {
        if (const auto* started = std::get_if<start>(&cause.payload)) {
            return turn.send(echo_, ask{.value = started->value});
        }
        if (const auto* answered = std::get_if<answer>(&cause.payload)) {
            answers_.push_back(answered->value);
        }
        return {};
    }

private:
    xactor::actor_ref echo_;
    std::vector<int>& answers_;
};

The first test case drives the actors with a test_driver, one message a step. After each step it checks what that message changed: the fuel of the execution, which each message an actor sends takes a unit of, and the answers the client kept. BOOST_TEST returns whether its check held, so the case stops where a check it cannot go on without fails:

/** Whether one step of the driver delivered a message. */
bool stepped(xactor::test_driver<message>& driver) {
    const xactor::result<bool> step = driver.step();
    return step.has_value() && *step;
}

/** One message a step: after each, the test checks what that message changed. */
void the_client_keeps_what_the_echo_answers() {
    std::vector<int> answers;
    xactor::scheduler<message> system(xactor::budgets{.fuel = 10});
    const xactor::result<xactor::actor_ref> echoing = xactor::create_actor<echo>(system);
    if (!BOOST_TEST(echoing.has_value())) {
        return;
    }
    const xactor::result<xactor::actor_ref> asking =
        xactor::create_actor<client>(system, *echoing, answers);
    if (!BOOST_TEST(asking.has_value())) {
        return;
    }
    const xactor::correlation_id execution{.value = 1};
    if (!BOOST_TEST(system.deliver(*asking, start{.value = 7}, execution).has_value())) {
        return;
    }

    xactor::test_driver<message> driver(system);
    BOOST_TEST(stepped(driver));  // The client handles start, and asks.
    BOOST_TEST_EQ(system.fuel_of(execution), 9U);
    BOOST_TEST(stepped(driver));  // The echo handles the ask, and answers.
    BOOST_TEST_EQ(system.fuel_of(execution), 8U);
    BOOST_TEST(answers.empty());
    BOOST_TEST(stepped(driver));  // The client handles the answer, and keeps it.
    BOOST_TEST(answers == std::vector<int>{7});
    const xactor::result<bool> last = driver.step();  // Nothing is left, and nothing failed.
    BOOST_TEST(last.has_value() && !*last);
    BOOST_TEST(system.idle());
}

The second runs the same deliveries twice, records each run in an envelope log, and checks that the two logs are equal, as every pair of runs of the same deliveries must be (The envelope log):

/** Runs the client and the echo on one start for each of `numbers`, and returns their log. */
xactor::envelope_log run(const std::vector<int>& numbers) {
    std::vector<int> answers;
    xactor::envelope_log log;
    xactor::scheduler<message> system(xactor::budgets{.fuel = 10});
    const xactor::result<xactor::actor_ref> echoing = xactor::create_actor<echo>(system);
    if (!BOOST_TEST(echoing.has_value())) {
        return log;
    }
    const xactor::result<xactor::actor_ref> asking =
        xactor::create_actor<client>(system, *echoing, answers);
    if (!BOOST_TEST(asking.has_value())) {
        return log;
    }
    std::uint64_t correlation = 0;
    for (const int number : numbers) {
        ++correlation;
        const xactor::correlation_id execution{.value = correlation};
        BOOST_TEST(system.deliver(*asking, start{.value = number}, execution).has_value());
    }
    xactor::fifo_driver<message> driver(system);
    BOOST_TEST(driver.run_until_idle(&log).has_value());
    return log;
}

/** Two runs of the same deliveries record equal envelope logs. */
void two_runs_record_the_same_log() {
    const xactor::envelope_log first = run({1, 2, 3});
    const xactor::envelope_log second = run({1, 2, 3});
    BOOST_TEST_EQ(first.entries().size(), 9U);
    BOOST_TEST(first == second);
}

main calls the cases and returns boost::report_errors(), the program’s status:

the_client_keeps_what_the_echo_answers();
two_runs_record_the_same_log();
return boost::report_errors();

When every check holds, the program prints No errors detected. on its standard error, nothing on its standard output, and returns 0. A check that fails prints its expression, its values, its file and its line on the standard error, and main returns 1. Built without exceptions, the program links a definition of boost::throw_exception, as any program does (Building it).

Guarantees

What xactor promises whatever its caller does: the rules its results keep, which the sections above teach and the tests check. A guarantee keeps its number, and the anchor named after it, so a comment of the code or of a test cites it by that anchor: (doc: #xactor-invariant-13) sends its reader to the thirteenth guarantee. b2 libs/xactor/doc, which builds this page, fails on a citation that names no anchor of it.

The scheduler, its turns, its drivers and its log:

  1. The messages of one mailbox are handled in the order they were enqueued.

  2. run_one takes the actor at the front of the queue and puts it back at the end while its mailbox is not empty, so delivery is first-in first-out across actors too.

  3. An actor is in the queue at most once.

  4. run_one handles exactly one message, and returns false only when the scheduler is idle. A handler that returns an error ends its actor with the status error and keeps the error for error_of, unless its turn had already ended the actor, which then stays as it ended; run_one still returns true, and every other actor keeps its turns.

  5. deliver, send, reply and a released timer put an active target actor in the queue when it is not there; a message to an actor that has ended is dropped (guarantee 23).

  6. Each correlation_id names one execution. The first deliver, clock_tick or release_next that names it opens it with budgets.fuel, and nothing refills it: a later delivery with the same correlation shares what it has left. A delivery from the host costs no fuel.

  7. Inside a turn, send and reply cost one unit, wake_at, with a key or without, one unit and spend(n) n units, all from the execution of the message being handled; spawn_child, stop_child, stop, finish, cancel_timer, self, parent, now and fuel cost nothing.

  8. What the execution cannot pay fails with resource_limit and changes nothing: nothing is enqueued, armed or spent, and a keyed wake_at leaves the timer under its key armed. spend takes all its units or none.

  9. turn::fuel is the fuel the execution of the message being handled has left; scheduler::fuel_of the same from outside, and the whole budget for an execution not yet opened.

  10. reply sends to the sender of the message being handled, in its execution. A message from the host has no sender, and a reply to it is invalid_argument, as a send to an address that names no actor is; neither is paid.

  11. Timers fire only for a deadline at or before the time the host brought, in (deadline, arming order) order. A timer replaced, cancelled or dropped never fires; a replacement takes a new arming order.

  12. No timer fires without a clock_tick or a release_next that reaches its deadline: time never advances by itself.

  13. A timer released by a clock_tick or a release_next belongs to that call’s execution, and its message’s sender is its own actor; releasing it costs nothing, since arming it was paid.

  14. run_until_idle returns only when idle() is true, and run_turn(n) handles at most n messages.

  15. fifo_driver and asio_driver produce identical envelope logs for the same deliveries.

  16. An envelope log given to run_one records {sequence, to, from, correlation, the fuel the execution had when the message was delivered, payload index} for every message delivered, before its actor handles it, and nothing for a dropped one.

  17. Two schedulers built with the same budgets and fed the same deliveries produce identical envelope logs.

  18. xactor reads no clock, no disk and no network.

  19. No turn blocks: nothing calls io_context::run, run_one or run_for.

  20. xactor throws no exception of its own: every operation that can fail returns a result, and the library compiles without exceptions, which the lint checks for every public header and for every test and example, which instantiate its templates. Where exceptions are on, an operation that allocates, such as spawn, deliver, send, wake_at or the log’s record, can still throw std::bad_alloc, as a standard container does.

  21. There is no static mutable state: two schedulers in one process are independent.

  22. test_driver exposes step, exactly one run_one, with or without a log, and nothing else; messages reach its scheduler through deliver.

  23. A spawned actor is active. Only an active actor receives messages: once it is done, error or stopped, its pending messages are dropped, and every later message to it is dropped too, never delivered and never logged. Dropping is not an error of the sender’s: a send to an actor that has ended succeeds, and is paid.

  24. finish(output) makes the actor handling the message done and keeps the output for output_of. An actor ends once: a finish once it has ended, a second finish or one after stop(), fails with invalid_argument and changes nothing.

  25. stop stops an actor and its family as stop_child does (guarantee 31) and returns the actors it stopped; an ended one stays as it ended.

  26. output_of is nullptr unless the status is done; error_of is empty unless the status is error.

  27. The values of status never change: active 1, done 2, error 3, stopped 4.

  28. The library names no message, id or error of any user. It asks of Message only that it be a std::variant that can be moved, whose index() the log records.

  29. create_actor<Logic>(system, inputs...) and a turn’s spawn_child<Logic>(inputs...) construct a Logic from inputs and run it as a new, active actor of the same system, returning its actor_ref; spawn does the same for a logic already constructed, and refuses a null one with invalid_argument. A turn of an actor that has ended refuses spawn_child before it constructs anything.

  30. A child spawned in a turn records the actor of that turn as its parent, and the parent records its children in spawn order; turn::parent returns the parent, and nothing for an actor the host spawned. turn::self is the actor handling the message.

  31. turn::stop_child(child) stops child and every actor descended from it that is still active, each after its own descendants, siblings in spawn order, and returns them in that order; their mailboxes and timers are dropped, and a member that had already ended stays as it ended while its descendants are still stopped. It is invalid_argument for anything but a child of the caller (the caller itself, a grandchild, an address that names no actor), which changes nothing. The caller is never in the family.

  32. wake_at(deadline, message, key) replaces the same actor’s timer under key; cancel_timer(key) removes it; keys belong to their actor.

  33. An actor that ends, done, error or stopped, loses its timers, and an actor that is no longer active, in the rest of the turn that ended it, arms no timer and spawns no child: wake_at and spawn_child are invalid_argument and nothing is paid. send still works.

  34. now() is the time the last clock_tick or release_next brought, 0 before any; next_deadline() the earliest deadline armed, none while no timer is. A tick earlier than the last moves now back: it releases what is due by then, and a deadline computed afterwards from now is earlier than one computed before it.

  35. turn::stop() ends the actor handling the message as stopped, alone: its children are its logic’s to stop, as after finish. It costs nothing, the rest of the turn runs as after finish, and a stop() once the actor has ended, a second one or one after finish, is invalid_argument.

  36. release_next(now, correlation) moves time to now and releases the first timer due by then, as clock_tick would release it, and says whether there was one; a host that runs the system between two releases lets a timer’s handling cancel or replace a later one of the same tick.

webcpp::xactor::scheduler

The system that holds the actors and gives each of them one message at a time, run by its host.

Synopsis

Declared in <webcpp/xactor/scheduler.hpp>

template<class Message>
class scheduler;

Description

Each actor has a FIFO mailbox, and the actors with messages waiting wait in one FIFO queue, each at most once: run_one takes the actor at the front, hands it the first message of its mailbox, and puts it back at the end while its mailbox holds more. A message an actor sends waits in a mailbox, and is never handled inside the sender’s turn. The scheduler keeps each actor’s logic, status, output, error and family for as long as it lives. It starts no thread and reads no clock: its time is what the host brings.

Note

One FIFO mailbox per actor and one FIFO queue of actors with work make the delivery order a function of the enqueue order alone, which is what makes a run deterministic and lets two drivers produce one log. Fuel is kept per execution: every message caused by one host delivery, whatever actor sends it, is paid from that delivery’s execution.

Appendix A: Glossary

The terms this page uses, in alphabetical order. Each entry says what the term means here, what it is in the code, and which section explains it.

Actor

An independent object that reaches others only by messages: it has its own state, which only it changes, and it handles one message at a time, from its mailbox. In xactor, an actor is a logic running in a scheduler, at an address, a number from 1 in the order the actors were created.

In the code: an xactor::actor_ref, which create_actor, the scheduler’s spawn and a turn’s spawn_child return.
See The model.

Actor logic

What an actor does, apart from the actor that runs it: a class with one handle, called with one message at a time and the turn it arrived in, through which it does everything it does. It never sees the scheduler, its mailbox or the driver. Its members are the actor’s state, and only its own handle changes them.

In the code: a class derived from xactor’s actor_logic<Message>, whose handle takes the turn and the envelope and returns an xactor::result<void>.
See Writing an actor logic.

Driver

What decides when turns happen: it hands the queued messages to their actors, one per turn, until none is left, or until it has handed as many as its host allows. Every driver delivers the same messages in the same order; they differ in who holds the thread.

In the code: fifo_driver for a program, test_driver for a test, one message per step(), and asio_driver for a native program that runs its turns as Boost.Asio handlers; each calls the scheduler’s run_one.
See Drivers.

Envelope

A message as xactor carries it, and as an actor logic receives it: the actor it is for, the actor that sent it, the execution it belongs to, its sequence number, in the order messages entered a mailbox, and the message itself.

In the code: xactor::envelope<Message> (to, from, correlation, sequence, payload); from is the address 0 for the host.
See The model.

Envelope log

The record of the messages a run delivered, one entry for each, written before the actor handles it. It keeps which alternative of the message variant arrived, not the message, so two logs compare cheaply: two schedulers built with the same budgets and fed the same deliveries record equal logs, whatever driver runs them.

In the code: xactor::envelope_log, given to run_one or to a driver, whose entries() are each a logged_envelope (sequence, to, from, correlation, remaining_fuel, payload_index).
See The envelope log.

Execution

Everything one input from the host causes: the messages and the timers that follow from it, through any number of actors, paid from one reservoir of fuel. A delivery or a tick from the host opens one, and every message it causes belongs to it.

In the code: an execution named by an xactor::correlation_id, whose fuel the scheduler’s fuel_of(correlation) tells.
See Fuel.

Fuel

The units an execution pays its work with: one for each message its actors send and each timer they arm, and the units they declare for their own work. An execution starts with the whole budget and is never refilled, so its work is bounded, whatever shape its messages take; what it cannot pay is refused, and changes nothing.

In the code: xactor::budgets::fuel, turn.fuel(), turn.spend(units) and errc::resource_limit.
See Fuel.

Guarantee

A rule xactor keeps whatever its caller does, under a number. A guarantee keeps its number and its anchor, and a comment of the code or of a test cites it by that anchor; the build of this page fails on a citation that names no anchor of it.

In the code: a comment of a test cites a guarantee by its anchor, the thirteenth as #xactor-invariant-13.
See Guarantees.

Host

The program around the actors: it creates them, delivers them messages, brings the time, runs a driver and reads what the actors ended with. A message from the host has no sender: its envelope’s from is the address 0.

In the code: the caller of create_actor and of the scheduler’s deliver, clock_tick, release_next, stop, status_of and output_of.
See Quick start.

Mailbox

Where an actor’s messages wait, in the order they were enqueued, until the actor has handled the one before: one first-in first-out queue for each actor, from which each turn of the actor takes one message.

In the code: a part of xactor::scheduler, which no logic sees.
See The scheduler.

Scheduler

The part of xactor that holds the actors and hands them their messages: one first-in first-out mailbox for each actor, and one first-in first-out queue of the actors that have messages waiting, each at most once. Each turn takes the actor at the front of the queue and hands it the first message of its mailbox, and the actor goes back to the end of the queue while its mailbox holds more. Delivering a message only puts it in a mailbox; a driver decides when turns happen.

In the code: xactor::scheduler<Message>, built with its budgets.
See The scheduler.

Static actor

An actor whose behaviour is a state machine compiled into the program: its states, events and transitions are C++ types and expressions, checked by the compiler and fixed when the program is built. An actor logic holds the machine as a member and hands each message to it, and the machine’s actions reach the system through the turn.

In the code: an actor logic over a Boost.MSM machine, whose events carry the message and the turn; xactor knows nothing of the library.
See Static actors.

Status

Whether an actor still receives messages: active, the one status in which it does, or done, error or stopped, each final.

In the code: xactor::status, which the scheduler’s status_of returns; its values are fixed and never reused.
See Lifecycle.

Timer

A message an actor arms for later, which comes back to the actor when the host’s time reaches its deadline. xactor reads no clock: the host brings the time.

In the code: turn.wake_at(deadline, message), with a key or without, turn.cancel_timer(key), and the scheduler’s clock_tick and release_next.
See Timers.

Turn

One delivery: the scheduler hands an actor one message, and the turn is everything the actor may do to the system while it handles that message. It sends and replies, spawns and stops its children, finishes or stops itself, arms and cancels timers and spends fuel, all through the turn, which knows the actor and the execution the message belongs to. A turn lives for one handle.

In the code: xactor::turn<Message>, handed to handle with the envelope.
See Turns.

What changed in xactor in each version of webcpp, newest first, one line per change. "Unreleased" is what the next version brings. The release notes of every version are on webcpp’s index page.

Unreleased

  • Breaking change: removed the guarantee that xactor runs without RTTI; build it with RTTI.

  • Changed the guarantee without exceptions to compiling only, which the lint checks.

  • Added the WEBCPP_XACTOR_NO_EXCEPTIONS configuration macro, defined automatically or by the developer.

  • Updated the documentation: a link to xstate, and a changelog appendix.

  • Changed config.hpp to include <webcpp/config.hpp>, webcpp’s configuration, which the build adds.
