webrtc is a header-only C++20 library of peer connections and data channels, one of the libraries of webcpp. Its types and operations carry the names and the shapes of the W3C’s WebRTC API, RTCPeerConnection and RTCDataChannel, and they are written in Asio’s model: every operation takes a completion token, runs its handler on the executor its object was made with, and fails as a value. Natively it runs over libdatachannel; in the browser, compiled with Emscripten, over the page’s own objects, so that a program is written once for both.

This page teaches webrtc section by section: two peers that talk, how a program builds with it, the runtime, signalling, the events, the data channels, the errors, cancellation and memory, what the native and the browser implementations stand on, how it differs from the W3C’s API, and what it guarantees. Every program it shows is one of the library’s examples, which the build compiles, runs and compares with the output shown. The reference lists every name the headers declare.

Overview

WebRTC connects two programs directly, through the networks between them, once each has told the other how to reach it. webrtc gives a C++ program the data-channel half of it: a peer_connection negotiates the connection with the other peer, and a data_channel carries messages over it, text or binary, reliable and ordered or not.

The names are the W3C’s, so that a reader who knows RTCPeerConnection.setLocalDescription() knows peer_connection::async_set_local_description, and the semantics are the W3C’s where a platform allows them, with every difference stated in Differences from the W3C’s API. The model is Asio’s:

  • every operation is an async_* member that takes any completion token, a callback, use_awaitable, use_future or a deferred token, and runs its handler on the object’s executor, webcpp::asio::any_io_executor unless the program chooses another;

  • what the W3C delivers as an event, a candidate, a state change, an incoming channel, a message, is a wait the program starts and starts again, as an acceptor’s async_accept (Events);

  • every failure is a value, an error_code of the category webcpp.webrtc or one of Asio’s (Errors), and every bound webcpp sets is a named option that fails as a value, never by throwing or blocking.

It runs on two targets, with exceptions on and off on both. Natively it runs over libdatachannel 0.24.6, which the superproject builds from its pinned sources (The native implementation). In the browser, compiled with Emscripten, it runs over the page’s own RTCPeerConnection and RTCDataChannel, through webcpp::asio’s bridge, in both of webcpp::asio’s suspension variants (The browser implementation). WASI has no WebRTC, neither in a guest nor from a host, so there the headers stop with an #error that says so.

Media, the tracks, codecs and transceivers of WebRTC, is not part of webrtc: it will get an interface of its own. Nor is any integration with another library: an actor of webcpp::xactor that needs a peer holds a peer_connection made on the executor its driver runs on and turns each completion into a message to itself.

Quick start

Two peers in one program open a data channel and exchange one message each way. A real program has its two peers in two processes, often on two machines, and carries what each says about itself to the other through a signalling channel of its own, a WebSocket or an HTTP request; these two hand it over directly, which is the only thing they do differently.

A program makes one runtime before any connection: natively it holds libdatachannel’s threads (The runtime). Each connection is made on an executor, whose handlers it runs; here both share one io_context. The configuration binds the connections to the loopback, so that the program needs no network:

asio::io_context io;
webrtc::runtime rt;  // libdatachannel's threads, made before any connection

// Host candidates on the loopback only, so that the example needs no network.
webrtc::configuration config;
config.bind_address = "127.0.0.1";

auto a = webrtc::peer_connection::make(rt, io.get_executor(), config).value();
auto b = webrtc::peer_connection::make(rt, io.get_executor(), config).value();

make returns a boost::system::result: a connection past the runtime’s cap, or a configuration the platform refuses, is an error, not an exception.

a creates a channel; b accepts it once the connection is up. Each side waits for what it needs, once: a waits for its channel to open and sends hello, then waits for an answer; b waits for the channel, then for a message, and answers it. Every handler runs on the io_context, and every one checks its error_code:

// a creates the channel; b accepts it once the connection is up.
auto chat = a.create_data_channel("chat").value();
std::optional<webrtc::data_channel> remote;
std::string at_a;
std::string at_b;
auto buffer_a = asio::dynamic_buffer(at_a);
auto buffer_b = asio::dynamic_buffer(at_b);

chat.async_wait_open([&](error_code ec) {
    if (ec) {
        return;
    }
    std::printf("a: the channel is open\n");
    if (const error_code sent = chat.send_text("hello"); sent) {
        std::printf("a: hello not sent: %s\n", sent.message().c_str());
        return;
    }
    chat.async_receive(buffer_a, [&](error_code ec, std::size_t, bool) {
        if (ec) {
            return;
        }
        std::printf("a received: %s\n", at_a.c_str());
        a.close();
        b.close();
    });
});
b.async_accept_data_channel([&](error_code ec, webrtc::data_channel dc) {
    if (ec) {
        return;
    }
    remote.emplace(std::move(dc));
    remote->async_receive(buffer_b, [&](error_code ec, std::size_t, bool text) {
        if (ec) {
            return;
        }
        std::printf("b received: %s (%s)\n", at_b.c_str(), text ? "text" : "binary");
        if (const error_code sent = remote->send_text("hi"); sent) {
            std::printf("b: hi not sent: %s\n", sent.message().c_str());
        }
    });
});

Then the signalling. a makes its offer, the implicit setLocalDescription() of the W3C, waits until it has gathered its candidates, the addresses b can reach it at, and gives b its local description, which by then holds them all; b answers the same way:

// a offers, b answers; each description goes over once its candidates are gathered.
void connect(webrtc::peer_connection& a, webrtc::peer_connection& b) {
    a.async_set_local_description([&](error_code ec, const webrtc::session_description&) {
        if (ec) {
            return;
        }
        gather(a, [&] {
            const auto offer = a.local_description().value();
            b.async_set_remote_description(offer.view(), [&](error_code ec) {
                if (ec) {
                    return;
                }
                b.async_set_local_description(
                    [&](error_code ec, const webrtc::session_description&) {
                        if (ec) {
                            return;
                        }
                        gather(b, [&] {
                            const auto answer = b.local_description().value();
                            a.async_set_remote_description(answer.view(), [](error_code ec) {
                                if (ec) {
                                    std::printf("a: the answer was refused: %s\n",
                                                ec.message().c_str());
                                }
                            });
                        });
                    });
            });
        });
    });
}

gather waits for candidates until the empty one, the end of gathering:

// Calls `done` once `pc` has gathered its candidates, whose end is an empty candidate: its local
// description then holds every one of them.
void gather(webrtc::peer_connection& pc, std::function<void()> done) {
    pc.async_wait_ice_candidate(
        [&pc, done = std::move(done)](error_code ec, const webrtc::ice_candidate& c) mutable {
            if (ec) {
                return;
            }
            if (c.candidate.empty()) {
                done();
            } else {
                gather(pc, std::move(done));
            }
        });
}

Waiting for every candidate before signalling is the simplest form of it. Signalling shows the other, which sends each candidate as soon as it is found, so that the connection starts sooner.

The program runs its io_context until both connections are closed, which a does once it has the answer; it gives up after thirty seconds, so that a broken network cannot hang it:

// Until both connections are closed, or the example gives up.
io.run_for(std::chrono::seconds(30));  // lint-run: the peers' events come from libdatachannel

It prints:

a: the channel is open
b received: hello (text)
a received: hi

Building a program

webrtc is header-only. A program inside a webcpp checkout names its target, /webcpp/webrtc//webrtc, which brings the headers, webcpp::config, webcpp::asio and, natively, libdatachannel:

alias webrtc : : <toolset>emscripten : : <library>headers <library>/webcpp/asio//asio ;
alias webrtc : : : : <library>headers <library>/webcpp/asio//asio
  <library>/webcpp/third_party//libdatachannel ;

Natively that target is /webcpp/third_party//libdatachannel: libdatachannel 0.24.6 with libjuice, libsrtp, usrsctp and plog, built by the superproject from the sources it pins, as static archives, with the program’s compiler and runtime settings, over the same source-built OpenSSL as webcpp::asio’s TLS. A first build makes them, and later builds reuse them. The submodule is initialized once:

git submodule update --init --recursive third_party/libs/libdatachannel
git submodule update --init third_party/libs/openssl

libdatachannel runs threads of its own, so a native program builds with threading=multi; a request for threading=single stops the build, naming the fix. webrtc works with exceptions on and off: natively it calls libdatachannel through its C API, which catches every exception libdatachannel throws and returns a code (exceptions), so a program built with exception-handling=off needs nothing more:

b2 threading=multi libs/webrtc/example
b2 threading=multi exception-handling=off libs/webrtc/example

In the browser the same target brings webcpp::asio, whose usage requirements link its browser runtime (the bridge’s export and JavaScript, which <webcpp/asio/browser/src.hpp> holds), embind and the flag of the suspension variant webcpp-suspend chooses, jspi or asyncify: a program built with b2 includes nothing more. A program built without b2 includes <webcpp/asio/browser/src.hpp> in exactly one translation unit and links with -lembind, -sJSPI (or -sASYNCIFY with JavaScript exceptions), -Wl,--export=emscripten_stack_get_current and -Wl,--export=_emscripten_stack_restore:

b2 toolset=emscripten webcpp-suspend=jspi libs/webrtc/test

The convenience header <webcpp/webrtc.hpp> includes every public header. <webcpp/webrtc/config.hpp> defines WEBCPP_WEBRTC_NO_EXCEPTIONS exactly when webcpp has no exceptions, as every webcpp library’s configuration does, and stops with #error on WASI, where no WebRTC exists.

The b2 feature webcpp-webrtc-unsupported=error|ignore, propagated, chooses what a setting a target cannot honour does: fail with operation_not_supported, the default, or be ignored where the platform does something equivalent of its own (Differences from the W3C’s API). Natively it decides a data channel’s max_packet_life_time of 0 (What the native target cannot honour), in the browser configuration::bind_address (What the browser cannot honour). On both targets the classes live in an inline namespace named after the policy, unsupported_error or unsupported_ignore, so their spelled names are the same, webcpp::webrtc::peer_connection among them, and two translation units built with different policies that pass an object between them fail to link instead of disagreeing at run time.

The runtime

Some of what WebRTC needs belongs to the whole process, or to the whole page: natively libdatachannel’s thread pool and global state, and on both targets the number of connections alive at once. webcpp keeps no global or static mutable state, so the program owns it, as a runtime:

  • it is made before any peer connection, and destroyed after the last connection and the last data channel: peer_connection::make takes it by reference, so no connection exists without one;

  • natively, making it loads libdatachannel’s global resources, with its thread pool of runtime_options::thread_pool_size threads when that is not 0, and destroying it waits until libdatachannel’s threads have stopped, for at most ten seconds, after which libdatachannel gives up and the program goes on;

  • it caps the connections alive at once at runtime_options::max_peer_connections, 256 by default, half of Chromium’s limit of 500 per page: make past the cap fails with too_many_peer_connections, and a connection’s place is given back once it is destroyed. peer_connections() says how many are alive.

Natively at most one runtime exists at a time in a process, because libdatachannel’s state is the process’s: a second runtime’s destructor would end the first one’s connections. It is a precondition, which the library does not check: a check would need a flag of the process, the static state webcpp keeps none of. A program makes its runtime in main, or in the one object that owns its connections, and passes it down; a test makes one per case, one case after another.

The connections made with one runtime may live on different executors and threads; its count is atomic. In the browser the cap counts the page’s census instead, every connection of the page until it is collected (The page’s census), and thread_pool_size means nothing.

Signalling

Two peers connect once each has the other’s session description, which says what they will exchange, and the other’s candidates, the addresses it may be reached at. Carrying them is the program’s: WebRTC leaves the signalling channel to it, a WebSocket, an HTTP request, a relay of its own. webrtc gives it the values to carry and the operations that apply them.

Descriptions

async_set_local_description() makes the local description and applies it, as the W3C’s setLocalDescription() without an argument: an offer, or an answer when a remote offer was applied. It completes with the description, a session_description whose type and sdp the program sends to the other peer, which applies it with async_set_remote_description(d.view()). The peer that offers sends first; the other answers once the offer is applied.

A description needs something to negotiate, so a peer creates its first data channel before it offers: the description then holds the connection’s data section, which every later channel shares. A channel created once the connection is up opens over it at once, on both peers, with no new offer or answer, as in a browser, where only a connection’s first channel needs negotiation. The W3C’s createOffer(), createAnswer() and negotiationneeded are not part of webrtc (Differences from the W3C’s API).

local_description() is the local description as it is now, with the candidates gathered so far; has_remote_description() says whether a remote one was applied.

Candidates

Applying a local description starts gathering candidates. async_wait_ice_candidate waits for the next one; the last, whose candidate is empty, is the end of gathering. A program either waits for the end and sends its local description, which then holds every candidate, as the quick start does, or sends each candidate as it comes, which lets the connection start sooner. The other peer adds each with async_add_ice_candidate(c.view()); an empty one ends the remote candidates and adds none.

A candidate needs the remote description first: one added before it fails with invalid_state, as in a browser. So a peer applies what it receives in the order it was sent, one operation at a time.

How to trickle candidates

Each peer’s end of the signalling channel is an inbox: what the other peer said, applied in order, the next operation started once the previous one has completed:

// What one peer says to the other: its description, or one of its candidates.
struct signalling_message {
    std::optional<webrtc::session_description> description;
    webrtc::ice_candidate candidate;
};

// One peer's end of the signalling channel: what the other peer said, applied in the order it was
// said, one operation at a time.
class inbox {
public:
    explicit inbox(webrtc::peer_connection& pc) : pc_(pc) {}

    // What to do once a remote description is applied.
    std::function<void()> on_description;

    // The signalling channel delivers a signal.
    void deliver(signalling_message s) {
        waiting_.push_back(std::move(s));
        if (!busy_) {
            next();
        }
    }

private:
    void next() {
        busy_ = !waiting_.empty();
        if (!busy_) {
            return;
        }
        const signalling_message s = std::move(waiting_.front());
        waiting_.pop_front();
        if (s.description) {
            pc_.async_set_remote_description(s.description->view(), [this](error_code ec) {
                if (ec) {
                    return;
                }
                on_description();
                next();
            });
        } else {
            pc_.async_add_ice_candidate(s.candidate.view(), [this](error_code ec) {
                if (!ec) {
                    next();
                }
            });
        }
    }

    webrtc::peer_connection& pc_;
    std::deque<signalling_message> waiting_;
    bool busy_ = false;
};

Each peer sends its candidates as it gathers them, the end included:

// Sends each candidate `from` gathers to `to` as soon as it is gathered, the end of gathering, an
// empty candidate, included.
void trickle(webrtc::peer_connection& from, inbox& to) {
    from.async_wait_ice_candidate([&from, &to](error_code ec, webrtc::ice_candidate c) {
        if (ec) {
            return;
        }
        const bool end = c.candidate.empty();
        to.deliver(signalling_message{.description = std::nullopt, .candidate = std::move(c)});
        if (!end) {
            trickle(from, to);
        }
    });
}

And each sends its description as soon as it has one, its candidates after it, so that the other peer’s inbox applies them in that order:

inbox at_a(a);
inbox at_b(b);
// b answers the offer once it is applied, then trickles its own candidates.
at_b.on_description = [&] {
    std::printf("b: the offer is applied\n");
    b.async_set_local_description([&](error_code ec, webrtc::session_description answer) {
        if (ec) {
            return;
        }
        at_a.deliver(signalling_message{.description = std::move(answer), .candidate = {}});
        trickle(b, at_a);
    });
};
at_a.on_description = [] { std::printf("a: the answer is applied\n"); };

// a offers, without waiting for its candidates, and trickles them after the offer.
a.async_set_local_description([&](error_code ec, webrtc::session_description offer) {
    if (ec) {
        return;
    }
    at_b.deliver(signalling_message{.description = std::move(offer), .candidate = {}});
    trickle(a, at_b);
});

The program waits until a is connected, then closes both connections. It prints:

b: the offer is applied
a: the answer is applied
a: connected

A real signalling channel carries the description’s type and sdp, and the candidate’s candidate, sdp_mid, sdp_m_line_index and username_fragment, as text or JSON of the program’s choosing; the values are the W3C’s RTCSessionDescriptionInit and RTCIceCandidateInit, so a peer in a browser reads them as they are.

While no wait is pending

An event can happen while the program has no wait of its kind pending, and each kind says what becomes of it, so that none is lost without a rule:

  • A state coalesces. A wait for a state change completes with the current state once it differs from the one the previous wait completed with, so a program that waits late sees the latest state, not every step to it.

  • Candidates queue up to options::max_queued_candidates, 64 by default, in order; past it a candidate is dropped from the queue and stays in local_description(). The end of gathering has a place of its own past the bound, so it is never dropped.

  • Incoming channels queue up to options::max_queued_channels, 16 by default; a channel past it is closed at once, as a connection past a listen backlog is refused.

  • Messages are kept from the channel’s creation until async_receive reads them (Receiving), so a channel accepted late, or handed from one owner to another, loses nothing it received before.

  • open, close and the buffered amount are states: a wait started after the channel opened, closed, or fell under its threshold completes at once, posted.

One wait of a kind at a time. A second wait of the same kind on the same object completes with already_started, and the first stays pending. A cancelled wait (Cancellation) consumes no event: the next wait gets what it would have got.

Waits and the io_context

A pending operation is outstanding work on the object’s executor and on its handler’s, as an Asio operation is: natively, run() does not return while a candidate or a state change is awaited. A program that starts its waits again after each completion keeps run() running until it closes the connection, and closing is how it ends. What arrives while no wait is pending is no work: a queued candidate or message does not keep run() alive.

Closing

peer_connection::close() is the W3C’s close(): every pending operation of the connection completes with operation_aborted, state() reads closed, and no state change is delivered for it. Its channels then close, and their pending operations complete with error::closed. A wait started on a closed connection completes with error::closed.

data_channel::close() completes the channel’s pending operations with operation_aborted, except async_wait_close, which completes once the channel is closed. When a channel closes for another reason, the peer, its connection, its transport, its pending operations complete with error::closed and async_wait_close completes without an error: that is how a program learns that the other side is gone.

Destroying a connection or a channel closes it first. Natively the destructor then waits until libdatachannel’s callbacks in flight for it have returned, so nothing of it is touched afterwards (The native implementation).

Data channels

A data_channel carries messages between two peers over their connection, each message whole, text or binary. A connection holds many of them, each with its own label and its own reliability: natively up to 1,024, the SCTP streams libdatachannel negotiates, so a negotiated channel’s id is under 1,024 there.

Making one

One peer creates a channel with create_data_channel(label, init) and the other accepts it with async_accept_data_channel once the connection is up. data_channel_init is the W3C’s RTCDataChannelInit: ordered, at most one of max_packet_life_time and max_retransmits for a channel that may drop messages, a protocol, and negotiated with an id for a channel both peers create themselves with the same id, which neither announces and neither accepts. create_data_channel returns a result: both reliability limits at once, negotiated without an id, the id 65535, or a label or protocol past 65,535 bytes fail with type_error; a closed connection with invalid_state; natively, under the default policy, a max_packet_life_time of 0 with operation_not_supported (What the native target cannot honour).

A channel is movable and not copyable; it belongs to whoever holds it, and its executor’s context outlives it. ready_state(), id() and buffered_amount() read what the W3C’s attributes of the same names read, as the channel opens, sends and closes; what it was created with never changes (A channel’s attributes). async_wait_open completes once the channel is open, at once when it already is, and with error::closed when it closed before it opened.

A channel’s attributes

label(), ordered(), max_packet_life_time(), max_retransmits(), protocol() and negotiated() read the W3C’s attributes of the same names, what the channel was created with. A channel the program created reads its data_channel_init; one it accepted reads what the peer announced when it opened the channel, so both ends read the same, but for negotiated(), false at the accepting end since a negotiated channel is never announced. Each is read once, when the channel is made, and costs nothing afterwards; label() and protocol() are views of text in the channel’s allocator, valid while the channel lives.

Here a channel’s messages may arrive out of order, each retransmitted three times at most, for a subprotocol of the program’s:

// Messages may arrive out of order, and each is retransmitted three times at most.
webrtc::data_channel_init init;
init.ordered = false;
init.max_retransmits = 3;
init.protocol = "chat.v1";
auto chat = a.create_data_channel("chat", init).value();

Each end reads it the same way:

// What one end of a channel reads of it, which never changes.
struct attributes {
    std::string label{};
    bool ordered = true;
    std::optional<std::uint16_t> max_packet_life_time{};
    std::optional<std::uint16_t> max_retransmits{};
    std::string protocol{};
    bool negotiated = false;
};

attributes attributes_of(const webrtc::data_channel& channel) {
    return {
        .label = std::string(channel.label()),
        .ordered = channel.ordered(),
        .max_packet_life_time = channel.max_packet_life_time(),
        .max_retransmits = channel.max_retransmits(),

Receiving

async_receive(buffer, token) appends the next message, whole, to the caller’s dynamic buffer, Asio’s first version (dynamic_buffer of a string or a vector), and completes with its size and whether it was text. The buffer outlives the operation. A message larger than the room left in the buffer (its max_size() less its size()) is not read: the operation completes with no_buffer_space and the message stays queued, for a later async_receive with a larger buffer.

Messages are kept from the moment the channel exists until they are read, in the order they came. Natively that queue is libdatachannel’s, of 1,024 messages: past it libdatachannel stops reading from the network and the peer is slowed down, a flow control that never fails. But the thread that waits for room is the one that delivers every channel of the connection, so a channel nobody reads stalls the connection’s other channels once 1,024 of its messages wait. A program reads every channel it holds, or closes it. Closing or destroying a channel discards what it holds unread, as the W3C discards what arrives once a channel left open, and releases the others; messages that arrived before the peer closed the channel are still delivered, then async_receive completes with error::closed. In the browser the queue is webrtc’s, bounded in bytes by options::max_received_bytes, since the browser has no flow control on receipt: past it the channel closes with receive_overflow (Receiving and sending).

Sending

send(buffers) and send_text(text) queue one message and return at once: nothing, or why the message was not queued, as an error_code. async_send and async_send_text do the same, and complete once the message is queued, at once, posted, for a program that composes operations. A send fails, and the channel stays open, when:

  • the channel is not open, invalid_state;

  • the message is larger than the smaller of options::max_message_size, 256 KiB by default, and the limit the peer announced, message_too_large;

  • queueing it would take the buffered amount past options::max_buffered_amount, 16 MiB by default, buffered_amount_exceeded;

  • natively, a text holds a zero byte, operation_not_supported, since libdatachannel takes a text as a zero-terminated string.

How to pace a large transfer

buffered_amount() is what the channel holds to send. async_wait_buffered_amount_low waits until it is at or under the threshold set_buffered_amount_low_threshold sets, at once when it already is. A sender keeps the buffered amount under a high-water mark of its choosing and waits for the low mark before it sends more:

// Sends `messages` messages, never more than `high_water` bytes queued at once.
class sender {
public:
    explicit sender(webrtc::data_channel& channel) : channel_(channel) {
        channel_.set_buffered_amount_low_threshold(high_water / 4);
    }

    void send() {
        while (sent_ < messages) {
            if (channel_.buffered_amount() + message_size > high_water) {
                // Too much is queued: wait until a quarter is left, then go on.
                channel_.async_wait_buffered_amount_low([this](error_code ec) {
                    if (!ec) {
                        send();
                    }
                });
                return;
            }
            if (const error_code ec = channel_.send(asio::buffer(payload_)); ec) {
                std::printf("send failed: %s\n", ec.message().c_str());
                return;
            }
            ++sent_;
        }
        std::printf("sent %zu messages, %zu bytes\n", sent_, sent_ * message_size);
    }

private:
    webrtc::data_channel& channel_;
    std::vector<char> payload_ = std::vector<char>(message_size, 'x');
    std::size_t sent_ = 0;
};

Errors

Every failure is a value. An operation completes with a boost::system::error_code; make and create_data_channel return a boost::system::result; send returns an error_code. None throws, with exceptions on or off, and none waits on the network; natively async_set_local_description makes the description in the call, which waits for the connection’s DTLS certificate, milliseconds the first time.

Memory

basic_peer_connection<Executor, Allocator> and basic_data_channel<Executor, Allocator> take an allocator as a standard container does; peer_connection and data_channel are the two with the default executor and std::allocator<std::byte>. make takes the allocator, and a connection’s channels use its own:

  • the object’s state is allocated through the object’s allocator, on the executor: the connection and its channels, the queues of candidates and of incoming channels, the text of a channel’s label and protocol, and that of descriptions and candidates, which the outputs carry, session_description and ice_candidate holding their strings in it;

  • an operation’s state is allocated through its completion handler’s associated allocator, as Asio’s operations are, so a program that binds an allocator to its handlers, or uses one with its coroutines, controls that memory too;

  • what runs on libdatachannel’s threads allocates through the standard allocator only: the copy an event carries to the executor, and the post that carries it. The object’s allocator may be a resource used only on the executor, and it is never touched from another thread;

  • what the platform holds is its own: natively, libdatachannel’s objects and the messages in its queues, and the copies its C API makes when a message is read (what reading a message costs).

The allocator outlives the io_context’s pending handlers, since a posted completion may hold the state until it runs. None of the types is shareable between threads: each is used on its executor.

The native implementation

libdatachannel

Natively webrtc wraps libdatachannel 0.24.6. No WebRTC exists in webcpp, in Boost, in the C++ Alliance’s libraries or in the standard library, and libdatachannel is the smallest complete implementation of it: data channels without a media engine, ICE through libjuice, SCTP through usrsctp, DTLS on the same source-built OpenSSL as webcpp::asio’s TLS. webrtc uses it unmodified, as a dependency, and copies none of its files: the superproject pins it at commit 6b1e2e6, with its nested sources at the commits tools/libdatachannel/pin.json lists, and builds it from them (Building a program). Nothing of it appears in a public header: a program never names libdatachannel.

libdatachannel is distributed under the Mozilla Public License 2.0, and its nested dependencies under their own licences, which the superproject’s third-party table lists. MPL’s copyleft is per file: while libdatachannel is used unmodified, it reaches none of webcpp’s files, which are under the Boost Software License alone. A program that distributes a native build of webrtc distributes libdatachannel with it, and keeps its licence and notices.

Threads

libdatachannel runs its own threads, a pool whose size runtime_options::thread_pool_size sets, and libjuice’s and usrsctp’s, which is why a native program builds with threading=multi. Every callback of libdatachannel runs on one of them, and webrtc’s do one thing there: copy what the event carries and post it to the object’s executor, through a weak reference to the object’s state, so that an event posted for an object that is gone finds nothing. No handler runs there, and nothing of the program’s allocator is touched there.

Destroying a connection or a channel runs on the executor: it closes the object, then calls libdatachannel’s rtcDelete*, which waits until the callbacks in flight for it have returned and calls none afterwards, as libdatachannel documents. The execution context outlives the object, as for Asio’s I/O objects, which is what keeps a libdatachannel thread from posting to a destroyed io_context.

Exceptions

libdatachannel reports its errors by throwing, and cannot be built without exceptions: the superproject builds its archives with exceptions whatever a program asks. Its C++ API lets those exceptions reach the caller; its C API does not, since every function of it catches what libdatachannel throws and returns a negative code instead. webrtc calls the C API only, so a program built with exception-handling=off uses the native implementation as one built with exceptions does, against the same archives, and gets every error as a value (the C API’s codes). No header of webrtc throws, tries or catches.

What the native target cannot honour

A data channel’s max_packet_life_time of 0. libdatachannel’s C API takes an unreliable channel’s limit as a lifetime when it is positive and as a number of retransmissions otherwise, so a channel created with a lifetime of 0 would be announced to the peer, a browser among them, as one of 0 retransmissions. Under the default policy create_data_channel fails with operation_not_supported; under webcpp-webrtc-unsupported=ignore (Building a program) it makes that channel, the platform’s equivalent, which both of its ends read as max_retransmits() 0. A getter has no failure to give, so a channel the peer announced with a lifetime of 0 reads as max_retransmits() 0 too, whatever the policy.

What reading a message costs

The C API reads a message by copying it out of libdatachannel’s queue into the caller’s memory, rtcReceiveMessage, which the C++ API’s receive() does not need to, since it moves the message out. webrtc first asks for the message’s size, to make room for it in the caller’s buffer, then reads it: two calls, each of which copies the message twice inside libdatachannel, four allocations and four copies in all, in libdatachannel’s allocator, before the copy into the caller’s buffer that both ways make.

The browser implementation

The page’s objects, through webcpp::asio’s bridge

Compiled with Emscripten, webrtc runs over the page’s own RTCPeerConnection and RTCDataChannel. Each connection and each channel is one registration of webcpp::asio’s bridge, the service of the io_context through which the page’s JavaScript events reach C++: the browser’s event handlers deliver to it, it records what arrived in the object’s state and posts at most one notification for all of it, and the notification completes the waits on the executor, in the order the browser delivered what they wait for: a description’s settlement delivered before the first candidate completes async_set_local_description first, so that a program that sends each candidate as it comes sends its offer before them. No handler of the program runs inside a JavaScript event, and an event reaches the program only while it has returned to the page’s event loop or while run() is suspended, in either of webcpp::asio’s suspension variants, jspi and asyncify. When the io_context is destroyed with operations pending, its shutdown destroys their handlers without calling them, as Asio’s own operations are, even when a handler holds the last owner of the object it waits on.

Every call into the browser is a JavaScript function that catches what the browser throws before it reaches WebAssembly and reports it by its DOMException name, so the browser implementation raises nothing of its own and works with exceptions on and off, as natively. A promise, as setLocalDescription() returns, is followed through the same bridge, whose event says how it settled. The names become values of webcpp.webrtc: InvalidStateError, OperationError, InvalidAccessError, TypeError and SyntaxError the value of the same name, any other operation_error.

The page’s census

The browser keeps no count of its connections that a program could read, and Chromium refuses more than 500 on a page. So the page keeps a census of its own, in JavaScript: every RTCPeerConnection webrtc makes counts from its construction until a FinalizationRegistry sees it collected. The max_peer_connections of a runtime caps that census, and peer_connections() reads it: in the browser it counts every webrtc connection of the page, whatever runtime made it, until it is garbage-collected, not only until it is destroyed. runtime_options::thread_pool_size means nothing there.

Receiving and sending

The browser delivers every message it receives at once, with no flow control, so webrtc keeps a channel’s unread messages in a queue bounded in bytes, in the channel’s allocator: options::max_received_bytes counts each message’s payload and the bookkeeping of its record, and is charged when the browser delivers the message, before the executor reads it, so that a busy or stopped io_context cannot make the page’s memory grow. Past it, or when a received message passes options::max_message_size, the channel discards what it holds unread and closes: ready_state() reads closing, then closed, and async_receive completes with receive_overflow or message_too_large.

A send is checked before the browser sees it, so a refused send leaves the channel open, as natively: the channel’s live readyState first, then the smaller of options::max_message_size and the peer’s maxMessageSize, then options::max_buffered_amount. A text must be valid UTF-8, since the browser sends a JavaScript string, or the send fails with type_error; it may hold a zero byte, which the native implementation refuses, and a leading byte order mark is part of it, sent and received as any other character.

Candidates

A local candidate carries all four of the W3C’s members, the media line’s index and the user name fragment among them. The browser ends each gathering generation with an empty candidate of its own; webrtc delivers the end of gathering once, when the browser has nothing more to gather. A remote candidate follows the browser’s own order of operations: a non-empty one follows the browser’s promise, so that one added while the remote description is still being applied is applied after it, and one added with no remote description fails with invalid_state. An empty one, the end of the remote candidates, never reaches the browser, as natively: it completes at once when a remote description is applied, after the one being applied settles, and with invalid_state when there is none.

What the browser cannot honour

configuration::bind_address names the one local address ICE binds to, which a browser cannot choose. Under the default policy make fails with operation_not_supported; under webcpp-webrtc-unsupported=ignore the address is ignored, since the browser chooses its addresses itself (Building a program).

Differences from the W3C’s API

webrtc follows the W3C’s WebRTC API where a platform allows it. Where one does not, the difference is here, with what a program gets instead.

What a target cannot honour follows one rule: by default it fails with operation_not_supported; under the b2 feature webcpp-webrtc-unsupported=ignore it is ignored, which a setting may be only where the platform does something equivalent of its own. The feature is propagated, so a whole program agrees, and setting both WEBCPP_WEBRTC_UNSUPPORTED_ERROR and WEBCPP_WEBRTC_UNSUPPORTED_IGNORE stops the build. Natively every setting is honoured, but a data channel’s max_packet_life_time of 0, which the rule decides (What the native target cannot honour); in the browser the rule decides configuration::bind_address (What the browser cannot honour). A getter has no failure to give: where a platform holds an attribute otherwise than the W3C says, the table says what the getter returns, whatever the policy.

Guarantees

What webrtc promises, and the tests that hold each promise, which fail when the promise breaks. A guarantee keeps its number, and the anchor named after it, so a comment of the code or of a test cites it by that anchor: (doc: #webrtc-invariant-3) sends its reader to the third. The tests are those of Testing.

  1. Two peers connect and talk. Two native peers on the loopback exchange their descriptions and every candidate, none refused, reach connected, and carry binary and text messages both ways, each read with whether it was text; so do two peers in one page of a browser. Held by native (a_full_exchange), the browser lane (browser_test, a_full_exchange) and every example of the page.

  2. Every handler runs on the object’s executor, and never inside the call that started its operation. An operation satisfied at once is posted; nothing of libdatachannel’s threads runs a handler. Held by events (a_satisfied_wait_is_posted), native, and lifetime under ThreadSanitizer; in the browser by browser_imports (resolutions_deliver_their_outcome), whose imports never re-enter C++.

  3. No event is lost without a rule. While no wait is pending, states coalesce to the latest, candidates queue up to their bound with a place kept for the end of gathering, and incoming channels queue up to theirs; a second wait of a kind fails with already_started, and a cancelled wait consumes nothing. Held by events (states_coalesce, no_change_keeps_waiting, one_wait_of_a_kind, a_cancelled_wait_consumes_nothing, the_bound_keeps_a_place_for_the_end).

  4. A channel keeps what it received before its first read. Messages are kept from the channel’s creation until async_receive reads them, in order. Held by native (received_before_the_first_receive) and the browser lane (received_before_the_first_receive, accepted_after_its_messages).

  5. close() delivers no state change. A closed connection’s pending operations complete with operation_aborted, its channels close with error::closed, and a later wait fails with error::closed; a channel closed by its owner completes its async_wait_close. Held by native (close_fires_no_state_change, a_channel_closed_by_its_owner) and events (close_aborts_and_then_refuses).

  6. run() returns once the connections are closed. A pending operation is outstanding work, and a program that starts its waits again keeps run() running until it closes its connection. Held by native (run_returns_once_closed).

  7. Every failure is a value. Of the category webcpp.webrtc, whose ten values are fixed, or one of Asio’s; nothing throws, with exceptions on or off. Held by error, native (errors_as_values) and the example webrtc_errors.

  8. A refused send or receive leaves the channel as it was. A send past the message size or the buffered amount fails and the channel stays open; a message larger than the room left in the caller’s buffer fails with no_buffer_space and stays queued, then reads into a larger buffer. Held by native (bounds).

  9. The native implementation works without exceptions. Built with exception-handling=off, against libdatachannel’s archives built with exceptions, it behaves as with them. Held by native_no_exceptions, events_no_exceptions, and every header compiled alone without exceptions. The browser implementation works without them too: every emscripten test that runs a program, under Node in both suspension variants (its _asyncify twins), and every program of the browser lane runs again with exception-handling=off.

  10. The object’s memory is its allocator’s, on its executor. Its state, queues and outputs are allocated through it, an operation’s state through its handler’s allocator, and nothing of the object’s allocator is touched on libdatachannel’s threads. Held by allocation (state_queues_and_outputs_in_the_allocator) and events (an_operation_is_in_its_handlers_allocator).

  11. Destruction is safe while events arrive. A connection and its channels destroyed while the peer floods them touch nothing afterwards, round after round. Held by lifetime (destroyed_while_messages_arrive), 100 rounds under ThreadSanitizer.

  12. A channel never read stalls its connection’s others, and its destruction releases them. Past 1,024 unread messages, natively, a message on another channel of the connection does not arrive; destroying the flooded channel releases it, and returns in under two seconds. Held by stall and lifetime (a_flooded_channel_is_destroyed_promptly), so that a change of libdatachannel’s behaviour fails them and this page changes with it.

  13. The runtime caps the connections alive at once. make past the cap fails with too_many_peer_connections, and a connection’s place follows its moves and is given back when it is destroyed. Held by native (errors_as_values, destruction_and_moves).

  14. A negotiated channel opens on both peers with the same id, and neither accepts it. Held by native (a_negotiated_channel).

  15. In the browser, unread messages never pass their budget. A channel’s unread messages and their records stay within options::max_received_bytes, charged as the browser delivers them; past it, or past max_message_size, the channel closes and async_receive completes with receive_overflow or message_too_large. Held by browser_backend (the_budget_or_the_size) and the browser lane (unread_messages_past_the_budget, a_received_message_past_the_size).

  16. Translation units that disagree on the unsupported policy do not link together. The classes live, on both targets, in an inline namespace named after the policy, so a channel passed between two such units names two different types. Held by config_boundary, which links, and config_mismatch, which must not, natively and on emscripten.

  17. A native peer and a browser peer connect and talk. A native peer and a peer in headless Chrome, signalled through a relay as JSON of the W3C’s RTCSessionDescriptionInit and RTCIceCandidateInit, connect with either one offering and exchange messages both ways, in both suspension variants; the page’s peer passes on every candidate Chrome gathers, in order, with the end. Held by the interop lane.

Testing

Testing a program that uses webrtc

A test needs neither the network nor a second machine: two peers in one process, each made with configuration::bind_address set to "127.0.0.1" and no ICE server, connect through the loopback’s host candidate alone, as the examples of this page do. The test hands each peer’s descriptions and candidates to the other directly, in place of its signalling channel (trickling candidates), runs the io_context with a limit, so that a broken exchange fails rather than hangs, and makes one runtime per case, one case after another (The runtime).

How webrtc is tested

webrtc’s tests are under test/, each declared in test/Jamfile, and each guarantee of Guarantees names the tests that hold it. They run on two targets, 75 tests in all, 37 natively and 60 on emscripten, under Node and in headless Chrome, with every connection on the loopback and no STUN, so that a lane with no network but the loopback runs them whole. The native suite runs as the build asks and without exceptions:

webcpp.run native : native_test.cpp : <library>/webcpp/webrtc//webrtc <threading>multi : native ;
webcpp.run native_no_exceptions : native_test.cpp
  : <library>/webcpp/webrtc//webrtc <threading>multi <exception-handling>off : native ;
Test What it checks

the public headers

Each compiled alone, with libdatachannel, as the build asks and, through the lint, without exceptions.

config, config_developer_defined, config_all_off

<webcpp/webrtc/config.hpp> defines WEBCPP_WEBRTC_NO_EXCEPTIONS exactly when webcpp has no exceptions, and keeps it when a developer defines it in a build that has them.

error, types, and their _no_exceptions twins

The category’s name and fixed values, a message for each, the options’ defaults, and the value types: their defaults, a description’s and a candidate’s view, and their text in a polymorphic allocator.

events, events_no_exceptions

The event machinery both implementations share, without a platform: states coalesce, one wait of a kind, a cancelled wait consumes nothing, the bound keeps a place for the end of gathering, a satisfied wait is posted, close aborts and then refuses, and an operation lives in its handler’s allocator.

native, native_no_exceptions

Two peers on the loopback: a full exchange, messages received before the first read, a channel’s attributes as created and as announced, a negotiated channel, errors as values, the bounds, close, a channel closed by its owner, destruction and moves, and run() returning once closed.

allocation

A connection pair over a polymorphic allocator on a counting resource: the state, a channel’s protocol at both ends among it, the queues and the outputs allocate there, and nothing of it on another thread than the one that runs the io_context.

lifetime

Connections and channels destroyed while the peer floods them, repeated, and a channel flooded and never read destroyed in under two seconds.

stall

A channel past 1,024 unread messages stalls its connection’s others, and its far end’s destruction releases them.

bench

The receive benchmark’s smoke pass (what reading a message costs): a few rounds of each path, each message checked.

browser_imports, browser_runtime, browser_backend

On emscripten, under Node, which has no RTCPeerConnection: the browser calls catch what JavaScript throws and report it by name, never re-entering C++, and texts cross whole; the census and the cap, a slot freed once a connection is collected; and the browser implementation’s semantics over a fake connection and channel of the test’s own, a channel’s attributes, the order of arrivals of different kinds, cancellation, a close with a notification in flight, and the io_context destroyed while handlers own the objects. Each runs with exceptions off too, and in the asyncify variant, its _asyncify twins, which form the own lane asyncify on emscripten, as webcpp::asio’s do: a target that names <webcpp-suspend>asyncify belongs in a lane of emscripten’s, since a build with no emscripten configured cannot expand that feature.

native_policy, native_policy_ignore, and their _no_exceptions twins

A data channel’s max_packet_life_time of 0 under each policy: refused with operation_not_supported, or made with 0 retransmissions, which both of its ends read.

browser_policy, config_boundary, config_mismatch

bind_address under each policy, and two translation units with different policies that fail to link when they pass a channel between them, natively and on emscripten, with their twins likewise.

the browser lane

Two peers in one page of headless Chrome (test/browser/): every native case that applies and the browser’s own, the receive budget and the size limit, refused sends, the close paths, allocation through a counting resource and bind_address, each program in both suspension variants and with exceptions off.

the interop lane

A native peer and a peer in headless Chrome (test/interop/), the same code against the public API, signalled through a relay over webcpp::beast’s WebSocket on 127.0.0.1: each offers in turn, sends ping and gets pong, in both suspension variants; natively, two peers through the same relay.

From the root of a webcpp checkout, the first two of these build and run the tests and the examples natively, as the build asks and without exceptions, and the third runs the tests under AddressSanitizer and UndefinedBehaviorSanitizer:

b2 threading=multi libs/webrtc/test libs/webrtc/example
b2 threading=multi exception-handling=off libs/webrtc/test libs/webrtc/example
b2 threading=multi address-sanitizer=norecover undefined-sanitizer=norecover libs/webrtc/test

On emscripten the tests run under Node, and the browser and interop lanes in headless Chrome, which CHROME names, else Playwright’s cached Chromium on macOS. Both start Chrome with --disable-features=WebRtcHideLocalIpsWithMdns, so that a page’s host candidates are its addresses; the browser lane checks first, with two peers of plain JavaScript, that the browser connects at all. Chrome 156 offers a page with no media permission only its default-route address, so the interop driver grants the page’s origin the microphone, which starts no capture, and the page then offers 127.0.0.1 too, where the native peer listens. The lanes run by name:

b2 toolset=emscripten webcpp-suspend=jspi libs/webrtc/test
b2 toolset=emscripten webcpp-suspend=asyncify libs/webrtc/test
b2 toolset=emscripten libs/webrtc/test/browser//browser
b2 threading=multi libs/webrtc/test/interop//interop
b2 toolset=emscripten libs/webrtc/test/interop//interop

The lifetime and native tests run under ThreadSanitizer too, the lifetime test for 100 rounds, which checks webrtc’s side of every hand-off between libdatachannel’s threads and the executor; libdatachannel’s archives are not instrumented:

b2 threading=multi thread-sanitizer=on define=WEBCPP_TEST_WEBRTC_REPEAT=100 libs/webrtc/test//lifetime libs/webrtc/test//native

b2 compares timestamps, so a result that counts is built from scratch, with b2 -a. The CI runs the tests on every native compiler of webcpp’s lanes, GCC, Clang on libstdc++, Apple Clang and MSVC, and on emscripten, the browser lane with its pinned Chrome, and the test matrix of every run is at https://webcpporg.github.io/report/.

Messages are kept from the channel’s creation until async_receive reads them: natively in libdatachannel’s own bounded queue, which slows the peer when it is full; in the browser in a queue of the object’s allocator bounded by options::max_received_bytes. Description

A message larger than the room left in buffer stays queued, and the operation completes with no_buffer_space. Once the peer closed the channel, the messages it sent before are still delivered, then the operation completes with error::closed. In the browser, once the unread messages passed options::max_received_bytes, or a message options::max_message_size, the channel closed, what it held is discarded, and the operation completes with error::receive_overflow or error::message_too_large.

webcpp::webrtc::runtime

What the platform holds for the whole process, or the whole page, which the program owns: natively libdatachannel’s threads and global state, and on both targets the cap of peer connections.

Synopsis

Declared in <webcpp/webrtc/runtime.hpp>

class runtime;

Description

A program makes one before any peer connection and destroys it after the last, and after the last data channel; make takes it by reference, so no connection exists without one.

Natively at most one exists at a time in a process, because libdatachannel’s state is the process’s: a second one’s destructor would end the first one’s connections. That is a precondition: webrtc keeps no static state to check it with. A native runtime counts the connections made with it.

In the browser the count is the page’s, kept in JavaScript, so that every runtime and every module of the page counts in one place, as Chromium counts its own limit: a connection counts from its construction until the garbage collector frees it, a closed one included.

Appendix A: Changelog

What changed in webrtc in each version of webcpp, newest first, one line per change. "Unreleased" is what the next version brings. The release notes of every version are on webcpp’s index page.

Unreleased

  • Added peer connections and data channels with the W3C’s names, in Asio’s model.

  • Added the native implementation over libdatachannel’s C API, with exceptions on and off.

  • Added the browser implementation over the page’s own RTCPeerConnection.

  • Added a data channel’s ordered, max_packet_life_time, max_retransmits, protocol and negotiated.

  • Added the unsupported policy natively; by default it refuses a max_packet_life_time of 0.

  • Added a runtime that holds libdatachannel’s threads and caps connections.

  • Added errors as values, in the category webcpp.webrtc and Asio’s codes, and [[nodiscard]] on every function that returns a boost::system::result.

  • Added the library’s page, with its examples, guarantees and differences.
